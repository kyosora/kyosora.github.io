Content Security Policy 實戰：用 nonce、hash 與 strict-dynamic 擋 XSS

發表於2024-11-06|資訊安全
|總字數:3.1k|閱讀時間:11分鐘

CSP 是 XSS 的第二道防線

先把邊界講清楚：Content Security Policy 不能修掉 XSS 漏洞。輸出編碼、HTML sanitization、避免危險 DOM sink 仍是第一道防線；CSP 的工作是限制腳本從哪裡載入、哪些 inline script 能執行，以及能不能使用 eval() 這類字串執行 API，讓注入成功後不一定能跑起來。

攻擊者注入 XSS 時，塞進 DOM 的往往是 <script>alert(document.cookie)</script> 這種直接寫在 HTML 裡的程式碼，或是 onclick="..." 這類行內事件處理器。瀏覽器一旦套上嚴格的 script-src，這些東西就跑不起來——這才是 CSP 的價值所在。

當 script-src 裡的 'unsafe-inline' 真的生效，inline <script>、事件處理器與 javascript: URL 都可能被放行，CSP 對常見 XSS 注入的防護會大幅下降。其他指令仍能限制圖片、連線、frame 與外部資源，所以不能說整份 CSP 完全沒用；但 script-src 這條最重要的防線確實被放鬆了。

我的目標會先定成：讓網站不靠生效中的 'unsafe-inline' 也能運作，再處理 unsafe-eval、來源範圍與其他指令。只盯一個關鍵字，還不足以判斷整份政策好不好。

動態頁用 nonce，靜態頁用 hash

那自家確實需要的 inline script 怎麼辦？答案是 nonce 或 hash，兩個都不是 unsafe-inline。

nonce（number used once）是伺服器每次回應產生的一次性 token。HTTP header 裡寫進這次的 nonce，HTML 裡每個合法的 inline script 標籤帶上同一個值，瀏覽器只執行對得上的那些：

攻擊者注入的 script 不知道這次的 nonce 是多少（每個請求都不同），所以執行不了。

nonce 不能從 URL、表單值或其他使用者輸入推導，也不能讓 CDN 把同一份 HTML 與 nonce 長時間快取給所有人。若 HTML 會經過快取，必須確認 header 與文件中的 nonce 成對更新；能完全靜態化的頁面，hash 通常更省事。

只有雜湊一致的 inline script 會被執行，連空白差一格都不行。靜態頁面或內容不會變的腳本用 hash，動態渲染的頁面用 nonce。

這裡有個容易誤會的細節：當 script-src 同時含有效 nonce 或 hash 時，支援 CSP Level 2 以上的瀏覽器會忽略同一指令裡的 'unsafe-inline'。Google 的 strict CSP 相容範例會保留它給舊瀏覽器使用；新瀏覽器則走 nonce／hash。真正危險的是 script-src 'self' 'unsafe-inline' 這種沒有 nonce 或 hash、讓 'unsafe-inline' 實際生效的配置。

strict-dynamic 省掉維護白名單的痛

只用 nonce 還有個現實問題：很多第三方腳本（Google Analytics、各種 SDK）載入後又會自己再去載別的腳本。那些被動態載入的腳本沒有 nonce，會被擋下來。逐一把域名加進白名單既煩又脆弱——研究早就指出，大多數 script-src 白名單能被有 XSS 漏洞的攻擊者繞過。

'strict-dynamic' 會把 nonce 或 hash 給「根腳本」的信任，傳遞給它用非 parser-inserted 方式建立的後續腳本。支援 CSP Level 3 的瀏覽器會忽略同一指令裡的 'self'、host source、scheme source 與 'unsafe-inline'，因此不用維護一長串 script host 白名單。

代價也要寫出來：只要受信任的根腳本會拿未驗證的 URL 建立 <script>，攻擊者就可能沿著這條信任鏈載入任意程式碼。strict-dynamic 省的是白名單維護，不是省掉對 loader 與第三方腳本的審查。

Google 官方建議的嚴格 CSP 長這樣：

讀法是：支援 CSP Level 3 的瀏覽器採 nonce + 'strict-dynamic'；CSP Level 2 瀏覽器採 nonce + https:；只懂 CSP Level 1 的舊瀏覽器才會退回 https: + 'unsafe-inline'。這是相容性取捨，舊瀏覽器拿不到同等防護，不能寫成所有瀏覽器都一樣安全。

導入順序：Report-Only 觀察，收白名單，上 nonce

直接把嚴格 policy 推到生產環境，大概率把自家功能擋一片。正確順序是三步走。

第一步，Report-Only 模式觀察。用 Content-Security-Policy-Report-Only 取代正式的 header，瀏覽器只回報違規、不真的擋。先看看現況到底違反了哪些規則：

report-uri 已被標記為過時，但瀏覽器相容性仍較廣；新做法是 Reporting-Endpoints header 搭配 CSP 的 report-to。兩個指令可暫時並存，支援 report-to 的瀏覽器會忽略 report-uri。違規報告是攻擊者可控制的輸入，接收端必須限制大小、驗證格式，顯示到後台前也要編碼。

第二步，依報告收斂。看報告裡冒出哪些合法的外部域名、哪些自家 inline script 被點名，逐一處理：能搬到外部檔案的 inline script 就搬出去，必要的外部域名加進對應指令。這一步的產出是一份「不含生效中 'unsafe-inline'」的草稿 policy。

第三步，上 nonce／hash 並切正式 header。把確實要保留的 inline script 改掛 nonce 或 hash，policy 從 Report-Only 換成正式的 Content-Security-Policy，開始真正執行。切換後繼續收報告，因為 Report-Only 沒走到的功能不會憑空消失。

順序反過來——先上嚴格 policy 再修——只會在生產環境炸一輪，被迫回頭加 'unsafe-inline' 滅火，然後就再也拿不掉了。

meta 標籤設 CSP 有功能限制

CSP 可以走 HTTP header，也可以用 <meta> 標籤：

但 meta 標籤設的 CSP 不支援 report-uri、frame-ancestors、sandbox 這幾個指令，寫了也會被忽略。meta 也只會影響它之後解析到的內容，放在前面的資源來不及管。要做違規回報、防點擊劫持或完整政策，還是應該由 HTTP response header 發送。

所以要用回報機制、防點擊劫持（frame-ancestors），就只能走 HTTP header。meta 標籤適合沒有後端控制 header 的靜態託管場景，當作備案。

載外部腳本配 SRI

放行了外部腳本來源，還有一層風險：CDN 被入侵、檔案被掉包，你的白名單照樣放行那個被竄改的檔。Subresource Integrity（SRI）擋這個。

做法是在 tag 上放 integrity（內容雜湊）；跨來源資源通常還要加 crossorigin="anonymous"，並確保 CDN 回應通過 CORS：

瀏覽器抓到檔案後算雜湊，對不上就拒絕執行。同源資源不必為了 SRI 強加 crossorigin；跨來源時若 CDN 沒回正確的 CORS header，資源會載入失敗。SRI 適合版本固定的檔案，會在同一 URL 原地更新內容的 CDN 反而不適合直接寫死 hash。

提醒一個過時資訊：曾經有個 require-sri-for script style 的 CSP 指令可以強制所有腳本都得帶 integrity，但它是實驗性的、已經從主流瀏覽器移除。現在的做法是直接在每個 tag 掛 SRI 屬性，靠 build 流程或 lint 規則確保沒漏掉，不要依賴那個指令。

真的拿不掉 unsafe-inline 的時候

有些第三方函式庫會在執行期注入 <style>、整段 cssText 或 inline style attribute，你又改不了它的原始碼。但先別急著把 'unsafe-inline' 加回去。我自己處理 ArcGIS 時，一開始也以為拿不掉；換成 IIS build 產物巡覽 94 個頁面後，最後成功移除，只留下少數 ArcGIS violation 且已測功能正常。完整過程在另一篇：AI 篤定說 CSP 的 style-src unsafe-inline 拿不掉，我追問一句後它道歉了。那次經驗剛好證明：console 有 violation，不等於功能必然壞掉，更不等於立刻接受風險。

真的拿不掉時，按這幾條走，而不是拿話術帶過：

優先只在 style-src 妥協，不要動 script-src。inline script 能直接執行 JavaScript，風險通常高於 inline style；但 CSS 注入仍可能做資料側錄、遮蓋介面或仿造登入畫面，不能寫成低風險。真要保留時，必須連同資料敏感度與頁面功能一起評估。

限縮到最小範圍。別整站都掛 'unsafe-inline'。只在真的需要的回應與指令上開，其他頁面維持嚴格。

誠實記錄成已知風險。寫進安全文件：哪個指令開了 'unsafe-inline'、影響哪些頁面、是哪個函式庫、測過哪些功能、補償措施與重測條件是什麼。對稽核照實列出證據與未覆蓋範圍，不要用「業界都這樣」帶過。

收尾

我以前會看到 'unsafe-inline' 就直接判定拿不掉，ArcGIS 那次實測後不再這樣做。現在的順序是先上 Report-Only，確認 violation 來源，再用 nonce／hash、外部檔案或套件設定處理；'strict-dynamic' 只在根腳本與動態 loader 都能審查時使用。真的需要放寬，才把範圍、版本與未測功能寫進風險紀錄。

判斷一份 CSP 不能只看一個字串。至少要一起檢查：

  • script-src 是否有生效的 'unsafe-inline' 或 'unsafe-eval'
  • nonce／hash 是否每次正確產生，strict-dynamic 的 loader 是否吃到不可信 URL
  • object-src、base-uri、frame-ancestors 是否符合需求
  • connect-src、img-src 等資料外傳路徑是否放得過寬
  • 違規報告、實際功能測試與套件升級後重測是否真的在跑

unsafe-inline 是很醒目的警訊，但它不是整份 CSP 的總分。
