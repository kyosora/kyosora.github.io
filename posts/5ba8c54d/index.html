eMudhra 憑證外洩：Windows 擋了，Java、Node 照樣放行

發表於2026-10-22|資訊安全系統與維運
|總字數:6.1k|閱讀時間:22分鐘

微軟 10 月 20 日透過 Windows 的自動更新，擋掉了 eMudhra 那幾張私鑰外洩的中繼憑證。我在開發機上用 curl.exe 連事件頁提供的測試站，確實被擋：

同一台機器、同一個測試站，換 Java 連。這台裝了四個 Java：自己裝的 JDK 17、JRE 8，還有 Rider、PyCharm 內建的 JBR。四個都至少有一條路徑連上了。

eMudhra 是印度的憑證機構。Mozilla 的事件報告寫得很直接：受影響的 8 把私鑰都是小於 256 的整數，實質上除了最後一個 byte 全是 0，最多試 255 次就算得出來。其中 6 把屬於簽網站憑證的中繼 CA，算出私鑰的人可以替任何網站簽憑證。Oracle 為此在 10 月 21 日發了季度更新之外的緊急公告 CVE-2026-91403，CVSS 9.1，跟上一篇的 PHP2Shell 同一天。要補的不是 Java 的程式碼，是 Java 的憑證信任判斷：舊版 Java 仍會接受這些中繼憑證簽出的憑證。

這篇是我把這台機器上的 Java、Node、Python、Go、.NET 逐一測過的紀錄，最後一段寫離線內網機怎麼檢查、怎麼補。測的是程式連出去時怎麼驗證對方的憑證，跟你 IIS 網站自己掛的憑證無關。

eMudhra 發生什麼事

  • 8 張中繼憑證：6 張 TLS 用（EM DV／OV／EV TLS CA - G3B、G3C），2 張程式碼簽章用（EM OV CS CA - G3B、G3C），2025 年 4 月 30 日簽出。
  • 每張都有兩個版本：一張由 eMudhra 自己的根憑證簽，一張由 Sectigo 的 AAA Certificate Services 交叉簽（5 月 14 日），兩張共用同一把金鑰，所以 8 把私鑰對應 16 張憑證。事件頁的測試站是 6 張 TLS 中繼各兩條路徑，共 12 條；程式碼簽章那 4 張不走 HTTPS，不在裡面。下面的實測也分成「eMudhra 根」和「AAA 交叉簽」兩條路徑。
  • 時間線：回報者 Wayne 10 月 17 日用 8 把私鑰各簽了一句 "We have a problem here - Wayne"，證明私鑰到手。Firefox、Chrome 當天就擋。eMudhra 18 日撤銷自己簽的 8 張，Sectigo 19 日撤銷交叉簽的版本。依事件頁的紀錄，Apple 19 日、微軟 20 日跟進。Oracle 和 OpenJDK 21 日發公告，Node.js 同一天的安全更新也包了進去。

事件頁有一段話，我認為是整件事的重點：那段期間的憑證透明度（Certificate Transparency，CT）紀錄裡，查不到經由這些中繼憑證簽出的憑證，所以在那段期間，會強制檢查 CT 的瀏覽器不會被這些私鑰偽造的網站憑證騙到。不強制 CT 的客戶端有沒有被攻擊過，沒有人知道。

許多非瀏覽器的程式預設不檢查 CT：Java 後端、Node 服務、Python 腳本、curl、監控系統。eMudhra 已經撤銷憑證，可是很多客戶端不讀撤銷資訊，只能各自更新信任判斷。

每個執行環境，各信各的

每個執行環境都有一份「我信任哪些根憑證」的清單。瀏覽器一份，Windows 一份，Java 的 cacerts 一份，Node 編譯時內建一份，Python 的 requests 用 certifi 套件帶的一份。微軟 10 月 20 日更新的，只有 Windows 那份。

Claude Code 照我的需求寫了幾支探測程式，各連兩條路徑的測試站，再連 google.com 當對照組（對照組全部正常，表上不列）。以下是這台機器的驗證結果，「放行」代表這個執行環境還接受外洩中繼憑證簽出的憑證：

「擋」是看到明確的封鎖或撤銷錯誤。「沒建成」是那份清單剛好沒有對應的根憑證，連不到底，不算修補。Rider 那個 JBR 拒絕 eMudhra 根路徑，是因為它的 cacerts 舊到還沒收 eMudhra 的根憑證。Windows 的根憑證區則是用到才下載，別台機器如果已經裝了 eMudhra 的根，其他條件相同的話，Python ssl 那格也可能放行。

這次測的、用預設驗證設定的程式裡，規律很清楚。直接呼叫 Windows 驗證 API 的，跟著 Windows 一起擋。只拿 Windows 的根憑證清單回去自己驗的（Python 的 ssl、Node 的 --use-system-ca、下面會提到的 Java Windows-ROOT），擋不住。自帶清單的，要各自更新。

Windows：擋下來的是封鎖清單

curl 回的錯誤碼叫 CRYPT_E_REVOKED，我一開始以為擋下來的是撤銷檢查，也就是 curl 連到 eMudhra 的 CRL 查到「已撤銷」。如果是這樣，查不到 CRL 的離線內網機就擋不住。

加上 --ssl-no-revoke 關掉撤銷檢查再連一次，還是同一個錯誤。再用 .NET 的 X509Chain 在本機建鏈，撤銷模式設成 NoCheck，不查 CRL 和 OCSP：

ExplicitDistrust 表示 Windows 明確不信任這張憑證。來源可能是本機的不信任憑證區，也可能是自動更新下來的封鎖清單（Disallowed CTL）。這台的不信任憑證區是空的，所以去看封鎖清單：它存在登錄檔 HKLM\SOFTWARE\Microsoft\SystemCertificates\AuthRoot\AutoUpdate 的 DisallowedCertEncodedCtl，匯出來用 certutil -dump 看，這版 ThisUpdate 是 2026/10/19 09:53（台灣時間），當下有 96 筆。事件頁記錄微軟是 20 日封鎖，微軟下載點上那個檔案的修改時間也是 20 日（18:02 UTC），清單內容則是 19 日就建好了。

Claude Code 一開始拿 16 張憑證的 SHA-1 指紋去比，一張都沒比到。回頭看 dump，這份清單用的雜湊不是憑證指紋，本次 eMudhra 這 8 筆用的是公鑰的 MD5。換成公鑰雜湊，16 張全中：兩個交叉簽版本共用同一把公鑰，所以 8 筆就擋掉 16 張，就算有人用同一把金鑰再簽一張新的中繼憑證，也一樣擋得住。

這條路有兩個前提：程式要走 Windows 的驗證 API，機器要收得到封鎖清單的更新。curl、.NET Framework、Go（Windows 版、預設設定）、truststore 都符合第一個，所以 Go 1.20.1 這種三年多前的版本也擋了下來。只是 Go 回的錯誤寫 certificate signed by unknown authority，看不出其實是被封鎖。

第二個前提，就是離線內網機的問題，放到最後一段講。

我接著想，既然 Windows 擋了，叫 Java 改用 Windows 的信任庫不就好了？JDK 在 Windows 上可以加 -Djavax.net.ssl.trustStoreType=Windows-ROOT。JDK 17 和 JRE 8 都試了，AAA 交叉簽那條照樣放行。Windows-ROOT 只讀 Windows 的根憑證清單，驗證還是 Java 自己做，不會去看封鎖清單。反過來，在這次用的預設驗證流程下，換成 Windows-ROOT 仍會套用 Java 自己的封鎖檔，所以下面的修法對它一樣有效，我也測過。

能處理的做法有三個，都實測過。不管用哪一種，每一個獨立安裝的 Java 都要各做一次：IDE 內建的 JBR、廠商系統安裝包裡自帶的 JRE、Tomcat 旁邊那個 jre 資料夾，都算。部分 Linux 發行版會把系統的憑證清單同步到套件版 OpenJDK 的 cacerts，照發行版公告更新之後，還是要確認程式實際用的是哪份信任庫，再跑一次探測。

升級

Oracle 公告列的受影響版本有 17.0.21、21.0.13、25.0.5、27.0.1 這些，也就是 10 月 20 日季度更新剛發的版本，剛升完季度更新的還要再升一次。修補版是 17.0.21.0.2、21.0.13.0.2 這類多一碼的版本。JDK 8 要看 build 號：Oracle 的修補版仍然叫 8u511，只是 build 從 10 月 20 日的 b09 換成 b32，要看 java -version 印出的完整版本才分得出來。OpenJDK 那邊寫 8u512 以前都受影響，以各廠商 10 月 21 日之後的緊急 build 為準。IDE 更新之後，記得確認它實際用的 JBR 版本。

換掉 blocked.certs

OpenJDK 公告提供了更新過的檔案，Windows 版在 https://ops.java/windows/blocked.certs。我這邊用 curl 抓回 403，改用瀏覽器才下載到。

打開撤銷檢查

啟動參數加 -Dcom.sun.net.ssl.checkRevocation=true -Dcom.sun.security.enableCRLDP=true，兩條路徑都被擋，原因寫的是 CA_COMPROMISE。兩個參數要一起加，這是 Oracle 給 TLS 應用程式的建議，適用預設的 JSSE 驗證流程，自己寫 TrustManager 的程式不一定吃這組參數。

它要拿得到 CRL 才有用，不能把它當成離線內網機的修補方式。Java 預設在查不到撤銷狀態時會直接判失敗，在連不到外網的環境開啟之前要先測過，不然其他連線也可能一起斷。

（順帶一提，AAA 交叉簽那張的撤銷時間是 2025-05-14，也就是它的簽發日，CA 把撤銷時間追溯到了簽發當天。）

Node：舊版加 --use-system-ca，反而多放行一條

Node 22.22.0 預設用編譯時內建的根憑證清單，來源是 Mozilla。Mozilla 在 2025 年 4 月撤掉了 AAA Certificate Services 的網站信任，Node 從 22.20.0 起內建清單就不再收它，所以 AAA 那條沒建成，eMudhra 根那條放行。

Node 22.15.0 起有 --use-system-ca，讓 Node 額外讀作業系統的憑證。我原本以為加了它就會跟著 Windows 擋，實際結果是兩條都放行。它把 Windows 的根憑證（包括 AAA）加了進來，封鎖清單卻沒跟著帶進來。Node 文件其實寫了：目前不支援依照系統設定，撤銷或不信任其他來源的憑證。

修補版 22.23.4 不管加不加 --use-system-ca，兩條都擋，錯誤是 CERT_REVOKED。Node 這次的做法是在 TLS 驗證時比對一份內建的公鑰雜湊封鎖清單，跟微軟一樣是擋公鑰。修補版本是 22.23.4、24.22.1、26.12.1。Node 沒有像 Java 那樣換個檔案就能套用的官方暫時解法，建議直接升到修補版。

Python：同一台機器，三種結果

Python 最亂，因為同一個直譯器裡就有三種驗證方式：

  • 標準函式庫 ssl：ssl.create_default_context() 在 Windows 上會讀系統的根憑證區，再交給 OpenSSL 自己驗，不看封鎖清單。這台的根憑證區有 AAA，所以 AAA 那條放行。
  • requests：預設用 certifi 套件帶的清單。這台的 certifi 是 2025.01.31，裡面 AAA 和 eMudhra 的根都有，兩條都放行。
  • truststore：把驗證交給 Windows，兩條都擋，錯誤是「憑證已經撤銷」。

升 certifi 只處理用 certifi 的程式，標準函式庫 ssl 那條路不會跟著變。想讓 Python 跟著 Windows 擋，可以裝 truststore（Python 3.10 以後），在應用程式進入點儘早呼叫 truststore.inject_into_ssl()，放在匯入 requests 等網路套件之前：

這個組合我也測了：程式開頭先 inject，再用 requests，certifi 維持舊版，兩條都擋，錯誤一樣是「憑證已經撤銷」。inject 之後 requests 仍會載入 certifi 的清單，這次即使留著舊版 certifi，Windows 驗證還是把兩條都擋下了。

離線內網機：事件頁那支腳本要連網

做政府案的，很多機器在封閉網路裡，收不到 Windows 的自動更新。封鎖清單停在舊版，根憑證區裡又有 AAA Certificate Services（這台就有），走 Windows 驗證的程式也可能放行。這部分我沒有實測，手邊沒有離線機，這台的 Windows Sandbox 也沒開。

事件頁給 Windows 的解法是一支 Block-EmudhraCompromisedCA.ps1，說明寫它適用於離線或關掉自動更新的機器。我把它下載下來讀，第一件事就是用 Invoke-WebRequest 去事件頁下載憑證清單。真正離線的機器跑它，下載那步就會失敗，什麼都不會匯入。

我比較推薦用微軟自己的檔案。

單機：匯入微軟的封鎖清單

在連得上網的機器，用 certutil -syncWithWU 把 Windows Update 上的信任清單整包下載下來。目的資料夾要先建好，我試過指到不存在的資料夾，certutil 直接回 0x80070002 失敗：

匯入的是不信任憑證區，自動更新那份封鎖清單的 ThisUpdate 不會跟著變，匯入之後它沒變不代表失敗。它擋的是這 111 張已知的憑證，不像自動更新那份是按公鑰擋，以後同一把金鑰簽出新的中繼憑證，它擋不到。

有 AD：讓內網機自己跟上

微軟文件〈Configure trusted roots and disallowed certificates〉寫了正式做法。內部伺服器每天排程跑 certutil -f -syncWithWU \\server1\CTL，共用資料夾要先建好，排程帳號要能寫、內網機要能讀。內網機透過群組原則（文件教你先加一個自訂的 ADM 範本）把下載位置指到這個共用資料夾或內部網站，登錄檔對應的是 HKLM\SOFTWARE\Microsoft\SystemCertificates\AuthRoot\AutoUpdate 底下的 RootDirUrl，值可以是 file://\\server1\CTL 或 http://server1/CTL。

改的只是下載位置。如果原本有政策把封鎖清單的自動更新關掉（EnableDisallowedCertAutoUpdate 設成 0），要一起改回來。這套機制跟 WSUS 是分開的，WSUS 有在更新，不代表這份清單也有。

檢查腳本

不管用哪種方式補，都要驗。我把前面的驗證整理成一支腳本。它不下載任何東西，也關掉撤銷檢查，所以斷網的內網機也能跑。不過 Windows 建鏈時仍可能嘗試下載缺少的憑證：斷網執行時，結果反映本機可用的資料；連網執行時，也可能包含建鏈期間下載的資料。腳本做三件事：

  1. 讀本機封鎖清單的版本。ThisUpdate 早於 2026/10/19 的，一定沒有 eMudhra。
  2. 數 LocalMachine\Disallowed 裡名稱像 eMudhra 中繼憑證的筆數，只能粗估。
  3. 拿事件頁 chains.zip 裡的 12 條憑證鏈，實際建鏈，看這台怎麼判。

我這台跑出來：

12 條全部「已封鎖」，看不到其他結果，所以我另外拿 google.com 的憑證鏈、一張自簽憑證、一個壞掉的 PEM 檔試過，分別得到「建鏈通過」「沒建成（UntrustedRoot）」和「讀取或建鏈失敗」。

這支腳本只代表 Windows 那份清單。內網機上的 Java、Node、Python 要各自處理：Java 的 blocked.certs 是純文字檔，帶進去就能換；Node 要帶新版安裝檔；Python 在外面先 python -m pip download certifi -d .\wheels，帶進去之後在目標環境跑 python -m pip install --no-index --find-links .\wheels -U certifi。如果程式改用 truststore，套件也要一起帶，而且那台 Windows 的封鎖清單要先補好，不然 truststore 跟著的也是舊清單。

我這台還要修的

  • JDK 17.0.12、JRE 8u431：升級，或先換 blocked.certs／blacklisted.certs
  • PyCharm、Rider 內建的 JBR：跟著 IDE 更新，再確認實際版本
  • Node 22.22.0：升到 22.23.4
  • Python 3.13：certifi 從 2025.01.31 升上去；標準函式庫 ssl 那條要另外接 truststore。Python 3.12 的 certifi 是 2024.02.02，更舊

做政府案的話，修完要留的紀錄跟上次差不多：每個執行環境的路徑和版本、用了哪種修法、修完之後的探測輸出。連線失敗的截圖不夠，那可能只是網路不通。

這次最讓我意外的是 Windows-ROOT 和 --use-system-ca。看名字會以為「改用系統的」就等於跟著系統擋，實測兩個都沒有。下次再看到「Windows 已經更新封鎖清單」這種消息，我會先問一句：這台機器上，還有誰在自己驗憑證？
