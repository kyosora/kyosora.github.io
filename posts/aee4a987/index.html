Zeabur、Railway 環境變數外洩之後：先換哪把金鑰，換完怎麼確認舊的真的失效

發表於2026-10-22|資訊安全系統與維運
|總字數:10.3k|閱讀時間:39分鐘

Railway 在台灣時間 10 月 22 日清晨貼出資安公告。處置清單裡有一行我看了兩遍：存在服務 registry 設定裡的 GitHub token，Railway 已經「移除」。往下翻到給用戶的處置指南，才寫清楚是怎麼回事：

Those registry tokens still work on GitHub until you revoke them.

Railway 刪掉的是它自己存的那一份，token 在 GitHub 上照樣能用，要你自己去撤銷。

一週前（10-14～15）Zeabur 也被入侵，它 10-19 發布的十月事件報告寫的是 3,218,965 筆服務環境變數。兩起事件都涉及用戶填在環境變數欄位裡的東西：OpenAI key、資料庫密碼、AWS access key、GitHub token。

我自己沒有這兩家的帳號，部落格放在 GitHub Pages。會寫這篇，一是 Zeabur 有台北機房，十月報告的影響範圍就列了台北的區域；二是「平台上的環境變數整包外洩」這種事，換成 Vercel、Render、Fly.io 或公司自己的 CI，處理步驟幾乎一樣。

這篇談三件事：外洩之後哪些要換、先換哪個、換完怎麼確認舊的真的失效。第三件最容易被跳過，上面那個 GitHub token 就是例子。

兩家各發生了什麼

時間都是 UTC，台灣時間加 8 小時。只列跟「你要做什麼」有關的部分：

Zeabur Railway
時間 10-14～15（今年第二次，第一次在 8 月底） 10-21，狀態頁 21:59 貼出資安公告
外洩範圍 3,218,965 筆服務環境變數（名稱和值）、321,810 個帳號；101 台 GCP 專用伺服器被以 root 登入 第三方可能存取了加密過的環境變數，其中一部分拿到解密內容；只說可能限於部分用戶，沒公布數字
平台已經處理 撤銷所有 Zeabur Access Token 和 zSend 的 API 金鑰，輪替登入用的簽章金鑰 暫停部署、請上游 AI 供應商撤銷金鑰、重設 bucket 的 S3 金鑰，讓 Railway 持有的 GitHub token、OAuth session、Railway API token 失效
要你自己處理 環境變數裡所有憑證，八月換過的也要再換；資料庫要進去裡面改密碼；GCP 專用伺服器建議備份後重建 所有環境變數；資料庫用 Regenerate 換；GHCR 用的 GitHub PAT 自己去 GitHub 撤銷

Zeabur 這次的根因，報告寫的是自己的長期管理憑證以明文存在私有設定儲存庫、能從公網使用，而且八月那次輪換漏掉了；攻擊者怎麼拿到這些憑證，官方說還無法確認。10-17 Zeabur 宣布結束營運，時程放在後面 Zeabur 那一節。Railway 的入侵途徑還沒公布。

兩家的說法有一點相近：都認為攻擊者是衝著 AI 服務來的。Zeabur 報告寫攻擊者「主要在找可以直接使用的 API 金鑰，特別是 AI 服務的金鑰」，也註明這只是對意圖的觀察；報告還提到一把用戶的 OpenAI 金鑰在 10-16 01:50 到 02:56 之間被拿去發了約 1,107 次圖片生成請求，但把這筆列為推測，不排除是從別的管道外洩。Railway 則說，他們認為這是一連串鎖定平台公司、意在入侵 AI 推論供應商的攻擊之一。兩邊都沒提到對方，我也找不到證據說是同一批人。

另外有兩個常見的誤傳。Railway 沒說「加密金鑰被拿走」，原文是「may have accessed encrypted environment variables and, for some of them, obtained the decrypted contents」，平台的主金鑰有沒有外洩，官方沒講。Zeabur 寫的「明文保存」，指的是 Zeabur 自己的管理憑證，以及它代管的 GCP 專用伺服器初始化設定裡的 root 密碼；用戶的環境變數在資料庫裡有沒有加密，兩份報告都沒寫。這兩點不影響你該做的事：變數只要在受影響範圍內，就當作攻擊者已經看到明文。

先止血，不用等盤點

有兩種情況不必等任何清單，現在就處理：

  • 用量或帳單已經不對勁，或是收到供應商「key 外洩」的通知信：那把 key 立刻撤銷。
  • 主機被登入過（Zeabur 那 101 台 GCP 專用伺服器就是）：先隔離，新的憑證在乾淨的電腦上產生，部署到重建好的環境。把新 key 填回還被別人控制的主機，等於再送一次。

其餘的照這個順序走：匯出舊值 → 依權限排序 → 撤銷、換新 → 驗收新舊憑證 → 清掉殘留的連線、臨時憑證，和攻擊者自己建的帳號與金鑰。

盤點：哪些要換、先換哪把

先匯出一份舊值

盤點要有清單，等一下驗收也要用舊值。所以我會先把現在的環境變數匯出來，存在自己信任的電腦上：檔案權限設嚴，不要放進 OneDrive、Dropbox 這類同步資料夾，不要進 git，事情處理完就刪掉。匯出失敗、拿不到舊值的，不要因此延後撤銷。

排序的原則

腳本先依憑證類型排一個預設順序，原則是「這把 key 落在別人手上能做什麼」：

  1. 可能新增存取方式的先換：AWS access key、GCP service account、GitHub token、AI 平台的 Admin key。權限夠的話，攻擊者能自己再建新的 IAM user、新的 access key、新的 deploy key，等你換掉原本那把，對方可能已經建好別的進入方式。Zeabur 八月那次就是一把帶出下一把：先打下某位用戶部署的 NextChat，從內部網路的路由快取拿到管理員的 Legacy API Key，再讀到內部管理服務環境變數裡的 AWS 金鑰（其中一把是 root key），進東京共享叢集，最後讀到正式環境的資料庫。
  2. 能直接花錢或冒用身分的：一般的 AI API key、Stripe key，還有 JWT、session 這類簽章密鑰。簽章密鑰拿到就能偽造登入身分，包括管理員。
  3. 資料庫密碼、加密資料用的 key：換的時候要協調服務重新連線。
  4. 其他認不出用途的。

這是腳本依類型給的預設順序，它讀不到每把 key 實際的權限。能偽造管理員的簽章密鑰、帶管理權限的資料庫帳號，應該往前排；只有唯讀權限的雲端或 GitHub 憑證，可以依影響範圍往後調。實際操作時前兩級可以一起做，撤銷一把 AI key 也就半分鐘的事。

例行輪換和確定外洩，做法不一樣。AWS、Stripe、OpenAI 文件教的都是不停機的例行輪換：先建新 key，應用程式全部換好，確認新 key 正常、舊 key 沒人在用，再停用、刪除；Stripe 還讓新舊 key 並存最多 7 天。確定外洩的時候，這段寬限期就是留給攻擊者的時間。Zeabur 的建議是「先到服務供應商撤銷舊的，再建立新的並重新部署」，Railway 的 Stripe 指南也要你把舊 key 的到期時間設成 Now。

Railway 用戶這次多一層兩難：部署暫停的時候，撤銷舊 key，服務就會壞到能重新部署為止；不撤銷，攻擊者手上的 key 就繼續能用。截至台灣時間 10-22 15:11，狀態頁說 Pro 和 Enterprise 已經能 build，Hobby、Free、Trial 還在陸續開放。我的判斷是先撤銷。side project 停機幾小時的損失算得出來，key 被拿去刷的帳單算不出來。

換完，舊的真的失效了嗎

驗收要兩邊都看：舊值打不進去，新值打得進去。只看前者，可能是你打錯了端點；只看後者，舊的可能還活著。而且這只過了認證這一關，下面分四種「舊的還活著」的情況。

平台說移除了，GitHub 上還活著

回到開頭那個 GHCR token。Railway 對兩種 GitHub token 的處理不一樣：帳號連線用的 token 被作廢了，存成 registry 憑證的 PAT 只是從 Railway 移除，在 GitHub 上仍然有效。

這把 token 的權限可能比你以為的大。GitHub 文件寫明，GitHub Packages 只支援 classic PAT；在網頁上建 classic PAT 時，勾 write:packages 會預設把 repo 一起勾上。當初為了讓平台拉 image 建的 token，很可能帶著所有 repo 的讀寫權限。classic PAT 也不會出現在組織的 PAT 管理清單，組織 owner 從那裡看不到、也撤銷不了。

撤銷有兩條路：本人到 GitHub 的 Settings → Developer settings → Personal access tokens 刪除；或是用 GitHub 的憑證撤銷 API，手上有 token 值就能送出，不用登入（這支 API 只收未驗證的請求，每小時 60 次）。新的 token 只給 read:packages、設到期日，再填回每個從 ghcr.io 拉 image 的服務。

--probe 刻意寫得很保守：

  • 發行方只看前綴，不看變數名稱。OpenAI 相容服務的 key 不少也是 sk- 開頭，接 DeepSeek 這類服務時把 key 放在 OPENAI_API_KEY 也很常見，它們不會被送去 OpenAI。被送錯地方，key 等於多給了一家公司看，回來的 401 也毫無意義。所以 sk- 只測 sk-proj-、sk-svcacct- 這種 OpenAI 專屬前綴。
  • Admin key、GitHub App 的 installation token（ghs_）和 refresh token（ghr_），打這些端點本來就不會成功，失敗也證明不了什麼，一律不測。
  • 只有 401，或是回應裡明確說 key 無效，才算「認證被拒」。403、429、5xx、轉址一律標「判斷不了」，而且不跟著轉址，key 只會送到寫死的官方網址。

改了密碼，已經登入的連線還在

資料庫是另一種「換了但沒失效」。MySQL 文件寫得很直接：

Static global privileges and passwords are unaffected for a connected client. These changes take effect only in sessions for subsequent connections.

Redis 的 ACL 文件也說，把使用者設成 off 之後，已經通過驗證的連線「will continue to work as expected」。PostgreSQL 的文件沒有一句話明講，我就在開發機上用 PostgreSQL 18.6 的免安裝版測了一次：連線 A 用舊密碼登入，分三次查詢，中間各停 8 秒，趁空檔改密碼。輸出節錄如下：

踢別人的連線要有管理權限，用應用程式自己的帳號通常做不到。MongoDB 的文件沒寫改密碼對既有連線的影響，Railway 的 MongoDB 指南也只說，之後用舊密碼的「新連線」會失敗。這次我沒測 MongoDB，最保險的做法是改完密碼重啟資料庫；replica set 要每個接受連線的節點都重啟。

兩家平台在這件事上的指示剛好相反：

  • Railway 禁止你自己跑 ALTER USER、CONFIG SET requirepass、db.changeUserPassword()，只准用 Database → Config 的 Regenerate，不然變數和資料庫只有一邊改到。PostgreSQL 和 MySQL 的指南寫明，Regenerate 會重啟資料庫，舊連線全斷；Redis 的指南說用舊密碼認證過的 client 下一個指令就會失敗；MongoDB 的指南只說用舊密碼的新連線會失敗。Redis 和 MongoDB 這兩份都要你自己列出連線（CLIENT LIST、$listSessions），踢掉不認得的。
  • Zeabur 共享叢集反過來，要你進資料庫裡面改密碼，因為只改 Zeabur 上的環境變數，不會動到資料庫內的密碼。報告沒提到要踢掉既有連線，上面那幾行要自己補。

做實驗時順手驗了另一個坑：拿「改密碼之前」的 pg_dumpall 還原。

psql 預設遇到錯誤會繼續往下跑。CREATE ROLE 報錯，但 dump 裡緊接著的 ALTER ROLE app WITH ... PASSWORD 'SCRAM-SHA-256$...' 照樣執行，舊密碼的雜湊就蓋回去了。Zeabur 的遷移指南有提醒這件事，而它 Dashboard 的線上備份，產生的正好是 pg_dumpall 格式。換完密碼再拿舊備份還原，等於把外洩的密碼裝回去。需要保留角色，可以用 pg_dumpall --no-role-passwords；只要資料，就用 pg_dump 一個資料庫一個資料庫匯出。

不過這只解決密碼。攻擊者在資料庫裡留下的函式、觸發器，照樣會跟著 dump 搬到新環境，PostgreSQL 的 pg_dump 文件也提醒，還原 dump 可能執行來源資料庫的超級使用者放進去的任意程式碼。從被入侵的資料庫匯出的東西，先在隔離的環境還原，看過裡面的物件再上線。

停用了金鑰，換出去的臨時憑證還在

雲端的長期金鑰可以拿去換短期憑證。AWS 的 IAM user access key 呼叫 GetSessionToken，就能換到一組 ASIA 開頭的臨時憑證，效期 15 分鐘到 36 小時，預設 12 小時。AWS Security Blog 寫得很清楚：

Rotating the credentials for the IAM user whose credentials were exposed will not invalidate any temporary credentials that were obtained using the user’s credentials.

那篇是 2014 年的舊文。現行的 IAM 文件依情況分開處理：IAM user 用 GetSessionToken 換出去的，加一條 deny policy，用 aws:userid 指定那個 IAM user；如果攻擊者已經 AssumeRole 進了某個 role，要到那個 role 撤銷有效的 session；root 的 access key 直接刪掉，但 root 換出去的短期憑證，權限沒辦法用 policy 改，只能等它過期（root 換的最長 1 小時）。GCP 也一樣，文件明寫停用 service account key 不會撤銷用它簽發的短期憑證，要立刻切斷，就得停用整個 service account。

這也影響查紀錄。攻擊者如果先換了臨時憑證，之後的動作在 CloudTrail 裡記的是 ASIA 開頭的 key ID；用外洩的 AKIA 去查，只會看到換憑證那一筆，要再拿那個 ASIA 查一次。CloudTrail 的 Event history 只保留 90 天、一次查一個區域，而且不含 S3 物件讀寫這類 data events。bucket 裡的東西有沒有被讀，沒事先開 data events 就沒辦法從 CloudTrail 回溯，有開 S3 server access logs 的話還可以從那裡查。

攻擊者自己建的東西

前三種是你的舊鑰匙還能用。最後一種是攻擊者自己打的新鑰匙，換多少把舊的都清不掉：

  • AWS：CloudTrail 找 CreateUser、CreateAccessKey、CreateLoginProfile、RunInstances
  • GitHub：repo 的 Deploy keys、Webhooks、Collaborators，帳號的 SSH key 和授權過的 OAuth App
  • 資料庫：陌生的角色、函式、觸發器、擴充套件。Zeabur 報告記錄東京 hnd1 至少有 2 個 PostgreSQL，從 10-14 起被植入會往外回連的程式
  • 主機：authorized_keys。被登入的 101 台 GCP 專用伺服器裡，有 50 台被加了攻擊者的 SSH 公鑰。Zeabur 建議這批主機備份後重建，說這是移除後門最可靠的方法；暫時不能重建的，至少清掉不認得的 SSH 公鑰、檢查系統帳號和排程、換 root 密碼並關掉 SSH 密碼登入。光改密碼不夠

兩家各自還要多做的事

Railway

  • CLI 和 CI：OAuth session 被作廢過，CLI 用 railway login 重新登入就好；Railway API token 則是全部失效，CI 要到 Railway 建新的 token 換上，railway login 救不了。狀態頁只說「all Railway API tokens」，沒明講包不包含 CI 常用的 project token（RAILWAY_TOKEN），直接換一把新的最保險。
  • bucket 的 S3 金鑰 Railway 已經換了，但容器只在啟動時讀變數，服務要重新部署才會拿到新的。
  • 直接貼死連線字串的服務，資料庫換密碼後不會跟著更新，改成 `${{ Postgres.DATABASE_URL }}` 這種 reference variable。
  • 沒收到通知信不代表沒事。Railway 只寄給「已確認受影響」的帳號，但要求所有人都輪換。

Zeabur

  • 期限：共享叢集 12-01 起暫停所有運行中的服務，之後只能手動恢復來備份，所以服務不想中斷，實際期限是 11-30；專用伺服器依各自的到期日，在 12-01 到 12-31 之間關閉。12-31 是平台全部停止的日子，你的期限比它早。
  • 搬家順便換。不要把舊值原封不動貼到新平台，打算之後再換，搬過去的那一刻就用新的。
  • 備份：Zeabur 的自動備份放在它自己的物件儲存，停業後會跟著消失，現在就自己匯出，並照上一節的方式檢查過再用。
  • n8n：檢查的 607 個用 PostgreSQL 的 n8n 裡，有 602 個把加密金鑰寫在環境變數，n8n 裡存的第三方憑證等於明文外洩。順序很重要：先在 n8n 裡列出存了哪些服務的憑證，到各個來源撤銷、建新的，再換 N8N_ENCRYPTION_KEY、把新憑證建回去，最後檢查每個 workflow 綁的是新憑證，實際跑一次。先換 key，舊憑證就解不開了，你連裡面原本存了哪些服務都看不到。
  • *.zeabur.app 網域在 Zeabur 結束後就會失效，寫死在 OAuth callback、webhook、金流設定裡的網址都要改。
  • 退款和資安賠償是兩種申請，都走 Support。開工單前先撤銷相關憑證，工單裡不要貼還有效的金鑰。
  • 資料庫裡如果有你自己使用者的個資，還有通知當事人的問題。個資法現行第 12 條是「違反本法規定，致個人資料被竊取、洩漏……」才要通知；修正後的條文改成知悉就要通知，符合一定通報範圍的事故還要通報主管機關，但施行日期由行政院另定，到今天還沒生效。這部分請找法務確認。

Zeabur 10-20 發的遷移指南，把 Railway 列為託管平台的第一個例子，隔天 Railway 就出事了。我沒有要說哪一家比較不安全。換到哪個平台，環境變數都放在別人的資料庫裡，能做的是讓它下次外洩時，要換的少一點。

下次少換幾把

  • 同一把 key 被好幾個服務共用，撤銷時就得一起更新，漏一個就是半夜被叫起來。能拆就拆，一個服務一把。
  • AI key 依平台能力設上限和到期日。有些上限會直接擋請求，有些只會寄通知，設之前看清楚是哪一種。Anthropic 的 key 建立時可以設到期時間。
  • 資料庫不要開公網。Railway 的指南提醒，開了 Public Access 的資料庫，在輪換之前，舊密碼可以從整個網際網路透過 TCP proxy 使用。

最費工的是找齊

Zeabur 十月報告裡，我覺得最該記住的是它更正自己八月說法的那一段。八月報告說內部管理金鑰都已經停用或輪替，其實設定儲存庫裡的明文叢集管理權杖和 AWS 金鑰沒換到。平台自己做輪換都會漏，第二次就是從漏掉的那幾把進來的。

按下撤銷很快，費工的是找齊相依的服務、處理換出去的臨時憑證和連線，再回頭確認新舊兩邊。這支腳本幫我整理候選清單、測得了的那幾家 key；解析不了的格式、認不出發行方的 key、資料庫和 session，還是要自己一個一個看。

附錄：secret_inventory.py

只用 Python 標準函式庫，我在 3.12 和 3.13 跑過。--probe 會把值送到各家發 key 的官方 API，不加這個參數就完全不連網。

設計上的幾個取捨，都是測出問題之後改的：

  • 不印任何值，重複的偵測靠指紋。第一版直接用值的 SHA-256 前 8 碼，後來想到 Sup3rS3cret 這種資料庫密碼，拿字典跑一輪就能從 8 碼反查，輸出要是被貼進 issue 就麻煩了。現在每次執行隨機產生 salt，內部用完整的雜湊比對，畫面只顯示 8 碼。
  • 資料庫只拿密碼比對。假資料裡同一個密碼寫在 PostgreSQL 的 URL、SQL Server 的 Password=...; 和單獨的 POSTGRES_PASSWORD 裡，整串比對抓不到，拆出密碼才對得上。
  • .env 解析不了就整行放棄，只回報行號。多行 PEM 私鑰裡 QUJDREU= 這種 base64 行，語法上剛好長得像 名稱=值，早期版本會把它當變數名稱印出來；引號解析錯了也不能猜，送去驗證的值跟原本的不一樣，結果就沒有意義。
  • Zeabur 的 ${PASSWORD} 引用另外列一區，不然所有引用同一個變數的連線字串，會被誤判成共用同一個密碼。Zeabur 的 JSON 格式是照 zeabur/cli 原始碼寫的，我沒有帳號可以實際跑過。

這些洞有一半是 Codex 審稿抓到的，三輪都給了最小反例：值裡混進換行時，urllib 的例外訊息會把整個 header 連 token 印出來；行尾註解會跟著 token 一起送出，被拒的其實是一串錯的字；跟著轉址會把 Authorization header 帶到新網址；"ab\"cd" 這種跳脫過的引號會被截斷；只帶一個 = 的 PEM 行，還是會被當成名稱；ADO.NET 的 Password="ab""cd" 被截成 ab，跟另一個不同的密碼誤判成共用。上述反例修正後，Claude Code 把它們寫成 17 個測試：用本機假伺服器回 200、401、403、429、500、302 和 Google 的兩種 400，確認轉址的目標沒有被請求、帶換行的值沒有被送出、壞掉的 JSON 不會讓整支程式停掉，輸出裡也找不到任何一個測試值或 PEM 的片段。測試過了，只代表這些反例不會再發生，.env 和連線字串的寫法太多，解析不了的它會跳過並告訴你，不會替你猜。
