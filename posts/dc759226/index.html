Anthropic 用 Scion 換掉 Git：版本控制繞回中央式，但回不去 SVN

發表於2026-10-15|AI產業觀察工具與生產力
|總字數:3.9k|閱讀時間:13分鐘

Anthropic 在 10/13 發了一篇工程文章〈Redesigning source control at Anthropic〉，說公司內部的 monorepo 已經不用 Git，換成自己寫的 Scion。理由很直接：每天合併進 monorepo 的變更，從今年 5 月的平均 2,500 次左右，漲到 9 月的 30,000 次以上。大部分程式碼是 Claude 寫的。

五月我寫 Cursor 雲端 Agent 那篇 時，Cursor 說內部 monorepo 有 40% 的 PR 由 agent 寫。五個月後，Anthropic 給了下一站：agent 寫得夠多，先被擠爆的是版本控制。

讀到一半我開始覺得眼熟。server 是唯一權威、client 隨時連線、commit 和 merge 在 server 上做，這套我到現在還在用，叫 TFS。

先講清楚，Scion 沒有對外提供。原文說它完全不適合拿來當一般用途的 Git 替代品，也很難包成對其他組織有用的形式，所以只分享設計思路（有幾篇二手報導寫成「明確表示不會開源」，比原文說得更死）。但它拆出來的問題跟我們有關。看完之後，我請 Claude Code 把我自己兩套版本控制的紀錄都撈出來，數字放在後半段。

Git 卡在 agent 一天幾千萬次的 checkout

原文的數字：

  • main 的歷史將近 100 GB，壓縮後的 working copy 超過 25 GB
  • 光 CI 每天就要 checkout 大約 2,500 萬次，還沒算開發環境、agent sandbox 和研究用的 job
  • 每次都完整抓的話，一天會有超過 600 PB 的 Git 流量
  • 高峰期他們跑了幾百台內部 git mirror 硬撐，merge 越快，mirror 離 main 越遠

Anthropic 自己的診斷很準：他們把 Git 當成中央系統在用，只有一份權威副本，連上來的幾乎都是永遠在線的 agent 和 job。Git 的設計前提是每個 client 都有完整歷史、能離線工作、在本地自己算 diff 和 blame。這些前提對人很友善。對每天幾千萬次、用完就丟的 checkout，大多是負擔。

repo 大小本身 Git 撐得住。Microsoft 當年為了把 Windows 的程式碼搬上 Git 做了 VFS for Git，後來從那套程式碼衍生出 Scalar，大型 repo 需要的功能也陸續進了 Git 本體。Anthropic 撞上的是兩件事：checkout 的扇出量，還有 merge 必須排隊。後面那件我覺得更有意思，留到談合併的那節。

Scion 把 Git 的資料結構倒過來

我挑四個設計重點：

  1. commit、merge、rebase、blame 全部在 server 上做。 client 只負責一塊有上限的本地快取、把檔案鋪到磁碟上、監控檔案系統的變動，再提供操作介面。沒有 push 這個動作，因為 commit 本來就發生在 server 上。checkout 可以只鋪你要的目錄，也可以虛擬化，檔案用到才實體化。
  2. 版本的單位叫 changeset，記的是相對第一個 parent 有哪些檔案變了，每個檔案指向一份壓縮過、用內容 hash 定址的 blob。Git 的每個 commit 指向一棵完整的樹，兩版差在哪，是比對兩棵樹算出來的。Scion 反過來，只記「這一版動了哪些檔」，整棵樹要用時才組。歷史和 blame 都為 trunk-based 的主線最佳化，除了 main 和 release，branch 一律不鼓勵。
  3. 沒有任何一個地方把整份 repo 實體化，連 server 也沒有。資料放在 Spanner 和 cloud storage，沒有 packfile，所以也不用 gc、repack。
  4. 三層快取：每台機器一層、每個區域一層，最後才是權威 server。client 要的都是不可變物件，哪一層都能回答，原文說每層命中率都超過 99%。

成果是整套基礎設施的用量變成舊 git mirror 的 1/200，CI 和研究用的 checkout 從幾分鐘變成幾秒，光 CI 就省下 25% 的 CPU。

有兩件事要打折看。1/200 的比較對象是他們自己那套 git mirror，不能直接套到一般的 Git 部署，原文也沒給資源明細。第二件是人力：原文說 7 個人花 5 個月就做完 Scion、code review 工具 Antique 和大約六個周邊系統，並完成遷移，大部分程式碼由 Claude 寫，早期內部版的 Claude Mythos Preview 還把他們手寫的 Git 匯入 pipeline 重寫成記憶體少 20 倍、快 4 倍。這些都是 Anthropic 自報，外人驗證不了，而且這篇文章同時也在展示 Claude 的能力。

讀到一半，我以為在看 TFS

我手上這個政府案，舊系統到現在還放在 TFVC（TFS 的版本控制），去年 12 月開始寫的新版改用 Git。TFVC 讓我吃虧的有三件事：

  • 設定繁瑣，新人換電腦、換路徑就容易出包
  • 有人 exclusive lock 了檔案就去休假，其他人只能乾等
  • 我們用的是 Server Workspace 模式，檔案是唯讀的，要先 check out 才能改。用 VS 以外的工具改了檔，pending changes 偵測不到，常常變成本機跟 server 以為的狀態不一致，最後只能 tf get /force 整包重抓

寫這篇時又中一次：Claude Code 撈 TFVC 紀錄碰到 TF30063，沒先翻以前的排錯筆記就叫我自己去登入，我提醒之後它才改用 /login 跑通。

把四套擺在一起看，Scion 的架構跟 SVN、TFVC 同一族；歷史是 DAG 這點像 Git，但它記版本的方式跟 Git 也不一樣：

我在 TFVC 吃的「本機跟 server 狀態不一致」，其實是 Server Workspace 這個模式的問題。TFVC 從 TFS 2012 起就有 Local Workspace，會自己掃描比對，VS 以外改的檔也抓得到。Scion 走的是另一條路：同樣以 server 為準，但讓 client 一直監控檔案系統。中央式不必要求人先舉手說「我要改這個檔」。至於有人鎖檔去休假那種事，原文沒提 Scion 有沒有檔案鎖，它強調的是 commit 本身不需要鎖。

但也回不去 SVN。SVN 的寫入集中在一台主 server，svnsync 鏡像和 write-through proxy 能分攤讀取，寫入還是要回主站，架構上跟 Anthropic 原本那幾百台 mirror 有點像。merge 也在 client 的 working copy 裡做，得先 checkout 才能 merge，這正是 Scion 想讓 agent 省掉的那一步。

合併前要先對齊多少，SVN 反而比 Git 像 Scion

這是我比完最意外的地方。比的是一件事：一個變更要進主線之前，得先跟多少「別人的最新狀態」對齊。

Git 對一般 branch 的 push 要求 fast-forward。你要直接推送更新遠端的 main，而遠端 main 多了你手上沒有的 commit，push 就會被拒，跟你們改的是不是同一個檔無關。你得先把遠端的新歷史 merge 或 rebase 進來，再推一次。走 PR 的團隊常常再加一條分支保護：「合併前必須跟 main 同步」，配上 CI，每個變更都要對著最新的 main 驗過一輪。merge queue 可以批次、可以平行測，但改 main 這個動作終究得一個一個來。每 3 秒一個 merge，這裡很容易塞車。

SVN 的 commit 只檢查你這次動到的檔案和目錄是不是最新版。別人改了別的檔，不會擋你，你也不用先把整個 working copy 更新到最新的 revision，混著不同 revision 的 working copy 是正式支援的用法。commit 本身還是原子的，進去之後就是 repository 的一個新 revision。TFVC 的 checkin 也是看這次受影響的項目有沒有衝突。

Scion 這邊，原文寫得很清楚：他們沒辦法在 merge queue 上複製全域的 repository lock，所以改把力氣放在 merge 之後、部署之前的自動測試，衝突交給 Claude 修。原文的說法是，Claude 修這些衝突，通常比人類發現衝突還快。移動 main 這個 ref，則是 Spanner 單一 row 上的 compare-and-swap，跟建立 changeset 分開。

原文沒寫 Scion 怎麼判定兩個變更衝突，這部分我不猜。能比的是減少等待的方式：SVN 不要求整份 working copy 先更新到最新；Anthropic 則降低了對合併前全域驗證的依賴，把重心移到合併後。省掉等待的位置不同，方向一樣。

這也不是換掉 Git 才做得到。Git 平台一樣可以在 server 端整合變更、改走 merge 後驗證；Scion 的價值還在於它為這種工作負載重做了資料存取和服務架構。

代價也很清楚。驗證從 merge 之前挪到 merge 之後，風險就落在 merge 後的測試、部署閘門、監控和回滾能力上。測試抓得到的衝突，Claude 修得快；抓不到的，會先進 main。原文沒給 merge 之後的回滾率或事故數字，這是我最想看、但沒看到的一塊。

Scion 的思路，Git 裡有現成的

Scion 的幾個想法，Git 已經有對應的功能。要不要用，看的是檔案數、checkout 頻率、CI 一次開多少 job、能忍多少延遲，repo 容量只是其中一項。

CI 那種只要 build、不需要歷史的 job，git clone --depth=1 抓最新一版就夠。懶得一個一個設的話，Git 2.38 起內建的 scalar clone 預設會開好 partial clone（要遠端支援）、sparse-checkout 和背景維護，平台支援的話也會開 fsmonitor。

fsmonitor 這行要講清楚。Git 不開它也偵測得到 VS 以外的改動，fsmonitor 只是讓它少做一些掃描。我在 TFVC Server Workspace 吃的那種虧，Git 本來就沒有。Scion 則把監控直接做成 client 的基本功能。

老實講，我那個 72 MiB 的 repo，上面這些一個都用不上。我卡的地方在別處，回頭翻紀錄才看清楚。

「帶 Claude 署名」是看 commit 訊息有沒有 Co-Authored-By: Claude 這行，我用的 Claude Code 設定會自動加。署名可以關、也可以手打，所以它只是粗略指標，說明不了 AI 參與了多少。4、5 月掉到個位數，是因為那兩個月的 commit 標題常常掛著 (codex-delegate)，大量寫碼交給了 Codex CLI，用 AI 的比例其實沒降。

我自己看出三件事。

第一，所有整合都在公司自架的 Azure DevOps 上完成，它就是唯一權威。10 個月只有 7 個 merge commit，歷史幾乎是一直線。Anthropic 那句「把 Git 當中央系統用」，在我這裡也成立，只是規模小了幾個數量級。

第二，這組數字當不了乾淨的前後對比。三個變數同時在變：工作從維護舊版變成重寫新版、版本控制從 TFVC 換成 Git、AI 的用量也一直在漲。我用的 TFVC Server Workspace，checkin 前要先 check out、處理 pending changes，成本高；Git 的 commit 輕到 Claude Code 每做完一件事就能 commit 一次。光是 commit 變便宜，數字就會往上跳。Scion 把這件事再往前推一步：連 push 都沒有了。

第三是量級。8 月最忙，287 個 commit，平均每天 9 個，最多的一天 35 個。拿 Anthropic 的每天 30,000 次攤平，大約每分鐘 21 次，我最忙的一整個月，他們 14 分鐘就合併完了。 我整個 repo 的 pack 檔是 72 MiB，他們 main 的歷史將近 100 GB。（嚴格說，他們算的是合併進 monorepo 的變更，我算的是 --all 底下所有分支的 commit，量級比較成立，單位不一樣。）

撈數字用的指令（Git 與 TFVC）

Git 這段是 Claude Code 當場寫的，我只補了註解：

分月有兩種口徑。--since、--until 看的是 committer date，表格用的是 author date；rebase 或 amend 過的 commit，committer date 通常會比 author date 晚。我第一版用 --since、--until 逐月切，4、5 月算出 189 和 93，換成 author date 是 175 和 107。

TFVC 用 tf history 匯出再分組。不加 /noprompt 的話，認證失敗會跳出登入視窗：

/format:brief 的日期格式跟著系統的地區設定，我這台是 2026/10/8，英文系統要改 regex。我們這台 TFS 得加 /login:網域\帳號,密碼 才過得了認證，但直接在互動式命令列輸入時，密碼可能留在 PowerShell 的 PSReadLine 歷史檔裡，Clear-History 清不掉那一份，能不用就不用。

Git 撐得住我，review 不一定

今年 4 月底之後，這個 repo 只剩我一個人在 commit。同事都離職了，現在是一個人加 AI 在維護和開發。照這條曲線，先撐不住的會是 review。

Anthropic 的答案是 Antique。它能設定語意化的核准條件，分得出「只改註解」和「動到敏感邏輯」，讓人把力氣放在有後果的變更上，審的是意圖，逐行看的負擔就少了。原文還有一段很老實：agent 有時會違反系統約束；讓 AI 互相挑錯的 adversarial review 有時太短視，需要有經驗的工程師把 Claude 從過度設計裡拉回來。他們寫，工程師的角色很多時候是對 Claude 說「不」。

在一人團隊裡，說「不」的只有我。

Git 還能撐我很久。該升級的是我讀 diff 的方式。
