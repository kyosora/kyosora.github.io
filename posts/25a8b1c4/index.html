修好上線了，使用者還在跑舊版？IIS 沒送 Cache-Control，瀏覽器自己決定快取多久

發布於 2026-11-26 約 10 分鐘讀完

上週修了一個巡查表單的 bug，修正上了正式機。我比過伺服器上的檔案 MD5，再用沒有快取的乾淨瀏覽器打開，看到的也是新版。

接著 PM 傳來一張 App 截圖，列表還在顯示時分秒。新版的列表只顯示日期。

更糟的在 log 裡。這次修正的另一半是存檔：新版網頁會把完整時間送給 API，舊版只送日期。有人從網頁存檔，送出的卻是只有日期的舊格式，又把 9 筆巡查時間存成 00:00:00。修正明明上去了，使用者手上跑的還是舊程式。

這是一套 Vue 2 的舊系統，沒有打包流程，頁面用 httpVueLoader 在執行期發 XHR 去抓 .vue 原始檔。檔名沒有 hash，載入時也不帶版本號。IIS 回 .vue 只附 Last-Modified 和 ETag，沒有 Cache-Control。

我很快就猜到是快取。要證明、要修，中間還有一個補完設定才會碰到的坑：只補 header，已經快取舊檔的人仍可能一路用到新鮮期結束。

伺服器是對的，這件事證明不了什麼

MD5 對、乾淨瀏覽器正常，證明的都是伺服器上的檔案。使用者的瀏覽器跑哪一版，要看使用者送上來的東西。

這個系統的寫入 API 每次都把整筆 JSON 記進當天的 log。網頁送的 payload 裡夾著一段只有網頁版才有的 Action 按鈕 HTML，App 送的沒有；舊版的巡查時間只有日期（像 "2026-11-18"），新版會帶上時間。

那 9 筆全都帶著 Action，巡查時間也只有日期。從 log 可以確定，送出它們的是舊版網頁。

舊版網頁怎麼還在？log 回答不了。一個部署前就開著、一直沒關的分頁，也送得出這種資料。讓我先往快取查的，是 .vue 的回應裡少了 Cache-Control。

沒有 Cache-Control，瀏覽器自己估能用多久

IIS 的 <clientCache> 預設值是 NoControl，靜態檔不加 Cache-Control，也不加 Expires。我在本機用 IIS Express 開了一個最小站台，.vue 的回應長這樣：

伺服器沒說這份檔案能用多久，HTTP 規範就讓瀏覽器自己估。RFC 9111 第 4.2.2 節允許快取在沒有明確期限時，自行指定一個「啟發式新鮮期」。回應帶 Last-Modified 的話，建議新鮮期不要超過「距上次修改」這段時間的某個比例，文中舉的典型值是 10%。

我翻了三個引擎目前的原始碼：

以這種帶 Last-Modified、沒有明確期限的 200 靜態回應來說，三個引擎都取 10%。Chromium 和 WebKit 在這段計算沒有設天數上限，Firefox 最多 7 天。前兩個涵蓋了 Chrome、Edge、Safari，還有 Android 和 iOS 的 WebView。新鮮期內，瀏覽器直接用快取，不會回伺服器確認。

算的是瀏覽器收到那份回應的當下：用回應裡的 Date 減 Last-Modified，再取 10%。

1 年 約 36 天 7 天

這是從收到回應那一刻起算的總長度，使用者還要卡多久，得再扣掉已經過去的時間。

舊系統最容易在這裡中招。那些 .vue 好幾個月沒人動過，等於讓瀏覽器自己決定可以好幾週不回來問。而你要修 bug，改的偏偏就是這種放了很久的檔案。

按了 F5，為什麼 list.vue 還是舊的

Chrome 團隊 2017 年在官方部落格說明過重新整理的行為：一般重新整理只重新確認主文件，其餘資源照一般載入的規則走快取。httpVueLoader 抓的 .vue 不是主文件，還在新鮮期內，就直接從磁碟快取拿。

寫這篇時，我請 Claude Code 用 IIS Express 加 Playwright 重現了一次。先放 v1、把修改時間設成 180 天前，開頁；再換成 v2（修改時間是現在），按 F5，再重新開一次頁面：

Chrome DevTools Protocol 回報後兩次的 .vue 都是 fromDiskCache: true。IIS Express 的 log 裡，list.vue 從頭到尾只收到第一次那個 GET。v2 已經在伺服器上，瀏覽器沒有來拿。

（IIS 預設不認得 .vue 副檔名，會回 404.3。重現時要先在 web.config 補一行 <mimeMap fileExtension=".vue" mimeType="text/plain" />。）

修法：只對放 .vue 的資料夾關掉

我不想動整個站台的快取行為，圖片和第三方套件沒必要每次都回來問。web.config 用 <location> 只罩住放 .vue 的資料夾：

DisableCache 送出的是 Cache-Control: no-cache。這個名字很容易誤會：no-cache 允許瀏覽器存，只是每次用之前都要先回伺服器確認。檔案沒變，IIS 回 304，只傳 header。真的不准存的是 no-store，那樣每次都要整份重新下載，這裡用不到。

補上之後跑同一支重現腳本：

IIS Express 的 log 依序是 200、200、304。最後一次 IIS 回 304，沒有重傳內容；瀏覽器確認快取還能用，沿用本機那份 v2，所以腳本看到的是 200 v2。站台根目錄的 index.html 還是沒有 Cache-Control，<location> 只管它包住的路徑。

補了 header，已經中招的人還是舊的

header 補上去，只解決了一半。

no-cache 是跟著新的回應送出去的。已經把舊檔存起來的瀏覽器，在啟發式新鮮期內根本不發請求，也就收不到這個 header。把重現的順序換一下：先讓瀏覽器在沒有 header 的狀態下快取 v1，再補上 DisableCache、部署 v2：

第 2、3 步，IIS Express 都沒收到 list.vue 的請求。到第 4 步按 Ctrl+Shift+R（不讀快取的強制重新整理），IIS Express 才收到新的 list.vue 請求，回傳帶 no-cache 的 v2。第 5 步按一般 F5，IIS 回 304。

所以當時兩件事一起做：

  1. 換掉 .vue 的網址（加版本號）。舊快取對不上新網址，等於作廢。
  2. 請使用者清快取或強制重新整理。桌面瀏覽器可以按 Ctrl+Shift+R；App 沒有這個按鍵，就請巡查員清快取。

版本號也有它的前提。寫這篇時又在本機驗了一次：入口 HTML 本身也沒有 Cache-Control，一樣會被啟發式快取。把 HTML 改成引用 list.vue?v=2 之後：

開新分頁（就像隔天從書籤點進來），瀏覽器連 HTML 都拿快取，裡面還是舊的引用。按 F5 會重新確認主文件，讀到新的引用，才換成 v2。瀏覽器要先讀到新版 HTML，才會去抓 list.vue?v=2。 這種網址固定的入口頁，我會設 no-cache，讓使用者從書籤進來時也會先確認一次。

被舊程式寫壞的 9 筆

資料用 log 還原。log 留著每筆建立當下的原始值，照著寫回去，守三條規矩：

  • 只送 {id, 欄位}，不送整筆，避免蓋掉其他欄位後來的修改
  • 寫之前先讀現值，確認還是被寫壞的那個值
  • 寫完讀回整列比對

靜態檔的 Cache-Control 怎麼選

什麼都不設，就是把決定權交給瀏覽器。我現在的建議是分三種：

檔案 策略 IIS 設定
入口 HTML 每次確認 DisableCache
網址固定、執行期才載入（httpVueLoader 的 .vue、舊系統的 .js） 每次確認 DisableCache
內容一改網址就換（檔名帶 hash，或每次改版都換版本號） 長期快取 UseMaxAge 加大 cacheControlMaxAge

內容會改、網址卻不會跟著換的檔案，別給長 max-age。 那等於把啟發式快取的問題自己寫死，期限還由你指定，連 Firefox 的一週上限都沒了。

這次記住的事

「改版沒生效」先看回應 header 有沒有 Cache-Control。沒有的話，先假設使用者在跑舊檔，別急著懷疑程式。

下次接手這種沒有打包流程的舊站，我會在第一次部署前，同時查入口 HTML 和一支實際載入的 .vue。這次新版已經上線，舊版網頁還是把 9 筆巡查時間寫成了午夜，最後得靠 log 還原。
