前言

大型 SQL Server 環境裡，資料匯入匯出緩慢、維護作業得人工拖到半夜、備份還原偶爾出包、跨伺服器操作一多就容易漏步驟，這些幾乎是每個 DBA 遲早會遇到的問題。

sqlcmd 是 SQL Server 內建的命令列工具，把這些操作腳本化、掛上排程，能省下大量重複的手動工作。這篇整理我實際用過的幾種場景，並且特別把網路教學裡常見的幾個錯誤參數說明糾正過來——尤其是 -m 和 -k，被講錯的機率高得驚人。

先搞清楚：命令列參數 vs T-SQL 腳本

很多人把 sqlcmd 學壞，是因為一開始就把兩件事混在一起。sqlcmd 後面接的東西分兩層：

  • 命令列參數（-S、-U、-i 這些）：寫在 shell（cmd / PowerShell / bash）裡，控制 sqlcmd 怎麼連線、怎麼跑。
  • T-SQL 與 sqlcmd 指令（:setvar、:r、BACKUP DATABASE）：寫在 .sql 腳本檔裡，由 sqlcmd 讀進去送給資料庫引擎執行。

這兩層用的註解語法不一樣：shell 裡 -- 不是註解（cmd 會把它當參數），T-SQL 裡 -- 才是。所以下面命令列我用 cmd 的 :: 註解，腳本內容才用 --。混在同一行貼上去，多半跑不動。:: 只在 cmd 批次檔裡算註解，PowerShell 要用 #；在 PowerShell 裡複製時只取指令那一行。

大型資料庫匯入

匯入大量資料時，逐筆 INSERT 是最慢的選擇，每一筆都要寫完整交易記錄。真正能把時間從「數天」壓到「數小時」的關鍵，是用 BULK INSERT（或 bcp）搭配最小記錄載入。

先把匯入邏輯寫進腳本檔：

CHECK_CONSTRAINTS 是不帶值的開關，寫了才檢查，沒寫就不檢查。CHECK_CONSTRAINTS = OFF 這種寫法是語法錯誤，本文舊版也寫錯過。不檢查的代價是：載入後這些約束會被標成 not trusted，查詢最佳化工具不再拿它們當依據（UNIQUE 和 PRIMARY KEY 則永遠會檢查）。資料驗完後跑一次 ALTER TABLE dbo.BigTable WITH CHECK CHECK CONSTRAINT ALL;，約束才會重新變回 trusted。

最小記錄載入（minimally logged import）有三個前提：①資料庫復原模式為 SIMPLE 或 BULK_LOGGED（FULL 底下一律完整記錄）；②BULK INSERT 加上 TABLOCK（表級鎖）；③目標表沒有啟用異動複寫（replication 啟用時無論復原模式都完整記錄）。前提都過了，哪些頁能最小記錄，還要看目標表的索引（以下是一般 rowstore 表，clustered columnstore 另有規則）：

目標表 資料頁 索引頁
沒有索引的 heap 最小記錄 沒有索引頁
heap + 非叢集索引，空表 最小記錄 最小記錄；用 BATCHSIZE 分批時只有第一批是，第二批起完整記錄
heap + 非叢集索引，非空 最小記錄 完整記錄
clustered index（B-tree），空表 最小記錄 最小記錄；分批時第二批起只剩資料頁最小記錄
clustered index（B-tree），非空 完整記錄 完整記錄

另外，任何一個索引設了 IGNORE_DUP_KEY = ON，資料頁和索引頁都會完整記錄。完整記錄的頁越多，磁碟 I/O 和記錄檔成長就放大越多。

再用命令列把這支腳本跑起來：

命令列參數說明：

  • -b：遇到嚴重性大於 10 的錯誤時，sqlcmd 結束並回傳非 0 的 ERRORLEVEL，方便排程判斷成敗。
  • -t 600：查詢逾時 600 秒（不是登入逾時，登入逾時是 -l）。
  • -i：指定要執行的腳本檔。

能把 10TB 級資料壓進可接受的時間窗，靠的是這幾件事一起做：

  1. 載入前把復原模式切到 BULK_LOGGED，搭配 TABLOCK；目標表的索引狀況對照上表，最省記錄的是沒有索引的 heap。正式機別切 SIMPLE：從 FULL 切到 SIMPLE 會斷掉交易記錄備份鏈，切回 FULL 後要補一次完整或差異備份，記錄備份才接得回去。BULK_LOGGED 不會斷鏈，代價是包含大量載入的那段記錄備份不能還原到任意時間點；載完切回 FULL 後馬上補一次記錄備份。
  2. 載入前先停掉目標表的非叢集索引，全部資料進去後再一次重建，比邊插邊維護索引快得多。
  3. 用 BATCHSIZE 控制每批 commit 的筆數，避免交易記錄一次撐爆。
  4. 來源資料切成多個檔，分多個 sqlcmd 工作平行載入。前提是目標表是完全沒有索引的 heap（連 clustered index 都沒有）：TABLOCK 在這種表上拿的是 BU（bulk update）鎖，多個載入工作可以同時寫。表上只要有任何索引，TABLOCK 拿到的就是排他鎖，平行的工作會互相等。要平行載入，就先把索引拿掉，載完再建。

注意一點：:setvar 只是宣告 sqlcmd 腳本變數，宣告完之後一定要在後面用 $(變數名) 引用才有作用。光寫 :setvar BATCHSIZE 10000 而下面從沒用到，那行就是死碼，什麼都沒設定。

這裡有個坑，本文舊版也寫錯過：-v 蓋不過腳本裡的 :setvar。官方的變數優先順序由低到高是：系統環境變數 → 使用者環境變數 → 執行 sqlcmd 前的 SET X=Y → -v → :setvar。上面的 import_script.sql 開頭已經寫了 :setvar DataFile，命令列傳什麼都會被腳本那一行蓋掉，而且不報錯，照樣去匯入舊檔案。

要讓 -v 生效，就把腳本裡的 :setvar DataFile 拿掉，一律由呼叫端傳值。忘了傳、環境變數裡也沒有同名的 DataFile 時，sqlcmd 會報「scripting variable not defined」，總比悄悄吃到寫死的舊路徑好。同一支腳本掛在排程器上、每次帶不同參數跑，就是這樣寫。

自動化備份

把備份寫成腳本掛排程，是減少半夜加班的第一步。下面這支可以直接跑，關鍵是腳本內用到的每個變數都要先 :setvar 定義，否則在 :on error exit 下遇到未定義變數會直接中止。

這裡刻意用 THROW;（不帶參數）而不是 RAISERROR(@msg, @severity, 1)。原因有兩個：

  • RAISERROR 重拋時得自己用 ERROR_MESSAGE()、ERROR_SEVERITY() 把錯誤重組，過程中原始錯誤號會遺失。
  • RAISERROR 重拋時嚴重性得自己帶。原始錯誤若是 19 以上，RAISERROR 必須加 WITH LOG，而且執行者要是 sysadmin 或有 ALTER TRACE 權限，否則重拋這一步自己又會報錯，反而蓋掉真正的原因。（20 以上、會中斷連線的錯誤連 CATCH 都進不去，那種情況只能靠 -b 回傳的 ERRORLEVEL 和錯誤記錄檔。）

THROW; 在 CATCH 區塊裡會原封不動把原始錯誤丟回呼叫端，是新版（SQL Server 2012 起）官方建議的寫法。

進階效能調校

平行處理（MAXDOP）

MAXDOP（max degree of parallelism）控制單一查詢能用幾個邏輯處理器。它是伺服器層級設定，用 sp_configure 設定，跟 sqlcmd 命令列無關：

MAXDOP 該設多少，沒有「核心數超過 8 就一律設 8」這種死規則。Microsoft 對 SQL Server 2016 以後的建議看 NUMA 節點：單一 NUMA 節點時，邏輯處理器 8 個以下就設成不超過處理器數，超過 8 個設 8；多個 NUMA 節點時，每個節點 16 個以下就設成不超過每節點的處理器數，超過 16 個設每節點處理器數的一半、最高 16。這裡的 NUMA 節點指 SQL Server 自動切出來的 soft-NUMA 節點（關掉 soft-NUMA 才看硬體 NUMA）。SQL Server 2019 的安裝精靈（Database Engine Configuration 頁面新增的 MAXDOP 頁籤）會依當前硬體算出建議值，安裝時就套用你接受或修改後的值；裝好後要依工作負載調整，執行個體層級用 sp_configure，單一資料庫另外用 ALTER DATABASE SCOPED CONFIGURATION。在大型 NUMA 機器上盲套「8」反而可能設錯，實務上要看自己機器的 NUMA 配置與工作負載類型（OLTP 通常設低、批次/報表可放寬）。

伺服器記憶體

這裡要特別澄清一個網路上流傳很廣的錯誤：sqlcmd 沒有任何控制伺服器記憶體的命令列參數。

很多教學把 sqlcmd -m 65535 講成「設定最大記憶體使用量」，這是完全錯的。-m 是錯誤訊息嚴重性等級開關：只有嚴重性大於等於該值的訊息才會送到輸出。SQL Server 錯誤嚴重性從 0 到 25，-m 另有一個特殊值 -m-1，帶它時連資訊訊息也一起送出。

關於 -m-1 的寫法，在 cmd 環境下 -m -1（加空格）是不合法語法，必須連寫成 -m-1。PowerShell 行為略有不同：PowerShell 在解析命令列參數時，-1 開頭的字串可能被視為獨立引數而非 -m 的值，導致 sqlcmd 拿到的 -m 無值或解析異常；保險起見在 PowerShell 裡也統一連寫 -m-1，不要依賴空格分隔。

65535 早已超出錯誤嚴重性上限，就算引擎不報錯，效果也只是把訊息門檻拉到天花板——換句話說，幾乎所有訊息都被你關掉了，跟記憶體一點關係都沒有。

要設記憶體上限，是用 sp_configure 'max server memory'：

建議值通常是「實體記憶體扣掉作業系統與其他服務所需」之後留給 SQL Server，常見抓 75%–90% 視機器專用程度而定，要保留足夠記憶體給 OS。

安全性設定

驗證方式

範例裡一直用 -U DBAdmin -P Password 的 SQL 驗證，但在有 Active Directory 的企業環境，Windows 整合驗證（-E）才是主流且更安全的選項：

-E 用目前執行 sqlcmd 的 Windows 使用者身分登入，帳密不出現在腳本或排程任務裡，也不怕被人在 Process List 裡看到明文密碼。沒有 AD 或需要連跨網域的伺服器才用 SQL 驗證。

加密連線

-N 控制加密連線，而且這裡有版本差異：ODBC 版 sqlcmd 18（mssql-tools18，底層是預設 Encrypt=yes 的 ODBC Driver 18）起，預設就是 -Nm（強制加密），沒加 -C 時會驗證伺服器憑證；舊版預設不強制加密。所以從舊版升到 18 之後，就算命令列完全沒寫 -N，連自簽憑證的伺服器也可能突然報憑證錯誤。明確寫出來比較不會搞混：

如果伺服器用的是自簽憑證、客戶端又沒匯入信任，會連不上並報憑證錯誤。測試環境若要在自簽憑證下仍加密但不驗證，可加 -C（信任伺服器憑證）——但正式環境不該這樣放行，應該佈署受信任的憑證。

結論

sqlcmd 本身不複雜，難的是分清楚哪一層該寫什麼，以及哪些參數被網路教學講壞了。幾個最容易踩到的地方：大量匯入要靠 BULK INSERT + TABLOCK + BULK_LOGGED，最小記錄載入的條件一個都不能少，正式機切 SIMPLE 會斷記錄備份鏈；-v 蓋不過腳本裡的 :setvar；-m 跟記憶體完全無關，它控制的是訊息嚴重性門檻，-m-1 要連寫，加空格在 cmd 就壞；-k 單寫是移除控制字元、-k1／-k2 是換成空白，-r 明確帶 0 或 1 最保險；CATCH 區塊重拋用 THROW; 而不是 RAISERROR；CREATE SERVER AUDIT 建好是停用狀態，少了 ALTER ... STATE = ON 那一行，稽核等於沒開。

把這些腳本掛上排程，半夜被叫起來手動跑作業的機會就少很多。
