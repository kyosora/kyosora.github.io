Visual Studio 除錯別只會按 F5：中斷點、符號與遠端除錯實戰

程式在第 9527 筆資料才出錯時，一路按 F5 重跑只是在浪費時間。條件中斷點能直接停在那筆資料；若問題只發生在遠端主機，還要把符號、驗證與防火牆一起處理。這篇把我認為最值得先學的 Visual Studio 除錯工具排成一條實際順序。

1. 中斷點（Breakpoint）的使用

中斷點是除錯最核心的功能。程式執行到中斷點時會暫停，讓你檢查當前的變數值、呼叫堆疊與程式狀態。

條件中斷點特別有用的場合： 迴圈裡有一萬筆資料，但只有第 9527 筆會出錯。這時設 i == 9527 當條件，比按 F5 按到手抽筋快多了。

除了條件中斷點，VS 還支援：

  • 動作中斷點（Tracepoint）：不暫停，只輸出一行訊息到 Output 視窗，適合用來追蹤流程而不影響執行
  • 命中計數（Hit Count）：第 N 次才中斷，處理迴圈問題很方便
  • 相依中斷點：當另一個中斷點被命中後才啟用


2. 重要的除錯快捷鍵

快捷鍵 功能 使用場景
F5 開始除錯 啟動程式並進入除錯模式
F10 逐步執行 (Step Over) 執行當前行，不進入方法內部
F11 逐步進入 (Step Into) 進入方法內部逐步執行
Shift+F11 逐步跳出 (Step Out) 執行完當前方法並返回
Ctrl+Shift+F5 重新啟動 重新開始除錯
Ctrl+Alt+P 附加至處理程序 開啟對話框，連接到執行中的程式
Shift+Alt+P 重新附加至處理程序 快速重新連到上次附加的程序

Ctrl+Alt+P 和 Shift+Alt+P 容易混淆：前者是開對話框讓你選要附加哪個程序（第一次用），後者是直接重新連上次那個（省略選擇步驟）。遠端除錯第一次連線必須用 Ctrl+Alt+P。

3. 進階除錯技巧

監看視窗（Watch Window） 是另一個很實用但常被忽略的功能：暫停時把滑鼠移到變數上可以快速看值，但如果要持續追蹤某個運算式（例如 users.Count(u => u.IsActive)），可以把它拖到監看視窗，每次中斷都會自動更新。

4. VS 內建效能分析工具

除了手動 Stopwatch 計時，VS 有內建的 Diagnostic Tools 視窗（除錯中自動開啟，或從「偵錯 > 視窗 > 診斷工具」叫出），可以看到：

  • CPU 使用率：時間軸上的 CPU 曲線，高峰區段點下去可看到哪個方法最耗時
  • 記憶體用量：追蹤 managed heap 的增長，拍下快照後比較兩個時間點的物件數量，是找記憶體洩漏的起點

需要更深入的效能分析時，用「偵錯 > 效能分析工具」（Alt+F2）開啟完整的 Profiler，選 CPU Usage 後會產生火焰圖，可以直接看到哪條呼叫路徑佔用最多時間。

5. 遠端除錯完整教學

遠端除錯讓你在本機 VS 對遠端主機（測試機、正式機）上執行的程式設中斷點。

5.2 遠端主機設定步驟

  1. 下載並安裝 Remote Tools

    Remote Tools 2022 和 2026 可以跟兩個版本的 Visual Studio 交叉搭配，預設連接埠也都是 4026。

  2. 以系統管理員身分執行 msvsmon.exe

  3. 開放防火牆

    32 位元除錯的額外 port 會受 Remote Tools 版本與「以服務執行」設定影響，不要看文章就固定多開 4025。先看官方 Remote Debugger Port Assignments，再只放行實際需要的來源 IP 與 port。

5.3 開發機連線步驟

  1. 開啟 Visual Studio，確認本機原始碼與遠端版本一致（版本不同中斷點會打不中）

  2. 偵錯 > 附加至處理程序（或 Ctrl+Alt+P）

    注意：這裡要用 Ctrl+Alt+P（開對話框），不是 Shift+Alt+P（重新附加上次那個）。

  3. 在「連接類型」優先選遠端（Windows 驗證）。無驗證模式只適合隔離的受信任測試網路，不要暴露到公司共用網段或網際網路

  4. 在「連接目標」輸入 IP位址:4026 或 機器名稱:4026，按 Enter

  5. 點「尋找」等清單出現後，選擇要除錯的處理程序

  6. 點「附加」開始除錯

5.4 連線前注意事項

  • 遠端執行的 DLL／EXE 必須和你載入的原始碼、PDB 來自同一次 Build；不是只看版本字串相同
  • Windows 遠端除錯預設從 Visual Studio 開發機讀取 PDB，不要求把完整符號檔放在遠端主機。用「模組」視窗確認實際載入路徑與是否精確匹配
  • 建議先在測試環境驗證流程，正式機上的遠端除錯會讓程式效能下降
  • 正式機遠端除錯請務必走 VPN 或專用網路，避免 msvsmon 暴露在外網

6. 常見問題（FAQ）

遠端除錯問題

  1. 無法連線

    • 防火牆是否放行 4026 TCP
    • Remote Tools 是否在 Visual Studio 官方支援的版本組合內；不要只靠「年分一樣」猜相容性
    • 確認 msvsmon 有在遠端主機執行，且顯示「等待連線」狀態
    • 若用機器名稱無法連，改用 IP 位址試試

  2. 找不到處理程序

    • 確認程式正在執行
    • 若程式是以 SYSTEM 帳號跑的服務，需要勾選「顯示所有使用者的處理程序」

  3. 中斷點命中但顯示「沒有符號」

    • 確認 PDB 檔案存在且與 DLL 的 Build ID 相符
    • 在「偵錯 > 選項 > 符號」加上 PDB 所在路徑

一般除錯問題

  1. 中斷點不會停下來

    • 確認執行的是 Debug 組態，不是 Release
    • 中斷點圖示空心？表示符號未載入，重新建置後再試

  2. Production 環境出問題無法直接除錯

    • 先靠結構化日誌（Serilog、NLog）縮小範圍
    • Application Insights 或類似的 APM 工具可在不中斷程序的情況下取得例外堆疊，但仍有取樣、網路與執行效能成本
    • 確認有需要才考慮遠端除錯，對效能影響不小

  3. 非同步程式很難追蹤

    • 善用「偵錯 > 視窗 > 工作」視窗看各 Task 狀態
    • 先看實際例外型別與 call stack；只有被 AggregateException、reflection 等包裝時，InnerException 才是下一層線索

7. 實用除錯建議

養成這幾個習慣，debug 時會快很多：

  • 條件中斷點比「F5 無限重試」省力，設好條件直接跳到問題點
  • Debug.WriteLine 輸出到 Output 視窗，不會干擾 UI，比 Console.WriteLine 更適合除錯用途
  • 提交前記得清除 Debugger.Break() 這類除錯用程式碼，可以在 CI 加個 grep 保底
  • 變數命名清楚，監看視窗裡的值才有意義；temp1、temp2 看到會想哭
  • Diagnostic Tools 的 CPU/記憶體時間軸，養成除錯時瞄一眼的習慣，有時問題在你還沒意識到前就已經在圖上很明顯

8. 例外處理與日誌的搭配

遠端環境不能隨時附加除錯器，日誌品質決定了排查速度。

幾個讓日誌真正有用的原則：

  • 用結構化日誌（{UserId} 佔位符而非字串插值），才能在 Seq 或 Kibana 裡過濾
  • Warning 留給「出乎意料但程式能繼續跑」的狀況，Error 留給「需要人介入」的狀況
  • 每層只 log 一次，別在 repository、service、controller 三層都 log 同一個例外，堆疊裡會出現三份重複

我的優先順序是：條件中斷點先縮小輸入，例外設定抓第一個拋出點，再看 call stack 和變數；遠端附加放在最後。很多問題靠前兩步已經能定位，沒必要一開始就把正式機接上除錯器。
