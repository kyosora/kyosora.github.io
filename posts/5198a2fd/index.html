刪一個帳號拖垮平台：Inngest 的重試為何塞滿連線池

發表於2026-09-30|系統與維運資料庫
|總字數:2.3k|閱讀時間:7分鐘

刪帳號通常不在系統最繁忙的路徑上。但 2026 年 9 月 18 日，Inngest 的帳號刪除流程卻讓其他服務也拿不到資料庫連線。

起點是 Vercel Marketplace 的解除安裝請求。它觸發實體刪除，沿著數十張資料表的外鍵做級聯刪除；後續同帳號的重試又卡在既有交易的鎖後面。PgBouncer 客戶端連線數升到平常約 14 倍，共享連線池耗盡。Inngest 事故報告

我認為這份報告值得讀，是因為每一個零件都很熟：外鍵、交易、重試、連線池。它們放在一起，卻讓一項低頻管理操作擴散成平台事故。

同一個刪除，做第二次並不免費

對「刪除帳號」來說，重複執行後的最終狀態可以相同：帳號不存在。這不代表第一次尚未完成時，第二次呼叫就不會增加負擔。

如果兩個請求都進入資料庫，第二個可能已經拿到連線，只是在等第一個釋放鎖。更多重試進來，等待者仍各自占用連線與排隊資源，即使它們都在追求同一個刪除結果。

flowchart LR
    A[第一筆刪除交易] --> B[級聯刪除並持鎖]
    C[同帳號重複請求] --> D[進入資料庫後等鎖]
    B --> D
    D --> E[占住連線]
    E --> F[後續客戶端排隊]
    F --> G[共享容量耗盡]

這張圖是依事故機制整理的因果示意，省略了各服務自己的連線池。它也不代表一筆 DELETE 必然鎖住整個資料庫。真正把影響擴大的，是互相等待的工作占住共享容量，讓其他工作連入場的機會都沒有。

所以我檢查刪除 API 時，會把兩個問題分開：重複請求的結果是否一致，以及重複請求能否在昂貴工作開始前被合併。第一個通過，第二個仍可能失敗。

重啟之後，又被同一批工作塞回去

事故中，16:26 UTC 重啟 PgBouncer 沒能解除阻塞；16:39 取消原始刪除與排隊中的刪除後，才逐步恢復。第二波影響裡，Postgres 的鎖已於 18:00 回到基線，連線池卻還多卡了約十分鐘。報告對第二波的具體觸發原因仍保留調查狀態。事故時間線

這裡有兩種不同的等待：

位置 正在等什麼 要看哪裡
PostgreSQL 內 查詢已進入後端，正在等鎖 pg_stat_activity、阻塞者 PID
PgBouncer 內 客戶端尚未分配到後端連線 SHOW POOLS 的 cl_waiting、maxwait

PgBouncer 的 transaction pooling 在交易結束後才歸還後端連線。查詢等待鎖時，交易還沒結束；尚未取得後端的客戶端，則在池內排隊。不能把所有等待者都算成 PostgreSQL 後端，也不能把 cl_active 全解讀成正在使用 CPU。PgBouncer 官方文件

重啟可以清掉某些連線狀態，卻沒有自動改變「誰還在持鎖」與「誰還在送工作」。如果入口繼續灌入請求，清空的容量很快又會被吃掉。

我會把「入口已停止增加同類工作」列為處置時要確認的事，再追阻塞交易與排隊者。資料庫圖表恢復正常之後，還得看應用程式是否重新拿得到連線、佇列是否真的在消退。

先限制同時進場的工作，再談重試速度

Inngest 報告列出的已上線措施之一是刪除流程的緊急開關，請求仍以固定事件 ID 留存；軟刪除、剩餘實體刪除的分批執行與同帳號去重，則列為後續調整方向。不能把改善清單都當成已經完成。官方處置說明

如果由我設計這條路徑，會先把「接受刪除請求」和「完成資料清除」拆開。前者持久記錄工作狀態，後者由有並行上限的 worker 處理。同一帳號正在刪除時，重送請求應取得既有工作的狀態，不再建立另一筆昂貴刪除。

固定事件 ID 是其中一個工具，但它得搭配原子去重與可恢復的工作狀態。只在記憶體裡放一個 processing = true，跨程序或重啟之後仍可能重複執行。若採租約，也得處理租約過期後舊 worker 尚未停下的情況。

分批同樣不能只看 SQL 裡有沒有 LIMIT。單批刪掉一個父項目，若仍級聯到大量子資料，工作量依然可能失控。我會沿著外鍵關係檢查每批實際影響的資料量、交易時間與鎖等待，再決定批次大小。

重試的退避與隨機延遲可以降低同時湧入的機率，但無法保證同一帳號只執行一次。若原始交易還活著，慢一點送入的重試仍可能排在它後面。並行上限、同帳號序列化與去重，處理的才是這個重疊問題。

Timeout 能縮短等待，不能替工作去重

PostgreSQL 的 lock_timeout 限制每次取得鎖的等待時間；statement_timeout 限制整個陳述式的執行時間。前者不管拿到鎖後還要跑多久，後者也不是多個陳述式合計的交易期限。PostgreSQL 逾時設定

這兩個 PostgreSQL 設定都不涵蓋尚未取得後端連線、仍在 PgBouncer 排隊的時間。應用程式等待取得連線的期限，也要另外處理。

我也不會單憑 max_client_conn 報錯就把容量一路調大。更多名額可能只讓更多工作排進來；需要先確認資料庫還有處理餘裕，以及不同工作負載是否有各自的上限。即使分了使用者或邏輯池，也要檢查它們是否仍受同一個全域連線額度限制。

下次我會先查那個很少人用的管理功能

這起事故讓我想到的是刪帳號、整批匯入、歷史資料清除這類功能。它們平常請求少，測試時也很容易只放幾筆資料，於是成功案例看起來都很快。

我會補的驗收情境很具體：準備一個資料量大的帳號，刻意讓第一筆工作變慢，再連續送入相同請求。同時觀察無關 API 能否正常取得連線，以及停止新請求後，需要多久才排空。

這能檢查的，是慢操作會不會拖走別人的容量，以及解開阻塞之後，系統是否真的有能力消化積壓。

讀完這份報告，我最想回頭看的，是那些平常被認為「偶爾才跑一次」的功能。低頻只代表它不常開始，沒有告訴我它一旦卡住，會占著多少資源不放。
