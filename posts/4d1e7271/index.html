IIS 用 C# 呼叫 LibreOffice：轉檔權限與逾時修正

發表於2024-11-02|程式設計系統與維運
|總字數:2.4k|閱讀時間:9分鐘

我第一次把 LibreOffice 轉檔程式部署到 IIS 時，本機能跑，伺服器卻只留下三種結果：沒有輸出檔、權限不足，或 soffice.exe 卡著不結束。

我一開始把問題全歸到身分模擬，照網路範例串了 LogonUser、ImpersonateLoggedOnUser、DuplicateTokenEx 和 CreateProcessAsUser。程式變長一大截，權限也越開越多，問題仍然不好查。

後來我才發現，這個做法把兩件事混在一起了：誰負責執行 LibreOffice，以及程式怎麼確認轉檔成功。固定由同一個帳號轉檔時，最直接的解法是讓 IIS 應用程式集區本身就用那個身分執行，再由 Process.Start 啟動 LibreOffice。這樣不需要在每次請求裡切換 Windows token，也不用把密碼塞進 Web.config。

2026-07-27 修訂：舊版文章把 CreateProcessAsUser 的權限授予對象寫錯，也多做了一次不必要的 DuplicateTokenEx。這次依 Microsoft 與 LibreOffice 官方文件重寫，舊程式碼不建議繼續使用。

先釐清 Process.Start 用誰的身分

ASP.NET 的 impersonation 作用在執行緒。Microsoft 明確指出，從 ASP.NET 產生的新程序仍以 worker process 的身分執行，不會自動繼承執行緒的模擬身分。

固定使用一個轉檔帳號時，我現在會從兩種配置選一種：

情境 做法
檔案都在本機 維持 ApplicationPoolIdentity，把必要資料夾 ACL 授給 IIS APPPOOL\<集區名稱>
需要用指定的網域帳號存取檔案伺服器 把轉檔工作拆到獨立集區或 worker，讓它直接以專用服務帳號執行

兩種做法的共同點是：w3wp 與它啟動的 LibreOffice 使用同一個可預期身分。若同一套 Web 應用真的需要替多個使用者建立不同身分的程序，那才值得考慮 CreateProcessWithLogonW 或 CreateProcessAsUser。

第一，Microsoft 的 LogonUser 文件寫得很清楚：除了 LOGON32_LOGON_NETWORK 等少數情況，函式通常已回傳可交給 CreateProcessAsUser 的 primary token。本文使用的 LOGON32_LOGON_BATCH 不需要再用 DuplicateTokenEx 轉一次。

第二，SeIncreaseQuotaPrivilege 與可能需要的 SeAssignPrimaryTokenPrivilege 是 CreateProcessAsUser 呼叫端的條件。舊稿卻叫讀者一律把權限授給目標轉檔帳號，這可能造成錯誤碼 1314 仍然存在，還平白擴大帳號權限。

Microsoft 對替代憑證的建議是：若 CreateProcessAsUser 因 1314 失敗，可考慮不要求這些特殊權限的 CreateProcessWithLogonW。代價是目標帳號必須能在本機互動登入，密碼也要交給呼叫端。對一個固定用途的 IIS 轉檔服務來說，這通常還是比「直接設定集區身分」更難管。

IIS 與資料夾權限

以下用集區 DocumentConvertPool 為例。

在 IIS 管理員開啟應用程式集區的「進階設定」：

  • 識別：ApplicationPoolIdentity
  • 載入使用者設定檔：True

Load User Profile=True 讓集區有自己的 Windows profile，但它不會自動解決檔案 ACL。本文另外指定 LibreOffice 的 UserInstallation，因此這個設定也不是轉檔成功的唯一條件。

權限只給需要的目錄：

  • 來源目錄只需要讀取。
  • 輸出與 profile 目錄需要修改權限。
  • LibreOffice 安裝目錄只需要讀取與執行，通常既有 ACL 已足夠；不要授予寫入權限。

如果改用專用帳號，就把上面的 IIS AppPool\DocumentConvertPool 換成那個帳號。不要為了省事把 D:\、網站根目錄或 C:\Program Files 整棵開成 Full Control。

用 soffice.com 才拿得到錯誤輸出

LibreOffice 官方文件在 Windows 範例使用 soffice.com，並說明不需要命令列介面時才改用 soffice.exe。IIS 的轉檔工作正需要 stdout 與 stderr，因為轉換濾鏡錯誤、檔案損壞與 profile 問題都可能寫在裡面。

舊稿雖然宣稱「把輸出與錯誤導向記錄檔」，實際的 STARTUPINFO 沒有設定 STARTF_USESTDHANDLES，也沒有建立 pipe，所以一個字都沒接到。下面改用 .NET 內建的 ProcessStartInfo，少掉 P/Invoke，也真的能讀取兩個輸出串流。

獨立 profile 解決的問題

LibreOffice 官方文件要求程序能寫入 user profile。多個轉檔程序共用預設 profile 時，後啟動的程序可能接到既有 instance，或卡在 profile lock。-env:UserInstallation=file:///... 可以指定另一個 profile 位置。

範例每次建立不同目錄，轉完後再刪除。這會增加啟動成本，但比多個 request 爭同一份 profile 好查。轉檔量變大後，我會改成固定數量的 worker 與 profile，而不是讓每個 HTTP request 無上限地啟動 LibreOffice。

逾時仍有邊界

Process.Kill() 只保證嘗試終止目前拿到的程序，不是完整的 process-tree 管理。如果特定 LibreOffice 版本另開子程序，或轉檔工作不能接受強制終止，正式環境應把它放進獨立 worker，搭配 Windows Job Object 或外部工作排程器做整棵程序樹的生命週期管理。

這也是我不建議在同步 HTTP request 裡大量轉檔的原因。LibreOffice 是大型文件解析器，來源檔又通常不可信。比較安全的配置是低權限 worker、固定輸入與輸出目錄、併發上限，再由 Web 應用查詢工作結果。

出錯時先看這五項

  1. log 裡的 WindowsIdentity.GetCurrent().Name 是否為預期的集區身分。
  2. 來源目錄有沒有 Read，輸出與 profile 目錄有沒有 Modify。
  3. 伺服器是否存在 soffice.com；若只有 soffice.exe，先確認 LibreOffice 版本與命令列行為。
  4. stdout、stderr 與 exit code 實際寫了什麼，不要只用「輸出檔不存在」猜原因。
  5. 同一時間是否啟動太多 LibreOffice，或意外共用同一個 profile。

我原本想用更多 Windows token API 解決這個坑，最後反而是刪掉 P/Invoke 後比較可靠。讓程序身分在 IIS 設定裡一次決定，程式碼只負責啟動、等待、收錯誤與驗證輸出，責任清楚很多。
