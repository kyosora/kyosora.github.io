API 單獨打 0.09 秒、從瀏覽器按要 20 秒：ASP.NET Session 鎖讓請求排隊

發表於2026-11-12|前後端開發系統與維運
|總字數:3.7k|閱讀時間:13分鐘

PM 在 Notion 開了一張單：登入頁按「我的E政府」→「登入我的E政府」之後，畫面好幾秒沒反應，使用者會以為沒按到。PM 要的是一個 Loading。

這個系統是 ASP.NET MVC 加 Web API，跑在 .NET Framework 上，前端是 Vue 3。按鈕背後有兩段：先跟後端要 E政府的登入網址（GET api/auth/sso/gsp-url），再整頁跳過去。兩段之間，登入頁什麼都沒變。

第一輪的修法就是照單全收。E政府在外部，慢一點很正常，加個遮罩讓使用者知道有在動就好。Loading 的 commit 都進版控了，我才發現這個判斷只對了一半。

Loading 加好了，取樣次數卻從 12 變成 87

遮罩很好加：按下就顯示「正在前往我的E政府，請稍候…」，一路留到頁面換走。驗收我交給 Claude Code，請它寫一支 Playwright 腳本：從按下按鈕開始，每 200 毫秒檢查一次畫面上的遮罩，直到換頁。

本機跑的時候，腳本用 page.route 把 gsp-url 攔在瀏覽器裡，延遲 3 秒再回一個假網址。11 項全過，取樣 12 次。

部署到測試機、改走真的後端，一樣全部 PASS。但其中一行長這樣：

腳本每次取樣之間固定睡 200 毫秒，87 次取樣中間至少隔了 86 段，算下來遮罩至少掛了 17 秒，還沒算每次查詢本身花的時間。

測試全過，使用者卻還是要等十幾秒。PM 說的「有點慢」就是這 17 秒，遮罩只是讓它看起來有在動。

本機為什麼量不到，等找到原因才想通：本機那支 gsp-url 根本沒送到伺服器，在瀏覽器裡就被攔下來了。

按鈕會打的請求，單獨測都很快

Claude Code 接著用 curl 把按鈕前後會碰到的請求各打一次：

本站的 UserLogin/SSOLogin 回 302 大約 1 秒（還不含 E政府頁面本身的載入），取網址 0.09 秒，按鈕自己會打的兩個請求加起來不到 1.2 秒。

唯一慢的是 sso-login，可是按鈕不會打它。這支是登入頁一載入、在 onMounted 裡自動打的：縣府員工從內部的員工入口網點進來時，瀏覽器會帶著入口網發的 SSO cookie，系統就直接登入，不必再輸入帳密。

一支跟按鈕無關的請求跑了 21 秒，按鈕的請求在瀏覽器裡就跟著慢。Claude Code 看到這組數字，第一個懷疑的是 Session 鎖。

帶同一個 cookie，才重現得出來

ASP.NET（.NET Framework 的 System.Web 這一套）的 Session 有一把獨占鎖。微軟文件寫得很清楚：同一個 SessionID 的兩個請求同時進來，第一個拿到 Session 的獨占存取權，第二個要等第一個跑完才會執行，除非第一個握鎖握到逾時。

這也解釋了單獨用 curl 為什麼量不到。curl 不帶 cookie，每次都是全新的 Session，誰也不用等誰。瀏覽器不一樣，送回同一個站台的請求都會自動帶上同一個 ASP.NET_SessionId cookie，開別的分頁也一樣。

同一支 gsp-url，帶著 Session 要 20.3 秒，不帶只要 0.08 秒。它晚 1 秒送出，一直等到 sso-login 放掉鎖才開始跑。

這個對照組有個不夠嚴謹的地方：第 4 步是等前面兩支跑完才送的，只能證明 gsp-url 本身不慢。要排除「那 20 秒整個站台都在忙」，第 3 步也要丟到背景，緊接著送出不帶 cookie 的第 4 步，最後再 wait，三支請求才會真的重疊。

PM 遇到的情況就是這樣：打開登入頁，sso-login 在背景握著 Session；這 21 秒內按「登入我的E政府」，gsp-url 就排在它後面。帳密登入也一樣會被卡住。

Global.asax 讓每個請求都搶同一把鎖

Web API 預設不用 Session。這個專案在 Global.asax.cs 裡強制打開：

網路上搜「Web API 使用 Session」，很多答案就是這三行。它對每個進到 ASP.NET 的請求設 Required，也就是要讀也要寫，每個請求都得拿所屬 Session 的那把獨占鎖。同一個 Session 的請求，不管是 API 還是頁面，全部變成單線道。

平常每支 API 幾十毫秒，排隊也感覺不出來。只要有一支卡住，後面整排都在等。

這三行也不能直接拿掉。系統的 E政府登入走 OIDC，state 和 PKCE 的 verifier 要先存在後端 Session，等 E政府導回來再拿出來比對。有些請求真的需要 Session。

21 秒跟 Windows 的連線逾時一樣長

再看 sso-login 為什麼要 21 秒。新版 API 只包了一層，實際邏輯在舊版的 controller 裡，順序是這樣：

  1. 呼叫入口網的認證 API，用系統的應用程式帳號換一張 token
  2. 看瀏覽器有沒有帶入口網的 SSO cookie
  3. 沒有 cookie，回「沒有取得SSOToken」

入口網的認證 API 在縣府內部，測試機和我的開發機都連不到，第 1 步就一直等到連線逾時。

21 這個數字很眼熟。我在自己的 Windows 11 上，對一個不會回應的位址開 TCP 連線：

21.09 秒後失敗，跟測試機上的 21.19 秒幾乎一樣。程式裡沒有人設 21 秒，所以我判斷測試機也是卡在建立 TCP 連線：SYN 送出去沒有回應，Windows 重送幾次後放棄。這是推論，我沒有在測試機上抓封包確認，而且 Windows 的重送次數和間隔可以調，你的機器不一定剛好 21 秒。

問題出在順序。沒有 cookie 的時候，第 3 步的結果在一開始就決定了；第 1 步等完 21 秒，換來的還是同一句「沒有取得SSOToken」。外部廠商、PM、所有不是從入口網進來的人，每次打開登入頁都要在背景陪它等 21 秒，而且等的時候手上握著 Session 鎖。

帶假 cookie 還是 21 秒，這正是要看的：只要有 cookie，就照樣走進舊的認證流程，那條路沒被跳過。至於帶著有效 cookie 的員工能不能登入成功，測試機連不到入口網，這裡驗不了。

項目 修改前 修改後
sso-login（不帶入口網 cookie） 21 秒 0.78 秒
gsp-url（跟 sso-login 同一個 Session） 20.3 秒 0.09 秒
按下按鈕到離開登入頁 17 秒以上 約 2 秒

0.78 秒是部署完第一次呼叫，同一個 Session 緊接著再打一次是 0.11 秒。

Global.asax 先不動

根治的做法是只讓需要 Session 的請求拿鎖。我比較過三條路：

做法 解決什麼 代價
sso-login 沒 cookie 就早退 一般使用者不再卡 21 秒 只修好這一支；別支 API 慢起來，一樣整排塞住
外部呼叫設短逾時 21 秒縮成幾秒 要改舊版共用的認證元件；有 cookie 的員工還是會被鎖那幾秒
依路由設定 Session 行為 不碰 Session 的 API 不再陪著排隊（要寫同一個 Session 的請求還是互斥） 要先盤點每一支 API 有沒有讀寫 Session，漏一支就是某個功能壞掉

第三條最乾淨，但動到的是整個系統的每一個請求。為了一張「加個 Loading」的單去改全域設定，我認為不划算，先記成技術債，這次選第一條。

真的要做，大概長這樣（沒有上線，只是示意）：

SetSessionStateBehavior 必須在 AcquireRequestState 之前呼叫，PostAuthorizeRequest 剛好在它前面。拖到 AcquireRequestState 當下或之後才呼叫，會丟 InvalidOperationException。

ASP.NET Core 的 Session 不上鎖，不會有這種排隊。代價換成兩個請求同時寫 Session 時，後寫的會蓋掉先寫的，連改不同的 key 都可能互蓋。

修好之後，Loading 的測試反而 FAIL

沒有入口網 cookie 時的 21 秒排除之後，Loading 還是留著。網路慢、E政府那邊慢的時候，使用者至少知道有在動。

部署完再跑一次驗收，真後端那組反而 FAIL 了：

後端變快了，按下去不到半秒就開始換頁。腳本從頁面外面一次次查元素，換頁中途不是拿不到結果，就是拿到的已經是下一頁，舊頁面上的遮罩一次都沒量到。

這支腳本之前就卡過一次。為了不真的跳去 E政府，腳本也把換頁要去的那個頁面攔下來，回一個假頁面。一開始在攔換頁的 callback 裡查同一頁的遮罩，結果整支卡到 30 秒逾時。看起來是換頁請求在等 callback 回應，callback 裡的查詢又在等換頁結束，兩邊互等。後來 callback 只負責延遲和回假頁面，取樣交給主流程，才有前面那個「87 次」。

最後的做法是從頁面裡面回報：用 MutationObserver 盯 DOM，再掛 pagehide，透過 page.exposeFunction 把每次變化送回 Node。這個專案的遮罩是用 v-if 整個節點加進去的，所以只盯節點增減就夠；如果你的遮罩是切 class 或 style 顯示，要再加 attributes: true。

這樣量到的是：頁面收到點擊後 2 毫秒，DOM 裡就有 .loading 節點；2050 毫秒離開登入頁，離開那一刻節點還在。它證明的是節點存在，畫面有沒有真的畫出來，要看截圖。另外，這次只有換到同網域的頁面時收得到 pagehide 的回報，換到跨網域的假頁面就收不到，原因我還沒查清楚。

遮罩本身還有一個容易漏的地方：使用者到了 E政府又按「上一頁」，瀏覽器可能直接從 bfcache 還原離開前的畫面，頁面不重新載入，遮罩就原封不動蓋在登入頁上。要在 pageshow 收掉：

這次記住的事

回頭看，PM 開單寫的是 Loading，真正在意的是慢。如果第一輪加完遮罩就交差，這 21 秒會一直藏在遮罩後面。之後接手的人只會看到單上寫著「已加 Loading」，不會知道後面還有 21 秒在等。

讓我回頭看的，是 PASS 那行裡的「87 次」。測試過了，數字怪怪的，還是值得停下來看一眼。

下次再遇到「單獨打很快、從瀏覽器按很慢」，我會先拿同一個 cookie 並發打一次，再決定要不要加 Loading。
