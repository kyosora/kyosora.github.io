流水號重複？SQL Server 只加 UPDLOCK 不夠，每月第一筆還是會撞號

發表於2026-09-23|前後端開發資料庫
|總字數:2.9k|閱讀時間:9分鐘

8 月初，廠商丟來一張截圖：正式機上有兩筆巡查案件，案號都是 115-07-041。

地址是同一條巷子的兩個門牌。資料的 id 是連號的 5817、5818，巡查時間差 70 秒，是同一位外業人員建的。

案號格式是「民國年-月-三位流水號」，每個月從 001 重新數。這種號碼大家都寫過，很多系統的寫法也跟這套一樣：查出這個月最大的號碼，加 1，存回去。

三個地方各自算號

我先把產號的程式碼全翻出來，總共三處：

  • 舊外業 App 的 6 支 Survey／Facility 頁面
  • 新版外業 App 的 useAnomaly.js
  • 新版管理端的案件編輯頁

三處都在前端算號。新版外業 App 的寫法長這樣（節錄）：

讀一次、算一次、寫一次，三個動作之間隔著網路，也可能隔著不同的使用者。兩個人幾乎同時存檔時，時間線是這樣：

時間 使用者 A 使用者 B
T1 查到本月最新是 040
T2 查到本月最新是 040
T3 算出 041，寫入
T4 算出 041，寫入

B 在 T2 查的時候，A 還沒寫進去，兩邊看到的是同一個世界。

新版外業 App 的狀況更糟。它在開表單的時候就把號碼算好放進畫面，外業人員拍完照、填完欄位才按存檔，中間可能隔好幾分鐘，這整段時間都是競態窗口。舊版至少是存檔當下才算。

還有一個順手抓到的問題：外業 App 補零補到 4 位（0041），管理端補 3 位（041），同一張表裡的格式根本不一致。

至於 70 秒的時間差為什麼還會撞號，我的判讀是：巡查時間是現場填的，不是寫進資料庫的時間。外業常常在沒訊號的地方作業，回到有網路的地方才批次同步，兩筆幾乎同時送出。

正式機先不動

撞號是真的 bug，但我沒有馬上改正式機。

正式機跑的是舊系統，年底新版上線就會換掉。我查過整張表，歷年只有這一組重複，算是多年一遇。在即將退役的系統上動產號邏輯，風險比撞號本身還高。

所以正式機只做兩件事：人工把其中一筆改成 042，再寫一支查重 SQL，每個月資料同步後跑一次：

回傳 0 列，代表這次檢查沒找到重複案號。新版系統才是要根治的地方。

預覽號和入庫號要分開

病根是同一個號碼身兼兩職：它是畫面上給使用者看的號，也是最後寫進資料庫的號。

把這兩件事拆開就好處理了：

  • 前端的 generateNotificNo 保留，開表單時照樣顯示一個預覽號，使用者體驗不變
  • 存檔時前端傳來的號碼一律忽略，改由後端在交易裡重新產號
  • 後端把真正的號碼回傳，前端拿來蓋掉預覽號

絕大多數時候預覽號就是最終號碼。不過從開表單到存檔之間，只要同月份有別的案件先存進去，最終號碼就會跟預覽不同，存檔後畫面會跟著更新。

後端交易怎麼寫

後端的核心是這段 SQL（實際程式碼的欄位比較多，這裡刪到只剩產號相關的部分）：

讀 MAX、組號碼、INSERT 都在同一個交易裡，關鍵是 WITH (UPDLOCK, HOLDLOCK) 這兩個 hint。XACT_ABORT ON 讓大部分執行階段錯誤直接中止並回滾整個交易，比較不會留下鎖著的半套交易；C# 那端的例外處理還是要做。

只包 BEGIN TRAN 沒用。SQL Server 預設的隔離層級是 READ COMMITTED，SELECT 讀完就放掉共用鎖，兩個交易還是能讀到同一個 MAX。

這段也有一個已知限制：流水號只取末三碼，每月上限 999 號，第 1000 號會被截成 000，之後再產號又會從末三碼繼續算，唯一性也跟著破功。這個系統每月幾十筆，我先接受；你的量如果可能破千，要在產號時明確報錯，或者連同解析和歷史資料一起擴位。

只加一個 hint 會怎樣

寫文章時我想確認每個 hint 各自擋掉什麼，就讓 Claude Code 在本機 LocalDB 開一張測試表，用兩條連線同時跑上面那段邏輯。第一條讀完 MAX 後刻意 WAITFOR DELAY '00:00:03'，第二條晚 0.3 秒出發，確保兩邊一定重疊。

分兩種情境跑：這個月還沒有任何案件，以及這個月已經有一筆 001。

hint 當月還沒資料 當月已有 001
不加 撞號（001、001） 撞號（002、002）
只加 HOLDLOCK 一條被判死結 一條被判死結
只加 UPDLOCK 撞號（001、001） ✅ 002、003
UPDLOCK, HOLDLOCK ✅ 001、002 ✅ 002、003

中間兩列最值得看。

只加 HOLDLOCK，等於把這張表的讀取升到 SERIALIZABLE。兩個交易讀的時候拿的都是共用鎖，互不衝突，接著都想 INSERT，寫入要的鎖又跟對方手上的共用鎖衝突，SQL Server 只好挑一個當死結犧牲者（錯誤 1205）。這是典型的讀後轉寫死結；實際互等的是哪些鎖資源，我沒有抓 deadlock graph 確認。號碼沒撞，但使用者看到的是存檔失敗。

只加 UPDLOCK 比較陰險。更新鎖彼此互斥，當月已經有資料時，第二條會卡在第一條鎖住的那筆 001 上，乖乖排隊，結果正確。可是 UPDLOCK 本身不提供 SERIALIZABLE 那種防幻讀的範圍保護。當月還沒有任何案件時，沒有一筆 001 可以讓兩邊去搶，這次測試裡兩條就一起讀到 0，各自插入 001。

在這次的測試條件下，漏洞只出現在空月份。如果測試都從已經有案件的月份開始，就會完全漏掉這個情境。

兩個一起加，HOLDLOCK 負責鎖住「還不存在的資料」所在的範圍，UPDLOCK 讓兩邊在讀取階段就搶同一把互斥的鎖。這次測試裡，第二條在讀取時就開始排隊，沒有走到只加 HOLDLOCK 時那種鎖轉換造成的死結。它多等了約 2.7 秒，剛好是第一條剩下的延遲時間。

這把鎖的代價

HOLDLOCK 鎖的是「掃過的範圍」。我後來查了 AnomalyNotific 的索引，只有 id 上的叢集主鍵，NotificNo 沒有索引。

這表示那段 LIKE @prefix + '%' 沒有索引可以精準定位，得掃過整個叢集索引，鎖定範圍可能遠大於當月那幾十筆，連其他月份的新增或更新都可能被擋住。實際鎖了哪些東西、擋到誰，要看執行計畫和鎖定粒度，我沒有在正式機上量過。

我接受這個代價。測試庫裡每個月的案件量是 26 到 41 筆，同時產號的機會本來就少，交易又短，就算排隊也感覺不到。

如果你的系統一天要產幾千個號，就該在號碼欄位加索引，讓鎖定範圍盡量縮到當月那一段。或者乾脆換成獨立的序號表，用一句 UPDATE ... OUTPUT 原子地加 1。

（我也想過 SQL Server 的 SEQUENCE，但它不會每月歸零，還得自己處理重置時機，比現在這段更複雜，就沒用。）

能加 UNIQUE 約束當最後防線當然更好，撞號時至少會報錯，不會默默寫進去。這次沒加，因為正式機那張表還是舊系統在寫，加了之後，舊系統一撞號就是外業人員在現場存檔失敗。

要講清楚的是：新 API 只保護經過它產號的請求。只要還有舊的寫入路徑在前端自己算號，整張表就不能保證不再重複。這也是為什麼正式機那支查重 SQL 要跑到舊系統退役、補上 UNIQUE 為止。

為什麼沒走共用的資料存取層

專案裡有一個全系統共用的 SafeSqlExecution，會用正規表示式把 SQL 改寫成參數化查詢。它只認得單純的 INSERT ... VALUES 和 UPDATE ... SET，碰到上面這段 DECLARE、TRY_CAST、表格 hint 混在一起的語句，會被它改壞。

改那個共用的改寫器，影響範圍是全系統的查詢，每一支都得重新驗證參數化有沒有被改壞，為了一個功能不值得。所以這支 API 的新增分支我直接用 ADO.NET，每個參數都明確綁型別：

編輯既有案件的分支不重新產號，維持原本的寫法沒動。

前端只剩回填

外業 App 的存檔改呼叫新的 API，存完用後端回傳的號碼蓋掉預覽號：

存檔成功的提示也加上最終案號。最終案號跟預覽不同時，外業人員從成功提示就能確認實際拿到哪一號。

補零位數順便統一成 3 位。

管理端則刪掉一段存檔前的查重檢查：它拿預覽號去查資料庫，查到重複就擋下存檔，要使用者「重新取得案件編號」。號碼改由後端決定之後，這段檢查只會在沒有問題的時候擋人，留著反而有害。

前後端都改完，我在專案的測試環境對存檔 API 同時送 5 筆請求，拿到 115-08-001 到 005，連續、不重複。

回頭看

修的時候我把重點放在「產號搬到後端」，寫文章回頭逐一拆 hint 才發現，最容易寫錯的其實是 hint 的組合，而且只測已經有資料的月份根本看不出來。

下次再寫流水號，我會先開兩條連線，挑一個空月份跑一次。
