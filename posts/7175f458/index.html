Win11 25H2 的 QTTabBar 分頁列救不回來，我改用 HoverPeek 做懸停預覽

我的一台 Win11 25H2（26200.9457），檔案總管裡 QTTabBar 的分頁列不見了，把 QTTabBar 升到 1.6.4 也一樣。

我前後追了兩輪。第一輪查到三個 feature 被一組優先權更高的設定開著，刪掉之後重開，三個 feature 都顯示停用。第二輪才確認：旗標關了，分頁列還是沒出來。最後我放棄了，回頭重構三月用 AI 寫的 HoverPeek，因為我一開始要的就只是 QTTabBar 的懸停預覽。

前半寫 QTTabBar 我查到哪裡、試了什麼都沒用；後半寫 HoverPeek v1.3 怎麼變快，又在哪裡卡死過。

先看兩個元件最後一次留下紀錄的時間

QTTabBar 有兩個元件：AutoLoader 是 BHO，負責在檔案總管開啟時把分頁列叫出來；分頁列本身是一個 Explorer band。

Windows 會在 HKCU\Software\Microsoft\Windows\CurrentVersion\Ext\Stats\{CLSID}\iexplore 底下記一個 Time，格式是 SYSTEMTIME（UTC），跟這個元件被檔案總管載入的時間有關。QTTabBar 的 CLSID 第四段是 A777 的是 AutoLoader，A333 的是分頁列：

出問題的那台，我開啟檔案總管後，A777 的 Time 仍會更新；A333 最後一筆停在 2026-02-02。我無法從這個日期判定分頁列何時開始失效。能確定的是，我在升級 QTTabBar 之前就看不到分頁列了，升到 1.6.4 後也沒有恢復。

寫這篇時，我在另一台 26200.9974 上也跑過同一段腳本，兩個元件的時間都停在 2 月 13 日；那台我沒有繼續追。

三個 feature，被更高的優先權開著

QTTabBar 社群（indiff 維護的分支）有兩張 issue 記錄了這件事。#429 有人回報，2025 年 12 月的 KB5072033（26200.7462）之後分頁列消失，用 ViVeTool 停用三個 feature（57048216、57048237、58988972）再重開就恢復了。到了 2026 年 3 月的 KB5079473（26200.8037）之後，#432 有人說重跑同樣三行沒用，也有人說仍然有效。

我這台的情況是，這三個 feature 在 HKLM\SYSTEM\CurrentControlSet\Control\FeatureManagement\Overrides\15 底下還各有一筆設定。Feature 設定有優先權，ViVeTool 原始碼裡的列舉寫得很清楚：User 是 8，ImageOverride 是 15。vivetool /disable 寫的是 8，比 15 低。

ViVeTool ID Overrides\15 底下的 key 名
57048216 815149711
57048237 1519792783
58988972 1482552975

這三個 key 的擁有者是 SYSTEM，只有 TrustedInstaller 有完整控制權，Administrators 只能讀。我先 reg export 備份整個 Overrides\15，再取得擁有權、刪掉這三個 key（Overrides\8 沒動），補跑一次 ViVeTool，重開機。之後查這三個 feature，都是 User (8) Disabled。

三個 feature 都停用了，分頁列還是沒有出來。 取得擁有權的腳本我就不貼了：要動 SYSTEM 擁有的登錄機碼，最後還沒用。

重建工具列版面後，我又查了哪些地方

  • 檔案總管存工具列版面的 ITBar7Layout 裡，我查到的時候沒有 QTTabBar 的 CLSID。我備份後刪掉，讓檔案總管重建。
  • 刪掉 HKCU\Software\QTTabBar\ActivationDate。這個值存在時，AutoLoader 只會在第一次自動啟用分頁列。刪掉後 AutoLoader 確實重跑了，但 A333 一直沒有新的時間紀錄。
  • 打開選項裡的「Enable QTTabBar on every Explorer window (experimental)」，hook 程式庫有載入，畫面上還是什麼都沒有。
  • 列舉檔案總管的子視窗：我檢查到的 ShellTabWindowClass > WorkerW > ReBarWindow32 不是隱藏，就是高度為 0，裡面找不到任何 WindowsForms 視窗。

查到這裡，我仍沒能讓這台的分頁列顯示出來。我推測 26200.9457 的檔案總管已經不再顯示舊式的 band 容器，但手上的紀錄證明不了這一點。

社群還有別的路。#429 有人回報，他在 26200.8037 用 QTTabBar 2048 Beta2，搭配 Windhawk 的「Classic Explorer navigation bar」模組（設成 Classic ribbon UI (no tabs)），再用 ViVeTool 停用 57048216 和 57048237，可以用，但分頁列只能放在視窗底部。#432 另一位留言者刪過 Overrides\8 和 Overrides\15 底下的機碼，也裝了 Windhawk，能叫出側邊列和底部列，但關掉檔案總管後就重置。也有人用 ExplorerPatcher、StartAllBack 換回 Win10 風格的檔案總管。這些我都沒試。

我要的其實只是預覽

QTTabBar 我用最多的是懸停預覽：滑鼠停在檔案上，圖片、影片、文字就浮出來。三月它的預覽功能壞掉時，我已經用 AI 寫過一個替代品 HoverPeek（當時的經過寫在這篇）。這次分頁列也沒了，我決定不再跟檔案總管的內部結構搏鬥，把力氣花在自己能控制的工具上。

v1.2 的 HoverPeek，從停下游標到預覽淡入完成，大約 750 到 850 毫秒：固定等 500 毫秒，解碼 100 到 200 毫秒，再淡入 150 毫秒。

我本來以為，光是從檔案總管找出游標下的檔案就很花時間，量起來只要 6 到 9 毫秒（UI Automation 加 Shell COM）。真正浪費的是圖片：先解出全解析度，用高品質濾鏡縮小，再編成 PNG 交給 WPF，WPF 又把 PNG 解一次。那 500 毫秒的等待，期間也什麼事都沒做。

這次重構跟三月一樣，大部分程式碼是 Claude Code 寫的，v1.3 的 commit 上看得到它的 co-author。改了三件事：

  • 等待期間就先開工：游標停穩 60 毫秒就在背景找檔案、解碼，滿 400 毫秒才顯示預覽，這時多半已經算好了。同一個檔案的並行請求共用同一次解碼；檔案沒改、結果還在最近 24 筆快取裡的話，移回去後滿 400 毫秒就直接用快取結果，不必再解碼。
  • 縮小解碼：JPEG 可以在解碼階段就以 1/8、2/8……的比例縮小，不必先解出全尺寸。縮好的像素直接交給 WPF，不再繞一圈 PNG。我測的圖片解碼流程快了 2.4 到 13 倍。
  • 先拿 Windows 的縮圖頂著：呼叫 IShellItemImageFactory 時帶 SIIGBF_THUMBNAILONLY 和 SIIGBF_INCACHEONLY，只要縮圖、只查 Shell 既有的快取，不要求它現做。Windows 已經有快取縮圖時，我量到取圖約 5 到 15 毫秒，清晰版好了再換掉。

淡入時間也從 150 毫秒縮到 60 毫秒。從停下游標到淡入完成的整段時間，我沒有用同一個口徑重新量測，上面都是分段的數字。

縮小解碼有一個坑。SkiaSharp 的 GetScaledDimensions 回傳的是「最接近」的級距，可能比你要的還小：6000px 的照片要縮到 800px，最接近的是 1/8，也就是 750px。小於目標時直接退回全尺寸解碼，一張 8MB 的 JPEG 要 112 毫秒；往上找一級（2/8）只要 67 毫秒。這是 benchmark 出現「螢幕縮放 100% 反而比 150% 慢」才抓到的：

用了一陣子才爆出來的三個卡死

v1.3 發出去，用了不到一天就卡死了，接著修出 v1.3.2。三個問題都是實際用到才遇上的。

一行 104 萬字元的 JSON。 壓縮過的 JSON、JS 常常整份只有一行。預覽讀的是前 1MB，讀檔只要 2 到 4 毫秒，卡住的是 AvalonEdit 和 TextBox 在 UI 執行緒上排版這一行。實際卡死的是兩個壓縮過的 JSON，我在不顯示視窗的情況下用同樣兩個檔案重跑排版，花了 59.9 秒。要限制的是行長，不是讀取量：現在每行最多顯示 2000 字元，超過就截斷並標示原因。

2.3MB 的 GIF 吃掉 7.6GB 記憶體。 這個 GIF 是 1080p、300 格，存在磁碟上只有 2.3MB。舊版用的 WpfAnimatedGif 會在 UI 執行緒一次解碼、合成所有影格，實測記憶體用到 7.6GB，UI 卡了 19.9 秒。改成背景用 Skia 逐格解碼、縮到顯示尺寸再交給 UI 之後，同一個檔案的最長卡頓降到 28 毫秒，記憶體只多了 4MB。

HoverPeek 一卡，整台電腦的滑鼠跟著頓。 低階滑鼠 hook（WH_MOUSE_LL）的回呼在安裝它的執行緒上執行，Windows 每次滑鼠移動都要等它返回。原本 hook 裝在 UI 執行緒，排版一卡住，滑鼠事件也被拖住。微軟文件寫得很直接：回呼超過 LowLevelHooksTimeout，Windows 7 以後會直接把 hook 移除，程式不會收到任何通知。hook 被移除後，HoverPeek 就收不到觸發預覽的滑鼠事件，直到重新安裝 hook。同一份文件也建議把低階 hook 放在專屬執行緒上，耗時的工作交出去，讓回呼盡快返回。現在 HoverPeek 就是這樣做：

（實際檔案還有安裝失敗時把例外丟回呼叫端、逾時檢查和 Dispose，這裡只留骨架。）

UI 卡住時，日誌也寫不出東西，因為卡住的就是要寫日誌的那條執行緒。所以 v1.3.2 加了一個看門狗執行緒，每秒排一個小工作給 UI，超過 3 秒沒被執行，就記下當時正在預覽的檔案路徑。

回頭看

QTTabBar 的懸停預覽，是我用過最順手的檔案總管功能。這次連分頁列都救不回來，有點可惜。

追的過程不算白費。下次檔案總管又有東西消失，我會先看 Ext\Stats 的最後一筆時間紀錄，再看 Overrides 底下有沒有更高優先權的設定。但再追下去，就是跟每個月的累積更新拔河。

HoverPeek 也靠 UI Automation 和 Shell COM 判斷游標下是哪個檔案，哪天微軟改了這一層，它一樣會壞。差別在於，到時候修的人是我。
