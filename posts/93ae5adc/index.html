老闆丟一句「這個報表，越快越好」，你打開資料表一看——好幾千萬筆。這時候用對工具跟用錯工具，差的不是幾分鐘，是幾個小時。

SQL Server 匯出 CSV 最常用的三個工具是 SQLCMD、BCP、SSIS。網路上很多範例其實是把它們的角色搞混的：最典型的就是把 bcp 命令當成 T-SQL 字串丟進 sp_executesql，抄回去一跑就語法錯誤。這篇把每個工具的定位講清楚，範例全部以可實際執行為前提，並附上分批匯出大型資料的正確寫法。

三個工具，三種角色

先把定位搞對，後面才不會誤用。

BCP（Bulk Copy Program）是獨立的命令列工具，走大量複製 API，常被選來處理單純的大量匯出。它不是 T-SQL，是在作業系統的命令提示字元執行的 .exe；到底比 SSIS 快多少，仍要用自己的資料量、磁碟與網路環境量測。

SQLCMD 也是命令列工具，主要拿來跑 .sql 指令稿、做自動化排程。它本身不是高效能匯出引擎——真要快速匯出大量資料，多半還是在 SQLCMD 指令稿裡呼叫 BCP。

SSIS（SQL Server Integration Services）是視覺化 ETL 平台，強在「匯出過程中要做轉換」：欄位對應、編碼轉換、異常過濾、條件分流。代價是設定與維護成本高。

工具 角色 強項 弱項
BCP 命令列匯出引擎 適合大量、單純匯出 彈性低、特殊處理麻煩
SQLCMD 指令稿 / 排程外殼 自動化、整合方便 不是匯出引擎，常需搭 BCP
SSIS 視覺化 ETL 複雜轉換、流程整合 設定複雜、維護成本高

效能上，BCP 通常是純匯出的第一個基準候選，但 SSIS 經正確設定後不必然比較慢。結果取決於來源查詢、磁碟 I/O、網路、驅動版本、資料流緩衝與轉換內容；用同一份資料和目的地實測再選，不照搬別人的秒數。

BCP 實戰

BCP 是這三者裡最該先學會的，因為大型匯出最後幾乎都會落到它身上。

關鍵旗標：

  • queryout：表示來源是一段查詢（如果是整張表用 out）。
  • -c：字元格式輸出。
  • -t","：欄位分隔符號設為逗號。
  • -S：伺服器名稱。
  • -T：使用 Windows 整合驗證。BCP 也支援 -U/-P，但把密碼寫進腳本或命令列可能洩漏到版控、程序資訊與作業記錄；排程優先使用受控的整合驗證帳號，不在指令列放祕密。

-T 跟 -U/-P 擇一，不要同時給。

效能相關旗標

  • -a 16384：要求使用 16 KB 網路封包。調大不保證變快，還要看伺服器設定、網路與驅動支援，先用同一批資料做 A/B 測試。

-b 是匯入時控制每批提交列數的選項，對 queryout 匯出沒有這個交易批次效果，所以不放進上面的命令。

這裡要點名一個網路上常見的幻覺旗標：**bcp 沒有 -O 這個選項**。保留識別欄位（identity）值的旗標是 -E，而且 -E 只在「匯入（in）」時才有意義——把資料檔裡的 identity 值原樣寫回去；對 queryout 匯出根本用不到。如果你看到範例寫 -O -- 保持身份值，那是錯的，照抄會直接報錯。至於 -h "TABLOCK" 這類載入提示，同樣是匯入時的最佳化，匯出時不適用。

BCP 要由作業系統啟動

bcp 是命令列程式，不是 T-SQL，不能交給 sp_executesql。也不建議把含查詢、路徑與分隔符號的複雜命令塞進 xp_cmdshell：除了擴大攻擊面，xp_cmdshell 對 command_string 的雙引號組數有限制，常見 BCP 命令很容易踩線。正式流程用 SQL Server Agent CmdExec／PowerShell step 或外部排程器，由受控作業系統帳號執行；輸出路徑位於執行 BCP 的主機，該帳號必須有目錄寫入權。

大型資料分批匯出

幾千萬筆一次匯出，記憶體與失敗重試都是麻煩，分批比較穩。重點是分批的邊界要組進實際送給 bcp 的命令字串裡——因為 bcp 啟動的是獨立的新連線，看不到你在外層 T-SQL 宣告的變數。換句話說，你不能寫 WHERE ID BETWEEN @StartID AND @EndID 然後期待 bcp 認得 @StartID；得在組命令時就把數值字串化拼進去。

注意這裡是用 SortID BETWEEN n AND n 的「ID 值區間」切批，而不是 ROW_NUMBER()。從實際 MIN 跑到 MAX，0、負數與 identity 缺口都不會因此漏列；缺口只會讓某批筆數少一點。正式流程還應產生 manifest，記錄每批邊界、輸出檔、BCP 結束碼與來源筆數，合併前核對總筆數。上述 View 把 NULL 轉成空字串，因此匯出後無法區分兩者；若業務需要區分，必須另外約定 NULL 表示法。

還有一個比切批更重要的前提：每個 BCP 都是不同連線，來源持續寫入時，各批不會自動共用同一個時間點。需要一致快照時，先暫停寫入、從唯讀快照／副本匯出，或在已評估 version store 的前提下，用單一 SNAPSHOT transaction 將本次資料 SELECT INTO 一張帶 run ID 的 staging table，再讓所有 BCP 只讀這張不再變動的表。manifest 只能發現筆數異常，不能把跨批次的新增、刪除或修改修回同一時間點。

BCP 會覆寫同名目的檔。正式流程先輸出到本次 run 的暫存目錄，確認所有批次與 manifest 後再原子改名／切換；不要直接蓋掉上一份已驗證的成品。

SQLCMD 的正確定位

SQLCMD 的價值在指令稿化與排程，不在匯出效能本身。

指令稿變數

要記得 :setvar 只是宣告 sqlcmd 指令稿層級的變數，本身不會對 SQL Server 做任何設定。它能在後續用 $(OutputPath) 這種 $() 語法被展開——但這套展開只在 sqlcmd 環境裡有效。把 $(StartID) 寫進一段準備交給 bcp 的字串、又不是在 sqlcmd 跑，它不會展開，會原樣留著變成壞檔名。

這段 SQLCMD 指令稿適合做匯出前的資料準備、驗證與失敗即停止；實際 BCP 由上一節 PowerShell 或 Agent CmdExec step 啟動，並以程序 exit code 判斷成敗。不要期待 :on error exit 自動接住另一個作業系統程序的錯誤。

別把 -m 當記憶體參數

網路上反覆出現一個錯誤，要特別澄清：

sqlcmd -m 是「錯誤訊息嚴重性等級門檻」（error level），只有嚴重性大於等於這個值的訊息才會輸出。它的有效範圍是 -1 到 25，寫 65535 直接超出範圍。要包含資訊性訊息，官方命令列語法寫成 -m-1，負號前不能插入空格。它跟記憶體一點關係都沒有——SQL Server 的記憶體上限是用 sp_configure 'max server memory' 設定的。

-b 才是有用的：遇到錯誤時讓 sqlcmd 以非零代碼結束批次，方便排程判斷成敗。

SSIS 實戰

SSIS 適合匯出途中要轉換的場景。它的設定主要在圖形介面拉元件，這裡只點幾個容易抄錯的地方。

緩衝區屬性屬於資料流程

效能調校常碰到這幾個屬性，但它們是資料流程工作（Data Flow Task）的屬性，在設計工具的屬性視窗設定，不是隨便在某段腳本裡賦值的變數：

  • DefaultBufferMaxRows：每個緩衝區的最大列數（預設 10000）。
  • DefaultBufferSize：每個緩衝區的位元組大小（預設約 10 MB）。
  • BufferTempStoragePath：緩衝溢出時的暫存路徑。

來源查詢要列出固定欄位，避免資料表新增欄位後讓 Flat File Destination 的欄位對應整批位移。也別用 NOLOCK 當匯出加速器：它可能讀到未認可資料、漏列或重複列，最後得到一份能開啟卻不可信的 CSV。

匯出時間長、又不想讓讀取阻塞寫入時，優先評估在資料庫層啟用 READ_COMMITTED_SNAPSHOT，或在工作流程中使用 SNAPSHOT isolation。這兩種方式都要先確認 tempdb 容量與版本儲存壓力；不能在沒評估的正式資料庫直接切換。MAXDOP 4 也只是示意上限，實際值要看 CPU、同時工作負載與查詢計畫，並非固定最佳值。

編碼：UTF-8 沒那麼單純

匯出 UTF-8 CSV 常見寫法是 -C 65001，但它只控制編碼，不會補上 CSV quoting。查詢仍要使用前面的匯出 View：

  • 官方一般 bcp 文件以 SQL Server 2016 起支援 code page 65001 說明；KB3136780 另記載 SQL Server 2014 SP2 加入相關支援。最後以實際執行的 bcp client 為準：先跑 bcp -v 記錄版本，再用含中文、emoji、逗號、換行與雙引號的小樣本往返驗證。
  • UTF-8 是 8 位元編碼，要搭 -c（字元格式）使用，不要用 -w（-w 是 UTF-16 寬字元）。
  • bcp 輸出的 UTF-8 檔不含 BOM，某些下游程式（特別是 Excel 直接開）可能因此判錯編碼把中文變亂碼。

所以單寫 -C 65001 不保證拿到下游都吃得乾淨的 UTF-8。版本不夠新、或下游要 BOM 的話，得另外處理。不確定環境支援度時，先在小樣本上驗證再放上生產。

怎麼選

把工具對到任務上，大致是這樣：

  • 純匯出、量大：先把 BCP 納入基準測試；再依實測與維運需求和 SSIS 比較。
  • 要排程、要串流程：SQLCMD 當外殼，內部呼叫 BCP。
  • 匯出途中要轉換：SSIS。欄位對應、編碼轉換、異常過濾一次到位。
  • 大量資料 + 複雜轉換：先比較單一 SSIS Data Flow 與「BCP 落地後再轉換」兩條路。後者多一次完整磁碟 I/O、暫存空間與故障點，只有需要保留中間檔、分段重跑，或實測確實較快時才值得採用。

收尾

三個工具裡，BCP 值得先納入大量匯出的基準測試。最重要的是別混淆角色：BCP 是作業系統命令，SQLCMD 適合執行資料庫前置／收尾腳本，SSIS 負責需要轉換與流程治理的 ETL。分批匯出還要處理一致性快照、exit code、manifest、暫存檔與成品切換，才不會產出表面成功、內容缺批的 CSV。
