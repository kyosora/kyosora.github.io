密碼或大檔推上 Git？用 git-filter-repo 重寫歷史並清理殘留

把密碼、API 金鑰或一個幾百 MB 的檔案不小心 commit 進 Git、又推上遠端——這時候光 git rm 沒用，它還躺在歷史裡，任何人 clone 下來都翻得到。要真正清掉，得重寫 Git 歷史。

Git 內建的 filter-branch 能做，但它慢、容易出錯，官方文件自己都標示不建議用了。目前官方文件普遍建議改用 git-filter-repo。

什麼是 git-filter-repo

用 Python 寫的開源工具，專門重寫 Git 歷史，是 filter-branch 的官方推薦替代品。比起 filter-branch，它快上一個量級、命令更直覺，還會自動做安全檢查（例如要求你在乾淨的 clone 上操作）。

安裝

情境一：移除意外推送的敏感資料

--invert-paths 是「保留以外的全部」，配合 --path 就是把這些路徑從整個歷史刪掉。

但有件事要先講清楚：把檔案從歷史移除，不等於敏感資料安全了。 只要它曾經推上遠端，就要當作已經外洩。先撤銷金鑰，再重寫歷史；順序反過來只是在延長可被使用的時間。

  • 立刻撤銷並更換所有外洩的密碼、金鑰
  • 檢查其他分支、fork、CI 日誌是否也有
  • 之後用 .gitignore + pre-commit hook（如 git-secrets）擋住下一次

清歷史是止血，換金鑰才是真正解決。

情境四：把子目錄變成根目錄

常用在從 monorepo 拆出一個獨立專案，連歷史一起搬走。

用之前要知道的幾件事

  1. 在全新的 clone 操作，並讓所有協作者暫停 push。原始 clone 留著當離線備份，但不要再把舊歷史推回遠端。
  2. 重寫後 commit ID、tag 簽章與 PR diff 都可能改變，先盤點 CI、部署與自動化是否依賴舊 SHA。
  3. 先用 git log --all -- 路徑 或 git log -S'敏感字串' --all -p 驗證真的清乾淨。
  4. 更新遠端時要覆蓋所有可寫 refs，敏感資料清除通常使用 git push --force --mirror origin，不能只 force push 目前分支。
  5. 不用手動下 git gc。git-filter-repo 跑完會 expire reflog、repack 本機物件；遠端主機、fork 與其他人的 clone 仍要另外處理。

GitHub 的 refs/pull/* 是唯讀，force push 不會清掉 PR 參照與快取頁面。憑證已撤銷但內容仍屬敏感資料時，可依 GitHub 官方清除流程 聯絡 Support；現有 fork 與協作者 clone 也必須各自清理或重新 clone。

整個 git-filter-repo 的世界都是位元組——路徑、email、訊息、檔案內容全是 bytes，這點一致。

跟 filter-branch 比

特性 git-filter-repo git filter-branch
速度 快 慢
上手難度 簡單 複雜
新 clone 安全檢查 有 無
官方態度 推薦 不建議使用

收尾

git-filter-repo 解決的是「重寫 Git 物件」，不會替你撤銷憑證，也碰不到別人的 clone、fork 與平台快取。我會先換金鑰，再停掉團隊 push，最後才做全 refs 重寫。callback 的 bytes 是操作上的坑；把本機跑成功誤認成資料已從世界上消失，才是資安上的坑。
