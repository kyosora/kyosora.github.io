別急著關掉 TLS 1.2：升級 TLS 1.3 前該懂的 Windows 相容性真相

資安弱掃跑完，報告上一條紅字：偵測到過時的 SSL/TLS 協定。很多人看到就把 TLS 1.0、1.1、1.2 全關掉，只留 TLS 1.3——想說版本越新越安全。

問題就出在這：弱掃從來沒叫你關 TLS 1.2。把 1.2 一起關掉、只留 1.3，在 Windows 伺服器環境幾乎一定出事——網站連不上、SQL Server 連不上、舊的內部系統全掛。下面拆解為什麼，以及正確的做法。

先搞清楚：弱掃到底要你關什麼

弱掃報告寫「過時的 SSL/TLS 協定」，指的幾乎都是 SSL 2.0/3.0 和 TLS 1.0、1.1。這幾個有已知的結構性弱點（POODLE、BEAST 那一掛），該關。

TLS 1.2 不在這個清單裡。它到現在仍然安全、主流、被廣泛支援。常見的合規型弱掃通常不會要你停用 TLS 1.2。

合規也不能只看版本號。PCI DSS 的核心措辭是使用「強式密碼學」，PCI SSC 已明確把 SSL／early TLS 排除在外，並長期建議遷移到 TLS 1.2 以上；它沒有普遍要求所有環境只能使用 TLS 1.3。實際是否合規仍要一起看 cipher suite、系統用途與適用版本，不能把一句「1.2 或更高」當成完整稽核規則。

為什麼「只留 1.3」會弄掛系統

撇開合規不談，純粹從技術可行性看，在 Windows 伺服器環境只留 TLS 1.3 也行不通。一層一層看。

作業系統這層

TLS 1.3 在 Windows 的 Schannel 裡，只有 Windows 11 和 Windows Server 2022 之後才原生支援。Windows Server 2019、2016 連這個協定都沒有。

所以如果你的機器是 Server 2019，在登錄檔裡「啟用 TLS 1.3」是沒有意義的——系統根本不會拿它協商。你以為開了，其實沒開；接著又把 1.2 關了，這台機器一個現代協定都不剩。

資料庫這層

SQL Server 更要小心。TLS 1.3 的基本條件包含 SQL Server 2022 CU1 以上、Windows Server 2022、TCP/IP、有效的伺服器憑證，以及支援 TDS 8.0 的驅動程式；用戶端採 Encrypt=Strict 才會走 TDS 8.0。少看驅動程式或憑證，伺服器版本升上去仍可能連不上。SQL Server 2019 與更早版本不支援 TLS 1.3。

更關鍵的一點：就算 SQL Server 2022 已經支援 TLS 1.3，微軟文件仍明確寫著：SQL Server 的衛星服務（satellite services）啟動時需要 TLS 1.2，不要在這台機器上停用 TLS 1.2。文件沒列出是哪些服務，所以別去賭哪個服務沒差。在有 SQL Server 的環境裡，TLS 1.2 基本上動不得。

應用程式執行環境這層

往上到應用層，同樣卡版本：

  • Java 要 JDK 11 以上才預設支援 TLS 1.3。Java 8 從 8u261 起才補進 TLS 1.3，但當時用戶端預設關閉，要用 -Djdk.tls.client.protocols="TLSv1.3,TLSv1.2"，或在程式裡指定 TLSv1.3 的 SSLContext／SSLParameters 才會開，之後的更新才改成預設開啟。Java 8 程式要連只開 1.3 的伺服器，先確認實際的 update 版本和啟動參數。
  • .NET Framework 依賴 Windows Schannel，不能只看 Framework 版本。微軟目前的相容表顯示：Windows 10 上最高仍是 TLS 1.2；Windows 11 上，目標 .NET Framework 4.6.2 以上可由作業系統協商 TLS 1.3。應用程式若把 SecurityProtocol 寫死成舊版本，作業系統支援也救不了。

只要環境裡還有一個沒跨過這條線的元件，「只留 1.3」就會在那裡斷掉。

正確的做法：淘汰舊的，守住 1.2

目標講清楚：要關的是 SSL 和 TLS 1.0、1.1；要保留的是 TLS 1.2；TLS 1.3 是有條件才加開，不是拿來取代 1.2。

真正要停用 1.0/1.1 時，得在每個協定的 Server 和 Client 兩個子機碼都寫兩個 DWORD 值：Enabled = 0、DisabledByDefault = 1。手動改登錄檔很容易漏，型別建錯（建成字串）設定還會無效。我的建議是直接用 IIS Crypto 這類工具套用 best practice 範本，它會把協定和 cipher suite 一起處理好，比手刻登錄檔安全。

這裡有個容易忽略的坑：關掉舊協定後，仍可能因為兩端沒有共同的 cipher suite 而握手失敗。你以為是 TLS 版本問題，其實是 cipher 沒交集。IIS Crypto 可以一起調整協定與 cipher，但套範本前仍要保留匯出檔並在測試環境驗證，別把「Best Practices」按鈕當成所有舊系統都適用的答案。

執行順序我會這樣排：

  1. 盤點。列出所有要連線的系統和它們的 OS、資料庫、執行環境版本，確認誰支援到哪。沒盤點就動手是最常見的災難來源。
  2. 備份。改之前先 reg export 把 SCHANNEL 整棵匯出，出事能立刻還原。
  3. 測試環境先跑。複製一份實際環境，關掉 1.0/1.1、保留 1.2，把關鍵流程跑一遍。
  4. 分批上。低風險系統先做，核心系統最後，每改一台測一台。

改完怎麼確認有沒有生效？對外網站可以用 SSL Labs 掃一遍看實際協商到哪個版本；內網服務用 openssl s_client -connect 主機:443 -tls1_2 指定協定測試，能握手成功就代表這個版本還通。

反過來測舊協定有個陷阱：OpenSSL 3.x 常因為用戶端自己的安全等級或系統加密原則，不肯送出 TLS 1.0／1.1，在用戶端就失敗（例如 no protocols available），根本沒送到伺服器。這種「失敗」證明不了伺服器已經關掉 1.0。要先把用戶端的安全等級降下來再測：

就算確定錯誤是伺服器回的，也要分清楚：protocol_version 才直接代表版本被拒；handshake_failure 也可能只是 cipher 沒交集。有些發行版的系統加密原則連降等級都開不了，所以我會再用 nmap --script ssl-enum-ciphers -p 443 主機 交叉確認，它自己組 TLS 握手，一次列出伺服器接受的協定與 cipher。

TLS 1.3 什麼時候加開？等 OS、資料庫、驅動程式與應用框架都跟上，再把 1.3 和 1.2 並存。握手測試要涵蓋網站、排程、備份、SSIS／SSAS 與舊用戶端，不能只用瀏覽器連首頁就宣布完成。

收尾

現階段在 Windows 伺服器環境，我會把目標定成淘汰 1.0／1.1、守住 1.2，再視整條連線鏈加開 1.3。SQL Server 官方目前仍要求保留 TLS 1.2 給衛星服務使用，因此「只留 1.3」甚至不該是通用終點。看到弱掃報告先確認它掃到哪個端點、哪個協定與哪組 cipher，再決定要關什麼。
