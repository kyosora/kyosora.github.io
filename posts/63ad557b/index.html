MinerU 4.0 安裝教學：4GB 顯卡筆電把繁中 PDF 表格轉成 Markdown

發表於2026-10-08|AI工具實戰工具與生產力
|總字數:3.2k|閱讀時間:11分鐘

做政府案常收到一種東西：機關給的 PDF 統計表，要把裡面的數字倒進資料庫，或丟給 LLM 讀。我之前都用 markitdown，文字型 PDF 還行，遇到掃描檔就沒輒。

今天翻 Hugging Face Papers 的熱門榜，看到 MinerU2.5 這篇論文還掛在上面，repo 已經 8 萬多顆星，而且出到 4.0 了。問題是我的筆電只有一張 GTX 1650 Ti，4GB 顯示記憶體，README 寫高品質檔位要 8GB。

所以這篇主要想回答一件事：4GB 顯卡的筆電，能不能把繁體中文 PDF 的表格轉成欄位沒有錯位的 Markdown。整個過程我讓 Claude Code 動手，我在旁邊看、做決定。

環境先講：Windows 11、Git Bash、uv 0.6.11、Python 3.12，對照組是 markitdown 0.1.8。下面的指令都是在 Git Bash 裡跑的。

裝之前先被擋了兩次

第一次是 README。Claude Code 讀安裝說明時停下來回報：裡面有一段叫你「複製給你的 agent」的訊息，內容是要 agent 執行 npx skills add 裝一個全域 skill，然後在全域記憶寫入一條偏好，大意是「以後凡是要讀 PDF、圖片、Office 文件，一律優先用 mineru」。

這段沒有藏起來，是寫給人看的安裝捷徑。但它要改的是 agent 的長期記憶，裝完之後每個專案讀文件都會先走它。我只是想試一個工具，沒打算讓它變成預設值，所以這段跳過，只裝 PyPI 套件。

第二次是掃描。我用 SkillSpector 掃了整個 repo，結果是 100 分、CRITICAL、DO NOT INSTALL，343 筆命中。數量最多的幾類讀下來，是拿 skill 的尺去量一個 1,149 個檔案的 ML 專案：

  • 48 筆「特權容器」全在國產加速卡的 Docker 教學文件裡
  • 16 筆「混淆程式碼」全是內附的 pdf.js 壓縮檔
  • 27 筆在單元測試和設計文件

剩下的是 eval、subprocess 這類寫法、依賴套件的漏洞公告、讀環境變數等等，我沒有每一筆都看完。我決定往下追的是遙測，因為它跟「裝了會不會往外送東西」直接相關。安裝後的 mineru/doclib/telemetry/service.py 有這幾行：

同意狀態有三種：未設定、啟用、停用。被註解掉的那行是「沒啟用就不送」，現在生效的是「明確停用才不送」。同一個檔案裡負責累計統計的 _record 用的也是同一個條件，往下則是組出 payload、送到 constants.py 寫死的 https://mineru.net/metrics/v2/metrics。

所以照 4.0.10 的程式碼讀，沒回答過同意提示的人，統計一樣會累計、一樣會進到上傳那段。註解寫著 prerelease 之後會改回來。要說清楚的是，這是讀程式碼的結論：我沒有啟動服務去抓封包，也沒有逐行驗證它聲明的「不收文件內容、檔名、路徑」。

（這算一個彎路：我本來想裝完直接跑 mineru telemetry disable 了事，結果它回「本地 mineru 服务未运行」。要先啟動常駐服務才能關遙測，這個順序有點妙。）

兩個指令長得很像，差在有沒有常駐服務

卡在遙測那裡才搞懂，4.0 裝完會有兩個主要指令：

指令 用途 常駐服務 遙測
mineru 文件庫：掃描、快取、搜尋、給 agent 分頁讀 要 有
mineru-kit 單純把檔案轉成 Markdown 不用 套件的 kit/ 目錄裡搜不到 telemetry

我只要轉檔，所以全程用 mineru-kit，沒啟動過服務。跑完去看資料目錄，只有模型和一個設定檔，沒有產生遙測用的資料庫。

安裝本身很快：

我裝到的是 MinerU 4.0.10，之後的版本行為可能不同。兩個套件一起裝了 41 秒，虛擬環境約 700MB。模型下載 1 分 20 秒，共 2.0GB：一包 819MB 的 ONNX 小模型（版面、表格、OCR），一包 1.2GB 的 GGUF 視覺語言模型。

mineru-kit models show 會告訴你它幫這台機器選了什麼：

README 寫的 8GB 門檻是 PyTorch 路線。我這台自動被分到 ONNX 加 llama.cpp，那條路線的說明是「CPU 可跑」。

同一份 PDF，四種轉法

測試檔用臺北市政府主計處公開的〈114 年 9 月臺北市物價變動概況〉新聞稿，9 頁，前 5 頁是內文和折線圖，後面 4 張統計表。表格有合併儲存格、兩層表頭、直書的分類標籤，很典型的公部門格式。

MinerU 4.0 有四個檔位，我跑了本機能跑的三個，加上 markitdown 當對照：

怎麼算轉得好不好？這四張表的資料列都是「一個名稱加九個數字」。我讓 Claude Code 寫了一小段腳本，數每個輸出裡「九個數字各自落在獨立儲存格」的列有幾列，四張表合計 89 列。MinerU 輸出的是 HTML 表格、markitdown 是管線表格，兩種各寫一個解析，判準相同。

這個數字能證明的事很有限：它只確認一列裡有九格各放一個數字。欄位有沒有對到正確的表頭、數字有沒有抄錯、列名對不對，它都抓不到，要另外核對。MinerU 的統計還多一條限制（非數字的欄位只能有一到兩格），markitdown 那邊沒加，所以對 markitdown 是比較寬鬆的。

工具／檔位 耗時 九個數字各佔一格的列（共 89 列） 發生什麼事
markitdown 22 秒 57 表格有出來，但表 1 多出一堆空欄；折線圖的座標數字被當成內文灑了一地
flash 40 秒 41 表 1 整張沒被認成表格，變成用空白對齊的純文字
basic 33 秒 52 四張表都認到了，但表 1 的 48 列只有 11 列過關
standard 107 秒 89 89 列都過關

basic 在表 1 壞得很有特色。那張表左邊有一欄直書的「基本分類」跨了幾十列，basic 把整組列名擠進同一格：

數字全黏在一起，這種輸出丟進資料庫只會更慘。standard 多跑一個視覺語言模型（log 裡多一段 VLM Predict），同一張表的欄位就分開了：

過關不代表數字對。表 2 的 20 列，Claude Code 把原頁轉成圖片逐格比對，180 個數字全對。這一步是它做的，我沒有自己再對一次；其他三張表也沒有逐格核對。

中間有一段虛驚。standard 的輸出裡，下跌項目那列寫的是「平均漲幅(%)」，其中一格是 -4.1，旁邊都是兩位小數。我第一個念頭是視覺模型在亂改數字，這種錯最可怕，因為看起來很合理。回頭放大原始 PDF，原檔就是寫「平均漲幅」，那格也真的是 -4.1。模型照抄了，是我多疑。

數 MinerU 輸出的腳本長這樣。這是整理過的版本，少了前面說的那條額外限制；markitdown 的版本是把 | 開頭的行切開，套同一個數字判準。

MinerU 的表格輸出是 HTML 的 <table>，帶 rowspan 和 colspan，所以合併儲存格的結構留得住。Markdown 的管線表格做不到這點。

4GB 顯卡撐得住嗎

這份文件、這台機器，撐得住。跑 standard 時我讓它每秒記一次 nvidia-smi：

  • 開跑前，其他程式已經佔掉 1,288 MiB
  • 尖峰 3,429 MiB，GPU 使用率最高 98%
  • 沒有出現記憶體不足

整張卡的用量多了大約 2.1GB，這是前後差值，模型和推論暫存都算在裡面。每秒取樣一次也可能漏掉更短的尖峰，頁面更大或更複雜時我沒測。瀏覽器開很多分頁、已經佔掉 2GB 以上的話就會很擠，跑之前關一關。

速度是另一回事。9 頁花 107 秒，其中模型推論 88 秒，換算一頁快 10 秒。幾十頁的文件可以接受。一千頁照比例推算大約要三個小時，這是線性外推，長文件我沒實測。比較實際的做法是用 --pages 只挑有表格的頁：

掃描檔才是分水嶺

公部門另一種常見的 PDF 是掃描檔，整頁是一張圖。我把測試檔的第 1、6、7 頁轉成 150 dpi 的純圖片 PDF，再跑一輪。

工具／檔位 耗時（3 頁） 結果
markitdown — 輸出 0 bytes
flash 26 秒 內文有 OCR 出來，表格 0 張
basic 32 秒 2 張表，68 列裡 44 列過關
standard 146 秒 2 張表，68 列都過關

OCR 的部分，我拿第一頁開頭一段和原檔的文字層比對，只比中文字和數字，共 300 個字。三個檔位都是 0 個錯字。

這個結果的適用範圍很窄。樣本只有 300 字；而且這是電腦產生的 PDF 直接轉成圖，沒有真實掃描會有的歪斜、底色和雜訊。實體掃描件、手寫、傳真品質的我都沒測。

就這次測的版本來說，兩個工具的差別在這裡：有文字層的 PDF，markitdown 很快，但表格要倒進資料庫還得清；沒有文字層的，它這次直接交白卷。

還沒解決的幾件事

standard 也沒有到完美，用之前要知道這幾點。

直書的分類標籤會黏進列名。 表 2 左邊直書的「商品性質別」五個字，被拆開黏到各列前面，「外食費」變成「性外食費」，「服務類」變成「商服務類」。數字沒錯，但列名要自己清，文字版的 basic 和 standard 都一樣。

全形標點被換成半形。 原檔有 44 個全形冒號「：」，MinerU 三個檔位的輸出全變成半形 :。拿來餵 LLM 沒差，要原文照登就得注意。

偶爾冒出 LaTeX。 掃描版有一處「下跌0.56%」被寫成 $0.56\%$，整份只有這一處。

圖片是 base64 內嵌。 9 頁轉出來的 .md 有 800KB，扣掉圖片的實際文字只有 2 萬字左右。把檔案當純文字整份送給 LLM 的話，大部分 token 會花在 base64 上，先把 data:image 那幾段濾掉。

另外兩件跟品質無關：CLI 的訊息是簡體中文；授權是自訂的 MinerU Open Source License，以 Apache 2.0 為底加了附加條款，要放進商用產品前自己讀一遍。

我之後會怎麼用

我的結論是分流，不會全部換掉：

  • 只要內文、不在乎表格的 PDF，繼續用 markitdown，快，裝起來也小
  • 要拿表格裡的數字，或者檔案沒有文字層，用 mineru-kit parse --tier standard，挑頁跑，列名自己再清一次
  • flash 和 basic 我大概不會用。basic 省下來的一分鐘，我寧可不要花在清表格上

帶常駐服務的 mineru 文件庫，等遙測那行註解改回來再說。

這次花最多時間的環節是決定要不要裝，轉檔本身反而很快。
