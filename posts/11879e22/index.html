SQL Server 日期轉換失敗？先查 DATEFORMAT

發表於2026-09-18|前後端開發資料庫
|總字數:1.8k|閱讀時間:6分鐘

9 月 17 日修派工單列表，本機開得好好的，測試機一進頁面就報「查詢派工單失敗」。連日期都還沒選。

翻後端紀錄，真正的錯誤是這句：

沒選日期也會碰到日期轉換，因為前端會自動補當年度的查詢區間。其中一段條件長這樣：

OccurTime 欄位是 datetime，比較時 SQL Server 需要把右邊的字串轉成日期。12 月 31 日這個值沒問題，解析規則卻會讓轉換失敗。

換成連字號，一樣失敗

排查紀錄裡最值得留下的是這組對照：把斜線換成連字號，甚至拿掉時間，都沒過。最後差別落在日期與時間中間那個 T。

當時開發環境的連線使用 ymd，測試環境卻是 dmy。對這次的 datetime 轉換來說，同一串年月日會得到不同結果。

下面是整理文章時重跑的測試。只處理常數，不需要建立資料表。請用一條獨立的測試連線執行，跑完關閉；SET DATEFORMAT 會影響這條連線後續的敘述。

這裡用 ISDATE 判斷這幾個字串能不能轉成 datetime，讓失敗項目顯示 NULL，方便放在同一張表比較。它不適合拿來當所有日期型別的通用驗證器。

實測引擎版本是 SQL Server 2022（16.0.1000.6），結果如下：

輸入字串 datetime 轉換結果
2026/12/31 23:59:59 無法轉換
2026-12-31 23:59:59 無法轉換
2026-12-31 無法轉換
2026-12-31T23:59:59 2026-12-31 23:59:59.000
20261231 23:59:59 2026-12-31 23:59:59.000
2026-01-02 2026-02-01 00:00:00.000

最後一列比報錯還麻煩。我想查 1 月 2 日，它會讀成 2 月 1 日，整條 SQL 照樣執行。只拿月、日都小於 13 的日期做測試，還可能以為修好了。

Microsoft 的 datetime 文件 有明列不受 SET DATEFORMAT 與 SET LANGUAGE 影響的字串格式，包括 yyyy-MM-ddTHH:mm:ss[.mmm]。這次統一採用帶 T 的寫法；yyyyMMdd 也是可用的選擇。

這張表的目標型別是 datetime。同樣在 dmy 下，我重跑 CONVERT(date, '2026-12-31') 與 CONVERT(datetime2, '2026-12-31') 都成功。這只能說明這個字串在這兩種型別的結果，不能推成「換成 datetime2 就不受 DATEFORMAT 影響」。斜線格式或其他輸入仍要確認解析規則。

要查出錯的那條連線

遇到本機正常、測試機失敗，很容易開始比資料或比程式版本。這次需要多比一項：連線的日期解析設定。

看結果裡的 language 與 dateformat。如果在 SSMS 開新連線查，只能證明那條 SSMS 連線的設定。要確認應用程式的狀態，得讓診斷敘述在實際出錯的連線上執行，或重現它的登入與初始化設定。DBCC USEROPTIONS 回傳的是目前連線啟用的選項。

登入的預設語言會影響初始日期格式，但連線還能執行 SET LANGUAGE 或 SET DATEFORMAT。後者會覆寫語言帶入的日期順序，所以只看帳號預設語言不夠。Microsoft 的 SET DATEFORMAT 說明 也特別區分：它改的是字串轉日期的解析方式，不會改資料庫裡日期的儲存格式。

這次還有一層干擾。既有資料存取元件會先用 .NET 的 DataTable.Select(filter) 檢查篩選條件。依當時的排查紀錄，這關接受了原本的日期字串，送到 SQL Server 才失敗。

同一份 filter，經過兩套解析規則。前一道檢查通過，沒有替後一道保證什麼。

這次先修共用的日期輸出

原始碼裡也補了一支回歸 scenario，檢查 helper 的輸出、掃描仍自行拼接的日期字面，並呼叫 API 驗證帶 T 的區間能通過 filter 檢查與資料庫查詢。整理本文時，我另用上面的常數查詢重驗 SQL Server 的解析結果；這不等於重跑整個系統的驗收。

能改後端時，直接傳日期參數

如果能調整查詢介面，我會讓前端只送起訖日期，由後端解析、驗證，再以日期型別參數交給 SQL Server。這樣就不用讓資料庫猜日期字串的順序。

例如舊欄位仍是 datetime，可以明確指定 SqlDbType.DateTime。下面是整理過的 .NET Framework 示範，假設已有開啟的 SqlConnection；資料表名稱是示意，並非這次部署的程式碼。

參數的值是 DateTime 物件；如果仍把日期字串塞進字串型別參數，轉換問題可能還在。型別要和欄位及需求配合，datetime2 欄位則可使用 SqlDbType.DateTime2。ADO.NET 參數文件 有列出指定型別與型別推斷的規則。

範例也順手避開原本的另一個邊界：<= 23:59:59 會漏掉當天最後一秒內帶小數秒的資料。查整年用「大於等於今年年初、小於明年年初」，就不用猜最後一刻應該補多少個 9。這是後續改造的建議，和這次已完成的日期格式修正分開看。

這次最容易漏掉的地方，是畫面還沒選日期，程式就已經替我組好一段日期 SQL。本機又剛好讀得懂，錯誤一直藏到測試機才出現。下次再碰到同樣的環境差異，我會早一點把實際送出的 filter 和連線設定一起攤開。
