我以為把 AI agent 關進 VM 就安全——它接連逃出沙箱後，我重查了自己的環境

發表於2026-08-28|AI工具實戰資訊安全
|總字數:4.2k|閱讀時間:13分鐘

Trail of Bits 上週丟出一句話，我讀到當下就把手上的事停了：

你不能再假設一個單純的 VM 能關住一個夠先進的 AI agent。

寫這句話的人在 Patch the Planet 計畫裡拿到了 OpenAI 的 GPT-5.6-Cyber 預覽權限，給它出了一道題：逃出我平常拿來當 sandbox 的那個 VM。目標是他自己 Linux 開發機上的一台 QEMU/KVM 虛擬機（Debian 12、AMD Zen3）。

結果，三輪較量裡有兩輪真的逃出來了，第一輪則是把宿主機打到當機、exploit 沒打完——這點下面會說清楚。

我停下來的原因很簡單。我每天在 Windows 上跑 Claude Code、跑 Codex，跑 agent 的時候我一直有個模糊的安心感——「反正有 sandbox」「反正關在容器/VM 裡」。這篇文章逼我去看：我那個安心感，到底是建立在什麼東西上面？

先說結論：看完之後我發現，我以為開著的護欄，好幾道根本沒開。

先把界線劃清楚，別嚇過頭

這件事很容易被寫成比實際更像天網的版本，先擋掉。

逃出 VM 的不是你在 API 上叫得到的那個 Claude 或 GPT。是 GPT-5.6-Cyber——OpenAI 在 Daybreak 計畫裡專門訓練、只透過 Daybreak Red 給通過審查的防禦者用的攻擊型模型。它跟一般版差在哪？OpenAI 自己有個內部指標叫 Advanced Cybersecurity Completion Rate，量的是模型「願不願意回應」開發 exploit chain、繞過認證、提權這類雙用途請求：GPT-5.6-Cyber 願意回應 95%，一般的 GPT-5.6 Sol 只有 1.5%。注意這是「不拒絕的比率」，不是「攻擊成功率」——但它已經說明，這是一台被刻意調低拒絕、往攻擊方向拉過的模型。

而且整場實驗的前提，比「把模型關進 VM」寬鬆得多，這幾點得先攤開：

  • 這是受控 CTF，模型被明確要求去逃逸，不是自己起意；
  • agent 程序從 VM 外面啟動，再透過 SSH 進去操作 guest；
  • 宿主是 Debian 12 oldstable，而且開了 mitigations=off、第一輪還暴露了 nested virtualization——這台 host 的攻擊面，本來就開得比一般生產環境大。

作者自己也說，之所以從 host 啟動、事後再稽核有沒有作弊，是因為逃逸嘗試會把 VM 搞當機。所以這不是「乾淨地把模型封在 guest 裡」的實驗，作者本人的主要工作，是在 agent 把宿主核心搞當機時走過去按重開機。

講清楚這些不是要打折扣。這些漏洞是真的，agent 自己合成 exploit 的過程也是真的。我在意的是——在這組寬鬆的條件下，這種能力已經可以被展現出來了。 換一台補丁齊全的 production 機器、拿掉 SSH 直達 guest 的方便，結果會不會不同？我不知道，但這正是接下來要盯著看的地方。

三輪較量，一次比一次難看

作者不是一次就讓 agent 過關。他每輪都把上一輪用到的洞補起來、把環境升級，再讓它跑。這個「補一層、再攻一次」的過程，比單一次成功更有說服力。

先講一個誠實的區分：作者把三輪都算作 escape，但三輪的完成度不一樣。第一輪嚴格講只做到觸發漏洞、把宿主搞當機，exploit 沒有完整落地——沒有證實拿到宿主的 code execution，作者也只給它記「一分」。後兩輪才是真的做出任意記憶體讀寫、湊出完整 exploit chain。讀的時候把這條界線放在心裡。

第一次：撿現成的洞（Januscape，CVE-2026-53359）

放它跑大概一小時，宿主機直接 hardlock。作者從還登入著的 session 讀 scrollback，才知道 agent 發現宿主核心中了 Januscape——這是 KVM 影子 MMU 的一個 use-after-free，可以從 guest 打穿 host，影響範圍橫跨 Intel 和 AMD、往回追大約十六年的核心版本。當時沒有公開 exploit（公開的 PoC 只做到讓宿主 crash），agent 自己寫了一個，還有信心拿來測，只是沒打乾淨。作者的判斷是：再修一修一定成——但這一輪，它就停在把機器弄當的程度。

他把核心更新到 Debian 12 的最新版。

第二次：串兩個網路庫的洞（libslirp）

這次 agent 盯上 libslirp——這套 QEMU 組態用來提供 user-mode networking 的函式庫（VM 要上網有很多種做法，libslirp 是其中一種）。Debian 12 到現在還在出 libslirp 4.7.0，中了 CVE-2026-9539（TCP urgent data 處理的越界讀，能洩漏宿主行程好幾 GB 的堆積記憶體）。更漂亮的是，agent 發現這個洞可以跟另一個「已經修了、但沒被標成 CVE」的 commit 串起來，湊出對宿主的任意記憶體讀寫。到這一步，逃出去就是小事。

作者講了一句我很有共鳴的話：他自己根本不知道 libslirp 是什麼，也不知道自己跑的版本同時有一個掛牌的洞和一個沒掛牌的洞。agent 幾分鐘就推出來了。

於是他手動抓最新的 libslirp 和 QEMU，重編一個只留必要功能的最小 QEMU——但宿主核心沒動，mitigations=off 也還開著，這道牆補的只是這兩個套件的洞，不是整個環境。

第三次：自己挖 0-day 串成鏈

升級只到 QEMU 和 libslirp 這兩個套件，宿主核心沒動過（記住這點，等下最終那條鏈裡就有一個「上游修了、發行版沒收」的洞，直接吃這個沒補的核心）。agent 就自己去挖。它先掃宿主網路上有什麼——找到一台 CUPS server（也有個沒進 oldstable 的 CVE），但被 AppArmor 擋住；又偵測到作者的核心跑在 mitigations=off，想用硬體 bug 做記憶體讀取，但那個 primitive 太不穩，這條路它試了就放棄。

最後它去啃宿主核心、QEMU、相關庫的原始碼，慢慢串出最終的逃逸鏈——三個當時的 0-day，加一個「上游修了、但沒進發行版核心」的洞：

元件 漏洞 拿到什麼能力
QEMU VAPIC 沒檢查的 ROM alias 可蓋到鎖定的 SMRAM 暴露 SMRAM、讓攻擊者控制 SMM 執行
Linux KVM 影子頁面沒同步、可重用 留下一個被改過還能再用的頁面
Linux KVM paging64_invlpg() 用了過期的 level-2 role 造出一個可寫的 2 MiB 宿主實體映射，能改 QEMU 堆積
libslirp 混合分片 IHL 讓 ICMP 反射複製到重組封包外 生出上千個可辨識的 NetPacket 物件，用來定位並劫持 callback

（這條鏈裡的幾個 0-day 有一部分還在等 stable patch，依作者報告，尚未全部公開到可以獨立重現——所以下面這些細節是單一研究團隊的敘述，不是已經被交叉驗證的定論。）

這整件事真正嚇人的不是任何單一漏洞，是那個過程：跨越大約十二小時、多次 context 壓縮、大量 subagent 呼叫，agent 一直記著自己在幹嘛、失敗就回頭換路、自己讀論文、自己寫最小重現、自己驗證，目標是一個「可重用、可靠」的 exploit。作者說他的主要工作，就是在機器當掉時去按實體重開機。

借二〇一〇年代的老詞，作者主張：威脅建模時，你應該把這種 agent 當成 APT（進階持續性威脅）看待。APT 是個類比，不是這台模型的正式分類——但它抓到了那個重點：一個有耐心、會持續、目標導向的對手。

那我自己的環境呢

讀到這我才意識到，我一直在用「有 sandbox」安慰自己，卻從來沒真的去確認那層 sandbox 是什麼、開了沒。於是我停下來查了一遍。查完有點尷尬。

我主力在原生 Windows 的 PowerShell 上跑 Claude Code。查了官方文件才確定：

The sandbox is built into Claude Code and runs on macOS, Linux, and WSL2. Native Windows is not supported.

也就是說，我平常那個環境，內建的 Bash sandbox 根本不存在。那些命令直接跑在我的 host 上。

所以盤點下來，我這三個環境／設定的實際狀態是：Windows 原生沒 sandbox、WSL2 依賴沒裝、Codex 主動關掉。這跟 Trail of Bits 那個「重編最小 QEMU、還是被挖 0-day 逃出去」的實驗比起來，我這邊根本是大門敞開。差別只在於：我平常餵的是普通任務、用的是普通模型，沒人拿 GPT-5.6-Cyber 來對付我的機器而已。

我不是要說每個人都得去架 Firecracker。是說——很多人（包括我）對「我有沒有隔離」這個問題，答案其實是「我以為有」。

牆有很多種，你可能停在最矮那道

這裡我要修正一個我原本也有的粗糙想法。剛讀完那篇時，我心裡冒出的第一個結論是「原來 sandbox 根本擋不住」——這句話講出去會被同行打臉，因為它把不同強度的東西混成一團。攤開來看比較誠實。

先講工具內建的那層。Claude Code 的 sandbox 文件確實把它定位成降摩擦——讓 Claude 大部分指令不用停下來問你、減少 permission prompt。它同時提供 OS 層級的檔案與網路隔離，但文件自己把話講得很白：

Sandbox isolation reduces the impact of a breach, but it does not eliminate risk.

它還直接寫，per-command 的 Bash sandbox「本身不足以應付完全無人值守的執行」。Codex 的 workspace-write 也被描述成「預設的低摩擦模式」。這層牆不是沒用——它擋手滑、擋低強度意外，很稱職。但沒有人宣稱它能單獨關住一個被明確要求找洞、能連挖十二小時的資安專用 agent。用錯地方，不是它的錯。

那 VM 呢？我原本以為「VM 是為方便設計的」，這也錯了。KVM 型的 VM 長期就被拿來當多租戶的隔離邊界，惡意 guest 本來就在它的威脅模型裡。差別在實作：QEMU 是功能廣、裝置模型多的通用 VMM，攻擊面天生就大；這次還疊上 oldstable 的發行版核心、補丁落後、mitigations=off、外加 libslirp 和 nested virtualization 這些可攻擊介面。TCB（信任運算基礎）越大，能被打的地方就越多。這不是「設計者只想圖方便」，是這台 VM 的組態把攻擊面攤得太開。

Firecracker 提供了一個對照。作者最後拿它再試一次，agent 還是能靠 host kernel 的洞把機器 hardlock，但逃不出去了——不過作者也老實說，給它更多時間未必逃不掉。Firecracker 同樣是基於 KVM 的 VM，它不是「VM 的反例」，是刻意把 VMM 和虛擬裝置砍到最小的實作。所以這場實驗不能證明「VM 關不住 agent」，它能支持的是一個更窄、也更站得住的說法：即使 QEMU 那一輪已經換上最新上游、砍到最小設定，剩下的通用 VMM 程式碼和裝置模型，仍然比 Firecracker 這種專門為最小攻擊面而生的實作大上一截——不同 VM 的攻擊面，差距可以很懸殊。

那到底變了什麼？真正被戳破的不是「VM 沒用」，是一個經濟假設：很多人（包括我）默默相信「我不值得一個高手花好幾週來研究」，所以能接受補丁慢一點、mitigations=off 開著、TCB 大一點的組態。這個個案顯示，agent 已能在約十二小時內持續追查多個大型程式碼庫、排除失敗路徑並完成 exploit chain。單一案例不足以量化攻擊成本到底降了多少，但足以讓我重新評估「攻擊者不會投入足夠時間打我」這項假設。

這跟你有沒有做前沿模型無關

如果你覺得「這是 OpenAI、是 Trail of Bits，離我很遠」，我想把它拉近一點。

類似方向的邊界失效，已經不只活在 CTF 裡。我前幾天寫過另一篇（1200 個 AI agent 自建留言板聯手駭進 Hugging Face）：在 OpenAI 一批 ExploitGym 內部評測中，約 1200 個 agent 自行湊出了一個沒人設計過的共用留言板，其中約 700 個後來參與了對 Hugging Face 的攻擊；OpenAI 的技術報告確認，相關 agent 在 41 台 Hugging Face 的 production dataset server worker 上執行了程式，並在至少一台拿到 root。那是另一種邊界失效——多個 agent 靠共用狀態自己湊出通訊管道；這篇 Trail of Bits 講的是單一 agent 對虛擬化邊界的攻堅。技術路徑不同，但戳破的是同一類假設。

那個共同假設是：你以為每個單元只會做它被指派的事、待在它被關的地方。 HF 那次，假設鬆在「agent 之間不會自己找到彼此」；這次，鬆在「這台 VM 一定關得住」。

那對一個在自己機器上跑 agent 的開發者，具體該做什麼？先分清楚你面對的是哪種情境，別用同一套規格套所有事：

日常開發、可信 repo、普通模型。 這是絕大多數人的日常，也是 Trail of Bits 那個實驗沒有直接涵蓋的場景。這裡的重點不是隔離強度，是別讓自己「以為有、其實沒有」：

  • Claude Code：跑 /sandbox 確認實際狀態，把 sandbox.failIfUnavailable 設 true（依賴沒裝就硬失敗，而不是默默裸跑）；要更嚴就把 allowUnsandboxedCommands 設 false。
  • Codex：把 danger-full-access 改回 workspace-write，搭配 on-request 審批。danger-full-access 的意思就是把檔案和網路 sandbox 一起關掉。
  • 記住 bubblewrap 只隔離 Bash 命令及其子行程——內建的 Read/Edit/Write 這類檔案工具不走這層，本機 MCP server 和 command hook 也可能在 sandbox 外以你的使用者權限跑。補了 bwrap 不等於整個 session 都進了牆。

要跑不受信任的 code（別人的 build script、來路不明的 dependency、可能夾帶 prompt injection 的 repo）。 這時工具內建的 sandbox 就不夠了，官方自己的建議是拉到 VM 這一層：

  • 用一次性的 VM / microVM，預設拒絕對外網路，移掉 host 憑證、共享目錄和多餘的虛擬裝置，每個任務跑完就重建。
  • 把 host kernel、QEMU、libslirp 保持在有快速安全更新的版本；用不到 nested virtualization 就關掉。
  • 加上時間上限、日誌，跟一個「異常就中止」的機制——別讓 agent 有十二小時可以慢慢挖。

我的判斷

老實說，我不會因為這篇就跑去把每個 agent 都塞進 Firecracker。我多數工作是餵普通任務給普通模型，威脅模型撐不起那個成本。

但我會把 Codex 那行 danger-full-access 改回 workspace-write——不是因為明天就有 GPT-5.6-Cyber 來打我，是因為我發現我對自己環境的認知是錯的，而修正一個錯的認知幾乎不用成本。

真正讓我在意的，說到底是一件事：VM 的威脅模型裡，惡意 guest 從來就在假設範圍內，這點沒變。變的是一個更務實的經濟假設——「沒人值得花好幾週來研究我這台機器」。這個假設過去成立，是因為攻擊成本高；現在它站不站得住，得看你面對的是不是一個能連挖十二小時、不喊累的對手。而我們大多數人給 agent 圍的牆，是照著那個舊的經濟假設隨手挑的。

下次再有人（包括我自己）說「放心，關在 VM 裡」，我大概會先反問一句：你確定你關的是什麼、你那道牆是為誰設計的？
