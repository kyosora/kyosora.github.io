底圖突然整片空白、重開主機也沒用：國土測繪中心 WMS 最低要求 TLS 1.2，舊 .NET 程式怎麼修

發表於2026-09-10|資訊安全系統與維運
|總字數:3.6k|閱讀時間:12分鐘

八月中使用者傳來一張截圖：系統產出的 PDF 裡那頁地圖，只剩幾個地點標籤孤零零浮在一片白上，底圖整個不見。

同一個症狀我七月才修過一次。當時的結論是防火牆，所以這次第一反應是「白名單又被誰收掉了」，第二反應是「圖台主機要不要重開」。兩個都錯，而且錯得很有教育意義：國土測繪中心的底圖服務現在最低要求 TLS 1.2，一段十幾年前寫的 .NET 元件只會講 TLS 1.0，握手被拒、例外被吞，於是整個系統沒有任何一行錯誤，只有一張白圖。

這篇把兩次修的過程都寫下來，重點放在「為什麼會靜默失敗」跟「為什麼症狀會時好時壞」。後者害我多繞了一圈。

背景：兩條產圖路徑，長得一樣、走的路完全不同

這是一套政府機關的線上申請系統，.NET Framework 加 ASP.NET MVC，地圖用國內一家 GIS 廠商的元件，下面就叫它 GIS 元件。民眾線上送件，承辦審過後系統產出 PDF，裡面附一張地圖：國土測繪中心的通用版電子地圖當底圖，上面疊申請的位置點位。

網站前端看地圖走的是圖台，網頁地圖早就改用 https://wmts.nlsc.gov.tw/wmts/EMAP5/...，走的是瀏覽器的 TLS。回報問題的人也補了一句「圖台上底圖是正常的」，這句話差點把我的方向帶偏。

因為 PDF 裡那張圖根本不經過圖台。後端在網站自己的 process 裡用 GIS 元件的繪圖工具直接畫，讀的是另一份圖層設定檔，走的是 .NET Framework 的 TLS。那份設定檔只有兩層：

同一個系統、同一家底圖供應商、兩個端點、兩套 TLS 協商。畫面上看得到，不代表伺服器端取得到；重開圖台主機對這個症狀也完全無效。這件事我七月就知道了，八月還是先想到重開，可見直覺這種東西不太會學習。

七月那次：真的是防火牆

七月的回報是另一種 PDF（申請書）的底圖白掉。在正式機上跑一行就抓到了：

TCP 443 不通。正式機的 outbound HTTPS 被防火牆擋住，程式連對方的門都敲不到。請機房把 wms.nlsc.gov.tw:443 加進白名單，重新下載，底圖回來了。

那次順手在申請書的產圖流程裡加了一段直接打官方 WMS 的程式，取圖時把 BBOX、HTTP 狀態、回傳 bytes、非白像素比例都寫進 log，想說下次再白掉至少能分辨是網路、服務還是繪圖的問題。這段程式從一開始就明確開了 TLS 1.2，後面會講到這件事的副作用。

（旁支：也是那時候發現這個 GIS 元件預設把圖徵畫到前景畫布，而 PDF 流程只初始化了背景畫布，前景是 null 時畫標籤會丟 ArgumentNullException。要明確把繪圖目標指到背景畫布。跟 TLS 無關，但同一條路徑上的坑。）

當時以為結案了。

八月：另一支匯出白掉，防火牆是通的

八月回報的是核定文件的 PDF。同一個系統、同一張底圖、同一個症狀，但這次 Test-NetConnection 是通的，log 也沒有東西。因為七月加的診斷 log 只加在申請書那支，核定文件是另一支方法，走的是 GIS 元件原生的 WMS provider。

這個系統有四支會產地圖 PDF 的方法，七月修的只是其中一支：

匯出 用途 八月狀態
A 申請書（後台） 七月已修
B 核定文件（民眾端） 白，本次回報
C 另一類案件的核定文件（民眾端） 白
D 另一類案件的申請書（後台） 白

另外三支照舊讓 GIS 元件的 provider 自己去抓設定檔裡那個 http://maps.nlsc.gov.tw 的 WMS。既然 TCP 連得上、程式碼也沒改，我把懷疑移到對方端點跟這邊執行環境之間的協商差異。

對方現在最低要 TLS 1.2

結果（2026-08-20 實測，2026-09-10 寫這篇時重跑一次相同）：

服務沒壞，只是門檻抬高了。老實說我只能證明 8/20 那天它不收 TLS 1.0，不能證明它是七月到八月之間改的：七月時正式機連 443 都不通，根本沒機會看見這件事，而七月修好的那支從第一天就是開著 TLS 1.2 打的。這個服務有沒有可能更早就不收 TLS 1.0，我不知道。對修法沒差，但寫出來免得你拿這篇當變更日期的證據。

再看自己這端。GIS 元件的 WMS provider 從頭到尾沒碰過 ServicePointManager.SecurityProtocol，在這個環境下實際值是 Ssl3 | Tls（旗標列舉，兩個同時開），最高只能協商到 TLS 1.0。對方拒絕握手，provider 拿到例外、吞掉、回一張空圖。逾時還寫死 8 秒。

（沒有額外登錄檔或 AppContext 開關的情況下，SecurityProtocol 的預設值由專案的 target framework 決定，跟機器上裝的 runtime 版本無關：以 4.7 以上為 target 的專案預設才是 SystemDefault、交給作業系統決定；target 較舊的專案就算跑在新 runtime 上，為了相容仍是 Ssl3 | Tls。這套系統實測就是 Ssl3 | Tls，至於是 target、登錄檔還是哪一層造成的，我沒有再追，因為修法都一樣。）

本機重現：四組實驗，只有一個變數有用

我不想在正式機上改程式碼賭猜測，所以拿專案 bin 底下的 GIS 元件 DLL，用 csc.exe 編了一支小 console，照匯出 B 的繪圖流程跑一遍，輸出 PNG。下面這支是整理過的骨架，元件的類別名稱我換成通用的寫法，載入設定檔那段照抄你專案原本的寫法就好，我實際用的版本更醜：

四種組合跑下來：

SecurityProtocol 設定檔的 URL PNG 大小 底圖
預設（Ssl3, Tls） http:// 22,655 bytes 白
預設（Ssl3, Tls） https:// 22,655 bytes 白
加 Tls12 https:// 447,224 bytes 有
加 Tls12 http:// 447,224 bytes 有

在這個元件底下，URL 寫 http 還是 https 沒有差別：HttpWebRequest 預設會跟著 302 走，轉到 https 之後一樣受 SecurityProtocol 管。唯一有差的是 TLS 1.2。我一開始想偷懶只改設定檔把 http 換成 https，這張表直接否決。

正式機我也做了端對端的量化：打那支核定文件的匯出 API，從回傳的 PDF 抽出 800×600 的地圖影像，算非白像素比例。修前 3.7%，就是那幾個點位；修後 72.4%。門檻我抓得很寬鬆（陸地為主的範圍，正常底圖遠高於 30%），純海域或淡色底圖這招會誤判，這裡的案件範圍不會遇到。這個數字比「肉眼看起來有底圖」可靠，之後驗另外兩支的時候不用再一張張開 PDF。

先講清楚 SecurityProtocol 是什麼性質的東西，再貼修法

ServicePointManager.SecurityProtocol 是一個靜態屬性，範圍是整個 AppDomain。這套部署裡整個 ASP.NET 應用程式就是一個 AppDomain，所以四支匯出共用同一份設定。改了它只影響之後新建立的連線，已經握手完的連線不受影響。

另外兩個相容性取捨也要說在前面：

  • 這裡用 |= 是因為要保留舊元件可能依賴的其他協定，這是舊系統的妥協，不是通則。如果你的專案 target 4.7 以上、初始值是 SystemDefault（數值 0），|= Tls12 反而等於把協定鎖死成只有 TLS 1.2，讓作業系統失去挑更新版本的空間。新專案別碰這個屬性，交給 OS。
  • request.Proxy = null 是因為這台正式機的 Global.asax 會塞系統預設 Proxy，而它的 outbound 其實是防火牆白名單直連，Proxy 設定是舊殘留。如果你的環境 outbound 必須走 Proxy 做稽核，這行不能照抄。

修法：把七月的做法套到剩下三支

七月那支申請書已經有一個自己取底圖的方法，這裡叫它 TryDrawBasemap，做的事就三件：打 https://wms.nlsc.gov.tw/wms（國土測繪中心較新的端點，舊的 maps.nlsc.gov.tw/S_Maps/wms 經 302 轉 https 後也還能用）、開 TLS 1.2、把 request.Proxy 設成 null。直接抓不到底圖時才退回讓 GIS 元件自己畫。

最陰的地方：症狀會時好時壞

追這條的時候我發現一個會讓人抓狂的性質，值得單獨講。

七月修好的申請書那支，只要有人下載過一次，就把整個 AppDomain 的 TLS 1.2 打開了；在那之後，其他三支透過元件 provider 去抓 WMS 也會跟著成功。App pool 回收、機器重開、改 web.config 或任何會讓 AppDomain 重啟的動作之後，狀態歸零，核定文件又白，直到下一次有人下載申請書。

所以「昨天還好好的」在這個問題上是零資訊。結果取決於呼叫順序，不取決於程式碼有沒有改。這也是為什麼我堅持用獨立 console 重現：在 IIS 裡試，你永遠不確定現在的狀態是誰留下的。

下次任何「圖突然白掉」我會先做的事

這次學到的東西其實一句話：舊 .NET 元件遇到外部服務升 TLS，典型症狀是靜默空白，不是報錯。

以前我會先怪自己的程式、模板、圖層設定，最後才想到對方。順序應該倒過來：先確認 TCP 通不通（七月那次就是這層），通了就分開看兩件事，對方收哪些 TLS 版本、自己的程式出得了哪些版本。前者花三十秒，以舊 .NET 最常卡的 TLS 1.0 為例：

看到 protocol version 的 alert，至少可以確定你打到的這個端點不收 TLS 1.0，接下來要查的是自己的程式出得了什麼版本，而不是繼續翻模板和設定檔。（如果對方前面有 WAF 或反向代理，拒絕你的可能是那一層，但對你的修法來說結論一樣。）

另外兩件事我也會照做：

  1. 同一個外部服務被幾支方法用到，一次列出來全部修，不要修一支就結案。七月只修一支，八月就回來還債。
  2. SecurityProtocol 這種靜態設定放進 Application_Start 一次做完，別散在各方法裡靠呼叫順序碰運氣。這次我沒動 Global.asax，能動但不漂亮；連同四條路徑統一記錄 HTTP 狀態和 WMS 例外，是下次改版要還的債。

IIS 這一端的 TLS 設定我之前寫過兩篇：別急著關掉 TLS 1.2 講的是自己當 server 時要注意什麼，IISCrypto 是弱掃整改的工具。這篇剛好是反過來的視角：你是 client，對方把門檻抬高了，而你的程式一聲不吭。
