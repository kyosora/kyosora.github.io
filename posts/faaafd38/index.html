韓國銀行 AI 入侵案：攻擊者的 CLAUDE.md 躺在開放目錄，被 CrowdStrike 整包撿走

發表於2026-10-12|AI產業觀察資訊安全
|總字數:2.6k|閱讀時間:8分鐘

韓國銀行被駭這件事，台灣媒體的標題多半寫「廣東 26 歲駭客」。我讀 CrowdStrike 10 月 7 日那篇原始報告時，停在另一行：

攻擊者的伺服器開著目錄瀏覽，Claude Code 的設定檔就放在上面，誰連過去都看得到。CrowdStrike 順著這個檔案找到第二台主機，分析了公開目錄裡的 session 紀錄、記憶檔和 ARTEX 設定，才寫得出這份報告。

我每天都在用 Claude Code。所以我想從這份報告拆出兩個跟工作有關的問題：開發工具留下的紀錄會不會被部署出去，以及非核心系統的風險該怎麼排。

先把報告講了什麼、沒講什麼分開

事件本身是這樣。9 月底到 10 月初，韓國多家金融機構陸續通報資料外洩。韓聯社報導有 7 家金融機構發生侵害事故，Reuters 後續報導的「至少 9 家」則包含被揭露或被媒體報導為攻擊目標的銀行，兩個數字口徑不同。受影響人數，多家媒體引述的是約 6.8 萬人。人數最多的兩家是 Yegaram 儲蓄銀行約 4 萬人、新韓銀行約 2.5 萬人；KB 國民銀行 119 人，韓亞銀行 89 人。韓國金融委員會 10 月 6 日發了消費者警示，隔天 CrowdStrike 的報告出來。

報告確定的部分：

  • 攻擊者用 ARTEX 加上 Claude Code。ARTEX 是中國開發的開源 agentic 滲透測試工具，剛釋出不久。
  • ARTEX 後端主要接 DeepSeek v4.1-flash，推測是透過 API 轉售商 xcai[.]pro 取得。其他 Claude Code session 接了 GLM-5.3 和 Grok 4.6。Claude Code 在這裡是工具，session 背後跑的不一定是 Claude 的模型。
  • 兩台主機分工：香港那台是主要基地，38.244.50[.]120 跑 ARTEX。
  • 攻擊者問過 Claude 哪裡賣得掉韓國外洩資料，還請它幫忙找韓國的 Telegram 資料買賣群。

報告沒說，或說得很保留的部分：

  • 沒有 CVE，也沒有入侵路徑。報告引述媒體報導，提到一家銀行被打的是「給貸款仲介用的貸款進度查詢服務」，另一家是「行員行動辦公支援系統」。
  • 受害機構數，報告自己寫明未確認。
  • 歸因只有中等信心，依據是工具來自中國、prompt 是中文。結論停在「可能是中文使用者、動機是錢」，未歸因於任何已知威脅組織，也沒有判定有國家支持。
  • 哪個步驟由哪個模型完成，公開版本沒有拆開。

至於「廣東茂名、26 歲」，來源是攻擊者叫 Claude 幫忙寫一份資安研究員履歷，把 ARTEX 的戰果寫成條列，prompt 裡附了姓名、電話、Telegram 帳號、年齡、學校和所在地。報告同時指出，操作者一開始填的出生日期是 2007 年 9 月 22 日，跟 26 歲對不起來。CrowdStrike 的說法是這些資料「很可能」屬於操作者，但現有資訊無法確認。

身分沒確認，所以我不會在這裡重貼那個帳號。截至 10 月 12 日，我查到的公開報導沒有提到逮捕或起訴。中國外交部 10 月 8 日的回應是不了解具體情況，並重申反對駭客活動。

報告發布後，ARTEX 的開發者把專案轉成閉源並停止更新。已經流出去的版本收不回來。

那個目錄裡有什麼

回到 .claude 這個目錄。以下是預設位置下跟這件事有關的幾個檔案：

攻擊者那份 CLAUDE.md 是一段中文滲透測試 prompt，規定模型該怎麼打。session 紀錄和記憶檔讓隔天的 session 能接著做，操作者不用每天重新交代進度。

撿到目錄的分析師拿到的是同一批檔案。操作過程能重建到什麼程度，看的就是這些紀錄，連他中途跑去問履歷怎麼寫都留在裡面。

寫到這裡，我叫 Claude Code 在我自己的機器上數了一下（10 月 12 日，範圍是 ~/.claude/projects）：39 個 session 檔，整個目錄 381MB，記憶檔 169 個。拿 grep -E 'password|api[_-]?key|token' 去掃，39 個裡有 36 個命中。token 這個字太常見，這數字一定高估，但我也不敢說裡面完全沒有貼過不該貼的東西。

攻擊者的目錄為什麼會對外，報告沒寫。

我們比較可能踩到的版本

多數人不會把家目錄開成 HTTP 服務。比較現實的是專案層的檔案：repo 根目錄的 CLAUDE.md、.claude/settings.json、.claude/settings.local.json。部署方式如果是「整個資料夾複製到站台目錄」，這些檔案就跟著上線了，跟十年前 .git/ 被整包抓走是同一個問題。

先從外面看一次回應狀態：

404 或 403 代表這次請求沒拿到檔案。看到 200 先別急著下結論，SPA 的 fallback 頁和自訂錯誤頁也會回 200，要把內容抓下來確認是不是目標檔案；3xx 則看它導去哪裡。

如果確認檔案真的公開了，先把來源站和 CDN 的存取一起擋掉、清掉相關快取，同時把存取紀錄和外洩的檔案留一份。檔案裡有還有效的憑證就馬上撤銷或輪替，不用等全部檢查完。接著才是確認暴露了多久、哪些資料，修掉部署流程，再從外面驗一次。沒有存取紀錄不代表沒人下載過。

IIS 的話，交給靜態檔案處理、又沒有 MIME 對應的副檔名不會送出，.md 和 .jsonl 通常會落在 404.3，算是運氣好。但只要站台有 .json 的 MIME 對應，這層限制就擋不住 settings.json。直接把路徑區段藏起來比較乾淨：

非核心系統，手上也有客戶資料

公開的 .claude 目錄解釋了研究人員怎麼追到操作者。銀行是怎麼被打進去的，是另一個問題，擋掉 .claude 也修不到它。

媒體報導的兩個入口，一個是給外部仲介查貸款進度的服務，一個是行員的行動辦公系統。照韓聯社的報導，銀行的說法是受影響的屬於業務支援系統，跟網銀、行動銀行的交易系統分開。交易系統沒事，資料還是出去了，因為這些輔助系統手上本來就有姓名、電話、年收入、核貸額度。

做過弱掃整改的人對這種系統不陌生。它對外、有個資，但被歸在非核心。各家銀行內部怎麼排修補順序，公開資料看不出來，我不想替他們猜。我能說的是這類系統被往後排時常見的理由：要打它得有人花時間摸，攻擊者會去挑更值得的目標。

CrowdStrike 在報告裡的評估是，AI 工具讓一個為錢而來的攻擊者能在短時間內完成多起入侵。讀到這句，我認為「攻擊者不會願意花這個時間」這個前提會越來越站不住。這是我的判斷，報告沒有給攻擊工時或成本的數字。

同一波事件裡，友利銀行和 NH 農協銀行表示入侵防禦系統擋下了攻擊，截至報導當時沒有發現資料外洩。韓國《京鄉新聞》10 月 5 日的報導提到兩個差異：友利的業務系統登入除了帳密還要生物辨識，農協則沒有對貸款仲介開放內部系統的連線路徑。報導用的是「據了解」的語氣，這兩項措施在這次攻擊裡實際起了多少作用，公開資訊還不足以確認。但多一道驗證、少一條對外路徑，都是不用等 AI 防禦產品就能做的事。

三月我寫過地下論壇的 agentic 攻擊框架，那篇引用的還是威脅情報報告裡的趨勢數字。這次有了操作紀錄外露的具體案例，而它會這麼具體，是因為攻擊者自己沒關目錄。

我自己會做的兩件事

第一件是拿上面那段 curl，花五分鐘把手上幾個站台掃過第一輪。

第二件是回頭看整改清單的排序。我會改用三個條件重排：對外暴露的程度、讀得到哪些個資、驗證和權限怎麼設，系統算不算核心不再是主要依據。

至於那位操作者，工具留下的對話和記憶檔，最後都成了公開線索。我用同一套工具，記憶檔 169 個，這件事我笑不太出來。
