在 .NET 8 Web API 示範零信任原則

發表於2024-10-19|程式設計
|總字數:7.7k|閱讀時間:34分鐘

零信任的核心是一句話：「永不信任，始終驗證」。聽起來像口號，落到 .NET Core Web API 上，它其實是一串很具體的工程動作——每個請求都要驗 JWT、每個端點都要授權、敏感資料落地前要加密、所有存取都要留稽核紀錄。

網路上談零信任的文章很多，但大多停在「驗證 token」這一步，把怎麼簽發 token、設定值放哪、middleware 怎麼掛這些「跑起來真正需要的東西」省略掉了。照著抄常常編譯失敗，或執行期吃一個 NullReferenceException。

這篇做的是一個教學用 API，把零信任原則對應到可讀的 .NET 元件。它不等於完整企業零信任平台：強式登入、裝置姿態、token 撤銷、金鑰輪替、防竄改稽核、secret store 與正式部署流程仍要由實際環境補上。

五個原則，對應五件事

零信任這套架構，我把它拆成五個原則，每一個都對應後面一段實作：

  1. 永遠驗證 — 每個請求都驗身分（JWT 簽發與驗證）
  2. 最小權限 — 只給必要的存取權（授權政策）
  3. 假設破壞 — 當作網路已經被打進來（限流、安全標頭）
  4. 全程加密 — 通訊與落地資料都加密（HTTPS、AES）
  5. 持續監控 — 記錄並分析所有活動（稽核日誌、Application Insights）

往下走的時候，你會發現這五件事彼此咬合：沒有簽發就沒有驗證，沒有授權政策最小權限就是空談。

授權：最小權限政策

驗過身分只代表「你是誰」，授權才決定「你能做什麼」。定義兩條政策——一條限管理員角色，一條檢查前面 token 帶的 api_access scope：

控制器上掛 [Authorize(Policy = "RequireApiAccess")]，請求就必須帶著 scope=api_access 的 token 才進得來。

有一個坑在這裡值得特別說。如果你的 Program.cs 是先呼叫 AddIdentity<ApplicationUser, IdentityRole>(...) 再呼叫 AddAuthentication(JwtBearerDefaults.AuthenticationScheme)，帶 JWT 的請求打到 [Authorize] 端點時會直接吃 401，不管 token 多正確。

AddIdentity 會註冊 Cookie schemes；純 JWT API 若沒有明確指定 scheme，很容易讓授權挑錯處理器。這份教學改用 AddIdentityCore<ApplicationUser>()，再補上角色、SignInManager 與 EF store，JWT scheme 則由 AddAuthentication(JwtBearerDefaults.AuthenticationScheme) 明確接管。

稽核日誌中介軟體

「持續監控」最基本的一層，是把每個請求的關鍵欄位記下來：誰、什麼時間、從哪個 IP、打了哪個端點。

{@AuditLog} 前面那個 @ 是 Serilog 的解構運算子，會把整個物件當結構化資料記下來，之後在日誌平台才能用欄位查詢，而不是塞一坨字串。

這仍只是基礎 request log，不能直接當合規稽核軌跡。正式環境至少要送到與應用程式分離、具 append-only／防竄改能力的集中儲存，限制查閱權、設定保留期限與告警，並避免記錄 token、密碼、完整 request body 等敏感資料。

敏感資料加密服務

「全程加密」不只指傳輸層的 HTTPS，落地的敏感欄位也要加密。這段是整篇最容易寫錯、也最危險的地方。

只替 AES-CBC 換隨機 IV 還不夠。CBC 能保密，卻不會驗證密文有沒有被竄改；服務若直接解密外部輸入，錯誤內容或處理時間可能變成 padding oracle。這篇既然以 .NET 8 為基準，直接用 AES-GCM。它每次產生新的 nonce，並附帶 authentication tag；密文被改過一個 bit，解密就會在回傳明文前失敗。

金鑰長度一定要在建構時就驗。這裡固定用 AES-256，傳錯長度就直接在啟動時報清楚，別等到第一筆資料加密才丟出難追的 CryptographicException：

payload 開頭的版本位元組只識別格式，不等於金鑰輪替。正式輪替還要保存 key ID，解密時由 key resolver 取得對應舊金鑰，完成重加密後再淘汰。nonce 不需要保密，但同一把金鑰下不能重複；associated data 則把密文綁定到 owner、record ID、tenant 與欄位用途，防止合法密文被搬到另一筆資料後仍驗證成功。

收尾

這篇把 JWT、claim 授權、可信代理限流、AES-GCM 欄位加密、基礎 request log 與健康檢查放進同一個教學專案。它的用途是示範零信任原則如何對應 .NET 元件；正式環境仍要補整合測試、外部身分提供者、token 撤銷與輪替、防竄改稽核、secret store、資料庫部署流程和監控告警。

如果只挑幾個最容易翻車的點記住，我會選這四個：Jwt:Key 沒設好會在啟動時吃 NullReferenceException；限流前要先處理可信代理；欄位加密要用帶完整性驗證的 AES-GCM；解密端不能接收外部任意密文。這幾項少一個，表面上的零信任都會留下明顯缺口。
