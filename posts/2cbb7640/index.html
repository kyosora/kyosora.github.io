為什麼需要限流

API 限流（Rate Limiting）的核心需求只有一個：保護服務本身不被流量壓垮，同時讓合法使用者繼續正常運作。這件事比聽起來更微妙——設太緊會誤殺正常請求，設太鬆則保護不到位。

幾個實際場景：

  • 單一 IP 在 10 秒內打了 5,000 次請求，幾乎可以確定是爬蟲或攻擊
  • 雲端服務按 API 呼叫次數計費，沒有限流的話一個 bug 就能讓帳單爆表
  • 資料庫連線有上限，突發高併發會讓所有請求一起逾時，而非只讓超額的那些失敗

常見限流策略

限流策略 實作複雜度 記憶體消耗 精確度 突發流量處理 分散式實作
固定窗口 低 低 低 差 易
滑動窗口 中 中 高 中 中
令牌桶 中 中 高 優 中
漏桶 高 高 高 差 難

1. 固定窗口計數器（Fixed Window Counter）

最直接的做法：每個時間窗口（例如 1 分鐘）內維護一個計數器，超過上限就拒絕。

核心問題是邊界效應。 假設限制每分鐘 100 次，用戶可以在 13:00:59 打 100 次，再在 13:01:01 打 100 次，2 秒內實際送出 200 次，系統卻全部放行。

適合用在：對精確度要求不高的內部 API、快速原型。有突發流量疑慮或高併發的場景不建議用。

2. 滑動窗口計數器（Sliding Window Counter）

把時間窗口切成更小的 bucket，持續滾動統計最近 N 個 bucket 的總量。它會縮小固定窗口的邊界突發，但仍是 bucket 粒度的近似值；bucket 越小越精確，狀態與運算成本也越高。

bucket 大小建議值：100ms～1s；總窗口依場景定，API 限流通常 1s～60s，爬蟲防護可以拉到分鐘級。

3. 令牌桶（Token Bucket）

系統以固定速率往桶裡放令牌，每次請求消耗一個令牌，桶空了就拒絕。桶本身有容量上限，最大允許突發量等於桶容量——這讓它很適合「平時流量不大、偶爾突發」的場景。

令牌桶與漏桶的核心差異：令牌桶允許突發（桶裡的令牌可以一次用光），漏桶強制恆速輸出（桶滿了才拒絕，但消費速率固定）。

4. 漏桶（Leaky Bucket）

工作先進入有容量上限的佇列，再以固定間隔逐一交給下游。這裡不能只維護一個 _queueSize 計數器後立刻回傳 true；那種寫法沒有真的排隊，瞬間進來的 100 個請求還是會一起打到資料庫。

分散式限流方案

單機 in-memory 方案在水平擴展後會失效，每個節點各自計數，限額實際上被乘以節點數。需要跨節點一致性時，Redis 是標準做法。

最佳實踐建議

分層設限。 同一個請求可以同時受到多層限制：IP 層（防爆破）、使用者層（公平使用）、端點層（保護昂貴操作）。每層閾值不同，任一層觸發就拒絕。

429 最好帶可用的重試資訊。 Retry-After 是標準 HTTP header，能告訴客戶端何時重試；前面的官方 limiter 只在 lease 提供 RetryAfter metadata 時才送出。剩餘額度與上限可採用組織選定的 RateLimit headers，但不能宣稱 X-RateLimit-* 是所有 API 都必須使用的唯一標準，也不要回傳算不準的 remaining。

閾值要從容量與 SLO 反推。 先在測試環境量出不同併發下的吞吐、p99、錯誤率與下游飽和點，再依可接受延遲、成本、流量分布與預留容量訂限額。70%～80% 容量或 1% 拒絕率只能是某個系統的起始假設，不能當成通用門檻；上線後以自己的 SLO 與拒絕原因持續校準。

白名單要最小化。 內部服務、監控探針確實需要排除限流，但白名單每增加一條就是一個潛在的繞過入口。定期審查，過期條目要清掉。

效能測試方法

使用 Apache JMeter

在 GUI 建立 Thread Group（50 threads、10 秒 ramp-up、100 loops），底下加入 HTTP Request sampler，再加 Summary Report 與 Aggregate Report listener；確認能跑後用 jmeter -n -t rate-limit.jmx -l result.jtl 以 non-GUI mode 執行。JMX 還需要 TestPlan、hashTree 與 sampler 等完整結構，別把網路上的片段 XML 當成可直接執行的測試檔。

測試要跑四種場景才有意義：正常負載（確認限流不誤殺）、突發負載（短時間大量請求）、持續高負載（確認限流持久有效）、邊界測試（打到剛好等於限額的 99%、100%、101%，確認閾值行為符合預期）。

使用 K6

K6 的好處是可以用 JavaScript 寫不同路徑與請求大小。單一 load generator 通常仍共用一個出口 IP；要驗 IP 分桶，必須使用多個具不同出口的 generator，或在可控制來源位址的隔離測試網路執行，不能靠偽造 XFF 假裝不同客戶端。

壓測後要看的三個數字：被拒絕率（上例的 rate_limited）、p99 延遲（限流路徑本身不能太慢）、記憶體使用量。有界漏桶的上限由 capacity 決定；滑動窗口則取決於識別鍵數量與保留的 bucket 數，不應籠統寫成隨總請求量無限線性成長。
