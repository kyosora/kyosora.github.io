去年還看好 React Native，Shopify 為什麼回頭寫原生

發表於2026-09-30|AI工具實戰前後端開發
|總字數:2.1k|閱讀時間:6分鐘

2025 年 1 月，Shopify 發表採用 React Native 五年的回顧，認為這條路走得成功，還看好它的未來。2026 年 9 月，同一家公司宣布要把行動 App 搬回 Swift 與 Kotlin。

我讀完這兩次說明，最在意的是一個很現實的問題：如果 AI 讓寫兩套程式的成本降下來，跨平台還省得下多少工作？Shopify 給了一個值得看的案例，但答案得連同它投入的驗證工具、原生工程師與既有產品一起算。2025 年回顧、2026 年回歸原生說明

先看清楚是哪個 App 搬完了

Shopify 的產品名稱很容易讓人看錯。9 月公布的 12 週遷移成果，指的是消費者使用的 Shop app。商家管理生意的 Shopify app 是另一個專案；依 9 月 21 日的文章，它有超過 300 個畫面，遷移仍在進行。Shop 遷移紀錄、Shopify app 的 Helix 工具

網路上很吸睛的「一個工程師、一週」也得補上後半句：那是 iOS SwiftUI 的概念驗證，尚未達到正式上線要求。Shop 從驗證到雙平台商店發布花了 12 週，有六位核心工程師，功能團隊中途也加入處理細節與相容行為。團隊手上還有能跑的舊 App，可以逐項對照。Shop 遷移紀錄

這些條件直接影響案例能不能搬到自己的團隊。接手一個已經知道要長什麼樣、怎麼運作的產品，和從零猜使用者需要什麼，是兩種工作。AI 再會翻譯程式，也無法替沒有定案的產品需求做最後決定。

跨平台當初省下的錢，重新算了一次

Shopify 在 2025 年回顧中，談到共用程式碼、跨 Web 與行動端調動人才的好處，也承認框架升級與依賴需要持續投入。到了 2025 年 9 月，Shopify Mobile 與 POS 還完成了 React Native New Architecture 遷移。這段歷史說明，回歸原生前，他們確實長期投資過這條路。五年回顧、New Architecture 遷移

2026 年的決策則把 coding agent 放進成本估算：平台間可以互相參考實作，重複撰寫功能變得便宜；直接使用原生 API，也減少了框架與依賴的中間層。Shopify 同時承認，兩套平台程式碼的維護成本依然存在。回歸原生說明

我會把這筆帳拆成四項：

工作 AI 可能改變的部分 團隊仍要負責的部分
實作功能 從另一平台與既有程式產生初稿 決定架構，審查平台慣例
接原生能力 協助查文件與修改呼叫方式 裝置、權限與作業系統差異
維持產品一致 產生測試、比對狀態與畫面 定義哪些差異可以接受
發版後維護 協助追查、同步修正 雙平台驗收與長期所有權

這是我的分析拆法，並非 Shopify 公布的成本報表。官方沒有提供完整的人時、模型費用與長期維護帳目，無法據此算出你的團隊能省幾成。

寫程式變便宜，是重新評估架構的理由。拿它直接推導「現在都該重寫」，中間跳過的工作太多了。

真正麻煩的是那些看不見的行為

Shop 的紀錄特別提到登入狀態、推播，以及分析事件和下游推薦系統需要的上下文。它們做了 Tardis 工具，讓工程師與 agent 查看執行中的事件、日誌和狀態，對照遷移前後的行為。Shop 遷移紀錄

畫面像不像，比較容易引起注意。少送一個事件、同一次點擊送兩遍，或者推薦來源掉了，使用者當下可能完全無感。等報表和推薦效果出現變化，問題已經跨過好幾個系統。

Helix 把大包重寫拆成能驗收的小段

Shopify 在回歸原生的說明裡，提過一次產出整個重寫版本的嘗試：即使事前準備規格，結果仍不適合維護與交付。後續商家 App 的遷移採用內部工具 Helix，將工作切成小段。回歸原生說明

這和 Shop 的 Pi、Tardis 是不同專案裡的工具，不能混成同一套已完成的遷移流程。

Helix 每段工作要經過行為測試、畫面比對、兩個獨立 agent 審稿，預設再由工程師核准。行為可以先透過 CLI 驗證，省下每次都啟動模擬器的等待。畫面比對若發現兩張截圖根本處於不同狀態，會要求重新擷取。Helix 工程說明

flowchart LR
    A[選定一小段功能] --> B[產生原生實作]
    B --> C[行為與畫面驗證]
    C --> D[獨立程式碼審查]
    D --> E[預設由工程師核准]
    E --> F[提交後進下一段]

工程師可以選擇自主模式，略過逐段人工核准；測試、畫面檢查與 agent 審稿仍需通過。因此不能把它描述成所有步驟永遠有人簽字，也不能把自動檢查當成零缺陷保證。Helix 工程說明

這個設計吸引我的地方很具體：出錯時，要回頭檢查的範圍可以限制在一小段讀得完的 diff。一次生成幾萬行程式碼，最後才請人驗收，光確認哪些地方值得信任就可能耗光力氣。

效能有進步，但還不足以替所有團隊選框架

Shop 公布的冷啟動數字，從點擊圖示算到首頁動態出現：iOS 由 3,200 ms 降到 2,466 ms，Android 由 4,433 ms 降到 2,233 ms。Shop 遷移紀錄

這些是同一團隊公布的遷移前後成果，沒有控制所有變因。Shop 團隊明說遷移時移除了部分畫面，也調整了其他流程，因此這組數字無法分離框架與產品改動的影響，更不能當成原生對 React Native 的通用跑分。

如果我在評估類似遷移，會先挑一條包含登入、推播入口和分析事件的完整流程。量測實作時間時，把原生審查、測試補齊、裝置驗證一起記進去；再安排一次雙平台需求修改，看看後續同步要花多少工。只做一張漂亮的新首頁，證據還太薄。

如果這次試做連驗證工具的投入都攤不回來，或團隊沒有人能判斷 Swift、Kotlin 的維護品質，我會先留在現有架構。正在穩定交付的產品，本來就不欠任何框架一次重寫。

Shopify 這次讓我重新注意到跨平台的另一筆帳：共用程式碼少了，產品行為就更需要明確的對照方式。比起「12 週搬完」的速度，我更想看一年後，兩套原生版本如何一起改需求、修 bug，以及維持一致。
