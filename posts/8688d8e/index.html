前言

身為後端工程師，你是否遇過這樣的情況：

  • 系統突然變得超級慢
  • 網頁一直轉圈圈
  • 收到「已超過連線逾時的設定」錯誤訊息

如果有，很可能就是連線池爆掉了。以下分享一個真實案例，從診斷、緊急處理到根治。

上面最容易出事的不是語法，而是把警告和可執行指令放在同一段。有人為了省時間整段貼進 SSMS，SINGLE_USER 真的會跑，恢復指令卻可能沒跑。連線池在應用程式程序內，優先處理洩漏的 SqlConnection、回收有問題的應用程式執行個體，或只終止已確認的個別 session；別把整個資料庫切成單一使用者模式。

  1. 使用 Using 區塊確保資源釋放

  2. 避免全域宣告資料庫連線

  3. 設定適當的連線池參數

Max Pool Size 預設值就是 100，直接填 100 等於沒改。實際調整依據：若應用有高峰期 N 個 thread 同時存取資料庫，Pool Size 設成接近 N；設太大反而讓 SQL Server 同時承受過多連線，效能反降。調整前先用上面的 DMV 查看實際峰值再決定。

注意： System.Data.SqlClient 是 .NET Framework 內建的舊版 provider，已進入維護模式。新專案或 .NET Core/.NET 5+ 環境，建議改用 NuGet 套件 Microsoft.Data.SqlClient，微軟已將後者列為主動開發的標準驅動。舊系統維護沿用舊 provider 沒問題，但新專案不建議照搬這段連線字串。

預防措施

監控：SQL Server Agent 可以定期彙總 session，但不能把伺服器總連線數直接拿去對照單一 Max Pool Size。ADO.NET 會依程序、完整連線字串與認證身分分成不同 pool，多台應用程式主機也各有自己的 pool；SQL Server DMV 看到的是總和。告警應先依 host_name、program_name、login_name 分組，再用該應用程式的執行個體數、連線字串與平時基線訂門檻。應用程式端則另外記錄開啟連線的逾時率、請求併發數與查詢耗時，兩邊資料合起來才判斷得出是哪一個 pool 在耗盡。

程式碼審查重點：SqlConnection 必須在 Using 區塊或 try/finally 中確保 Dispose()。容易漏的地方是早期 VB 程式的全域連線變數，以及呼叫端先手動 Open()、交給 DataAdapter.Fill() 後卻沒有釋放的寫法。若傳入的連線原本是關閉的，DataAdapter 通常會自行開啟並在完成後關閉；不能只看到 Fill() 就認定它洩漏。

重試機制：只對已確認屬於暫時性的錯誤重試，加入指數退避、jitter 與整體逾時預算。連線池已經耗盡時盲目重試會增加等待中的請求，讓事故更久。持續耗盡也不等於一定洩漏；慢查詢、阻塞、未提交交易、資料庫不可用，或合理但超過容量的併發流量都會造成同樣症狀。先看查詢耗時、blocking chain、交易狀態與應用程式併發數，再決定是修程式、調查 SQL，或在容量評估後調整 pool。
