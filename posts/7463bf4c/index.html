Windows Server 開 OpenSSH 只用金鑰登入：四台機器，四種卡法

發表於2026-11-12|資訊安全系統與維運
|總字數:5.1k|閱讀時間:18分鐘

十月底，我要從公司的筆電 SSH 進兩台客戶的 Windows Server。十一月初又多了兩台放在現場的 Windows 電腦。

需求很單純：裝 OpenSSH Server，只准金鑰登入，密碼一律不收。我讓 Claude Code 在筆電上產一組 ed25519 金鑰，再寫一支 PowerShell 腳本，拿到對方機器上用系統管理員跑一次：裝 sshd、開防火牆、寫公鑰、把登入後的 shell 換成 PowerShell。

四台機器，各卡在不同地方：

機器 系統 卡在哪 結果
伺服器 A Windows Server 2016 沒有 OpenSSH 選用功能 改裝 MSI，金鑰登入完成
伺服器 B Windows Server 2019 sshd 在聽，外面連 22 逾時 放棄 SSH，改用別的方式遠端
現場機一號 Windows 桌機 只關了 PasswordAuthentication 補關 keyboard-interactive
現場機二號 Windows 桌機 連不到 Windows Update；MSI 自帶防火牆規則 改裝 MSI，22 埠限定公司 IP

下面先講共通的安裝和設定，最後再講伺服器 B 的排查。

安裝：Server 2016 沒有選用功能，另一台連不到 Windows Update

新版 Windows 裝 OpenSSH Server，標準做法是 Add-WindowsCapability。微軟文件寫的最低需求是 Windows Server 2019 或 Windows 10 1809。伺服器 A 是 Server 2016（1607），Get-WindowsCapability 查不到任何 OpenSSH 項目，我的第一版腳本直接把空值塞給 Add-WindowsCapability -Name，當場爆掉。

現場機二號有這個選用功能，Add-WindowsCapability 卻丟 0x80240438，也就是 WU_E_PT_ENDPOINT_UNREACHABLE：連不到 Windows Update 的端點。那台在客戶的內網，我不想為了裝 SSH 去動它的更新設定。

兩台最後都改裝 GitHub 上 PowerShell 團隊發佈的 Win32-OpenSSH MSI。腳本改成先試選用功能，沒有或失敗再裝 MSI（節錄）：

腳本本身也出過兩個狀況。

第一次跑完，對方回我：「視窗直接關了，看不到印出什麼。」推測是用右鍵「用 PowerShell 執行」跑的，帳號本來就有系統管理員權限，腳本沒有另開提權視窗，在原本的視窗跑完就跟著關了。後來補上 Start-Transcript 存 log，結束時在 finally 裡 Read-Host 等對方按 Enter，至少能留下錯誤訊息。

另一個是編碼。腳本裡有中文，要存成 UTF-8 含 BOM。Windows PowerShell 5.1 讀沒有 BOM 的 .ps1，會用系統的 ANSI 字碼頁，繁中系統通常是 CP950，UTF-8 寫的中文就會被讀錯，嚴重時連腳本都解析失敗。

腳本最後會檢查 22 埠有沒有在聽。在 Server 2016 和 2019 上，Get-NetTCPConnection -LocalPort 22 -State Listen 都回報沒在聽，netstat 卻看得到 LISTENING。原因我沒追，判斷改用 netstat：

這次用 MSI 裝的現場機二號還有一個差別：安裝目錄沒有加進系統 PATH。實測 scp、sftp 都不能用，錯誤是找不到 sftp-server.exe。Win32-OpenSSH 的 wiki 把「更新系統 PATH」列為 SCP、SFTP 的必要步驟。那台我沒改 PATH，傳檔改走別的方式，所以補了 PATH 是否就好，我沒有驗證。

公鑰放哪裡，要看帳號

Windows 版 sshd 預設對系統管理員和一般帳號讀不同的檔案：Administrators 群組的成員讀 C:\ProgramData\ssh\administrators_authorized_keys，一般帳號讀自己家目錄的 .ssh\authorized_keys。這是預設 sshd_config 結尾的 Match Group administrators 區塊決定的。微軟文件也寫明，administrators_authorized_keys 的權限只能留給 Administrators 和 SYSTEM。

這次我把同一把公鑰兩邊都寫，省得腳本判斷對方是哪種帳號（節錄；讀檔那行補了 -Encoding UTF8，原版沒有）：

這段有三個要注意的地方。

/inheritance:r 只移除繼承來的權限，檔案上原本就有的明確授權不會被清掉。新建的檔案沒問題；如果是沿用舊檔，寫完要用 icacls 看一眼，只剩這幾個對象才算數。

administrators_authorized_keys 是整台機器所有管理員帳號共用的。公鑰寫進去，等於這把金鑰可以登入任何一個管理員帳號。我要的就是管理員權限，所以兩邊都寫；如果你只想開放某個一般帳號，就不要順手寫進這個檔。

$TargetSid 和 $TargetProfile 是腳本在提權之前先記下來、再用參數傳給提權後的程序。一般帳號跑腳本時，UAC 可能要求輸入另一個管理員帳號，提權後的 $env:USERPROFILE 就變成那個管理員的家目錄，公鑰會寫錯人。用同一個帳號按「是」提權則不會有這個問題。

（PowerShell 5.1 的 Set-Content -Encoding UTF8 會寫出 BOM，所以這裡改用 [IO.File]::WriteAllLines 配不含 BOM 的編碼。）

只關 PasswordAuthentication，伺服器還在宣告 keyboard-interactive

現場機一號最容易讓人誤判：sshd_config 已經寫了 PasswordAuthentication no，看設定檔會以為只剩金鑰。直接問伺服器接受哪些登入方式，答案不一樣：

sshd -T 印出的設定也是如此：

keyboard-interactive 是另一條登入方式，PasswordAuthentication no 管不到它，要另外用 KbdInteractiveAuthentication no 關。在 Windows 上它到底能不能拿來打密碼，我沒有實測；Win32-OpenSSH 早期的 issue #1554 回報過，7.7 版的 sshd 預設會宣告 keyboard-interactive，但 Windows 上其實沒有實作。

我還是把它關了。理由很實際：我要的是一行指令就能確認「只剩金鑰」，而不是每次都得解釋「這個雖然有宣告，但應該沒作用」。

設定放在 Match 之前

Windows 版 sshd_config 的結尾有一段 Match Group administrators。這個區塊一直延續到下一個 Match 或檔案結尾，裡面的設定只套用在符合條件的連線上。全域設定要放在它之前。

伺服器 A 用的做法，是把預設檔裡被註解掉的 #PasswordAuthentication 那一行換掉，位置自然就對了。下面只節錄處理「預設設定檔」的分支，改過的設定檔不能直接套：

現場機一號已經有 PasswordAuthentication no，這段會整個跳過，那台是另外在它下面補一行 KbdInteractiveAuthentication no，一樣在 Match 之前。sshd -t 只檢查語法，有沒有真的只剩金鑰，要重啟後從外面驗。

驗收：宣告清單只剩 publickey，再實際登入一次

重啟之後從外面再問一次：

只剩 publickey。但這只代表伺服器宣告的方法對了；公鑰路徑或 ACL 寫錯時，宣告一樣只有 publickey，卻誰都登不進去。所以最後一定再用指定的私鑰實際登入目標帳號一次。

這幾行改的是 sshd 自己的設定，遠端桌面不受影響，RDP 照樣用密碼登入。

MSI 自己開了一條「任何來源都能連」的防火牆規則

現場機二號要把 22 埠限定只讓公司的固定 IP 連。原本的打算很簡單：改 OpenSSH-Server-In-TCP 這條規則的遠端位址就好。

幸好裝 MSI 之前，Claude Code 先用 WindowsInstaller.Installer 的 COM 物件唯讀翻了一遍 MSI 的資料表，WixFirewallException 表裡有這一列：

MSI 安裝時會自己建一條叫「OpenSSH SSH Server Preview (sshd)」的入站允許規則，遠端位址是 *。只縮小其中一條允許規則，另一條照樣會放行任何來源。

所以那台的腳本不靠規則名稱，改成從 port 反查，把 22 埠的入站允許規則全部限定成公司 IP（整理過：實際跑的版本沒有篩 Action，那台剛好沒有 22 埠的封鎖規則；要拿去用，記得排除 Block，否則會把封鎖規則也改掉）：

這段只抓明確寫 22 的規則。LocalPort 是 Any 或埠範圍的允許規則抓不到，群組原則下發的規則也不在預設查詢的範圍裡，這些要另外看。改完再列一次，每條相關規則的 RemoteAddress 都只剩公司 IP，才算數。

現場機二號後來還有一段插曲：十一月六日清晨它的公網 IP 換了，原來是浮動 IP。sshd 只限制「來源是公司 IP」，跟它自己的 IP 無關，那邊不用改。要小心的是從公司連新 IP 的第一次：先抓新 IP 的主機金鑰指紋，跟 known_hosts 裡舊 IP 的紀錄比對（指令整理過）：

ED25519、RSA、ECDSA 三種金鑰各自跟舊紀錄相符，確認是先前信任過的那組主機金鑰，才加進 known_hosts。指紋對不上就不要連，可能是別台機器拿到了這個 IP。

伺服器 B：sshd 在聽，外面連 22 卻逾時

伺服器 B 卡得最久。

本機看起來都正常：netstat 有 0.0.0.0:22 LISTENING，防火牆規則開著、來源不限、綁的是 sshd.exe，AllowLocalFirewallRules 是 True，沒有入站封鎖規則，也沒有第三方防火牆。可是從外面連 22 會等到逾時，同一台的 3389、80、443 都通。

逾時和被拒絕要分開看。被拒絕通常是收到了 RST，常見原因是那個 port 沒有服務在聽，也可能是防火牆主動拒絕。逾時則是期限內沒完成連線，去程被丟、回程回不來、主機本身沒回應都有可能，光看逾時還不知道封包斷在哪。

排查途中出過兩次狀況。

一次是對方貼回來的輸出不對勁。Claude Code 注意到那份 PowerShell 開頭印的是「著作權 (C) 2016 Microsoft Corporation」，年份跟伺服器 B 對不上，懷疑輸出來自另一台。向對方確認，指令確實跑到伺服器 A 去了。

另一次在我這邊。我的筆電有一張 198.18.x.x 的虛擬網卡，是代理工具的 TUN 介面，會攔部分出站流量。我本來拿「連 GitHub 的 22 會通」證明公司沒有擋出站的 22，這個對照組可能根本沒走實體網卡。之後拿外部服務當對照組，我都先用 Find-NetRoute -RemoteIPAddress <IP> 看流量走哪張網卡。

用防火牆紀錄加對照組追查連線

本機幾項檢查都正常，但我還不知道外面送來的連線有沒有到達 Windows。做法是：在伺服器 B 打開 Windows 防火牆紀錄 60 秒，同一段時間從外面一直連 22，同時連一個確定會通的 3389 當對照組（整理過：原本只讀 Public 的紀錄檔，還原也沒包在 finally）：

結果：3389 有 4 筆 ALLOW，22 一筆都沒有。

對照組是這個測試的關鍵。只看 22，「沒有紀錄」也可能是紀錄根本沒寫成功；3389 有記到，代表同一個來源的連線在這段時間確實會被記下來，22 卻沒有。加上本機各層都查過，我判斷是主機前面的設備把 22 過濾掉了。這仍是推論：要百分之百確定，得在網卡層抓封包，或看上游設備的紀錄。伺服器 B 當時兩樣都沒做；網卡層這一步，後來在另一台補上了，寫在本節最後。

閘道 MAC 的 OUI 查出來是 Nokia，這台的固定 IP 又屬於中華電信 HiNet 的網段，我懷疑前面是電信業者的設備，我們沒有管理權限。

換一個 port 也不行

打電話等電信業者之前，我想先試另一條路：如果上游只擋 22，sshd 改聽別的 port 就好。做法一樣，開 60 秒紀錄，從外面同時連 30 個候選 port，看哪些會出現在紀錄裡。

這次先多確認一件事：被 Windows 擋下的封包有沒有記成 DROP。前一輪只證明 ALLOW 會記，如果 DROP 沒寫進去，「沒出現在紀錄裡」就更站不住。紀錄裡剛好有 5 筆區網 NetBIOS 廣播的 DROP，DROP 是會記的。

結果 30 個候選 port 裡，只有 21 出現在紀錄。加上先前確認連得通的 80、443、3389，目前從公司這邊確認進得去的只有這四個 port，全都有服務在用。21 是 FileZilla Server，FileZilla 也沒設固定的被動模式 port 範圍，我看不到上游設備的設定，沒確認到任何可以借用的 port，就停手了。

最後伺服器 B 的 SSH 我放棄了：sshd 停掉、改成手動啟動，防火牆規則停用，設定和公鑰都留著，哪天上游開了 22 再打開。要遠端操作那台，改成在上面裝 Claude Code，用 Remote Control 處理，這部分以後另外寫。

後來改用 pktmon：直接數網卡收到幾個封包

十一月十日，類似的情況又出現一次。現場機二號要連現場機一號的 SQL Server（1433），一號機的 Windows 防火牆已經放行二號機的 IP，還是逾時。

這次沒有再開防火牆紀錄，改用 Windows 內建的 Packet Monitor（pktmon，微軟文件寫 Windows 10、Server 2019 起內建），直接在一號機的網卡上數封包。對照組一樣要有：一號機的 80 從二號機連得通。下面是在 Windows 11 上跑的版本（整理過）：

二號機連 1433 之後，pktmon counters 只回一句「所有計數器都已歸零」。連 80 之後（節錄）：

打 1433，這組篩選條件下一個封包都沒記到；打 80，網卡那一列收到 3 個、送出 2 個。對照組有、1433 沒有，所以優先查一號機前面。前面是一台 D-Link 路由器，它的 Inbound 過濾還是二號機的舊 IP，改掉之後 1433 就通了。真正把結論釘死的是最後這一步：改了路由器，連線就恢復。

這一步也走錯過一次。第一次抓完，Claude Code 用 pktmon etl2txt 把紀錄轉成文字，看到四百多行，一度判斷封包有到一號機。那幾百行其實是元件清單和計數器，跟封包無關。判斷有沒有封包，看 pktmon counters 就好。

pktmon 能同時看網路堆疊的好幾個元件，輸出裡有網卡、WFP、TCPIP 各一列。這裡看的是網卡那一列的 Lower 計數，比單看防火牆紀錄更接近封包實際進出網卡的地方，判讀起來也直接得多。

回頭看這四台

四台最後分別停在安裝來源、認證設定、防火牆規則，以及疑似上游過濾這幾個環節，沒有一台是照教學文三行指令就裝好的。

現在每裝完一台，我會從外面跑一次 PreferredAuthentications=none，括號裡只剩 publickey，再用指定的私鑰實際登入一次，兩個都過才算完成。看設定檔不算數。

下次再遇到「本機都正常、外面就是連不到」，我會先用 pktmon 在網卡上數封包、配一個對照組，用結果決定下一步是繼續查本機，還是請網路端一起追。
