Pinia 還是 Vuex？Vue 3 新專案與舊系統怎麼選

發表於2024-03-15|前後端開發
|總字數:1.2k|閱讀時間:4分鐘

這篇舊稿原本把 Pinia 寫成「也支援 Vue 2」，還用 tree-shaking 和一組沒有來源的體積數字來分勝負。到了 2026 年，前一句已經過時，後一句也把幾個不同概念混在一起。

先講我的選擇：新開的 Vue 3 專案直接用 Pinia。既有 Vuex 專案是否搬遷，則看 Vue 版本、外掛依賴與測試覆蓋率，沒必要為了跟上推薦名單就整批重寫。

官方定位已經很清楚

Pinia 官方介紹說明，它在 2019 年從 Composition API 的 store 實驗開始，後來吸收 Vuex 5 討論中的想法，最後成為 Vue 官方推薦的狀態管理方案。

Vuex 沒有因此突然失效。Vuex 3 對應 Vue 2，Vuex 4 對應 Vue 3，既有系統仍可以維護；只是新專案沒有太多理由再背 mutation、巢狀 module 與額外的 TypeScript 包裝。

還有一個版本陷阱：Pinia 最新主線只支援 Vue 3。需要 Vue 2 的專案得留在 Pinia v2 分支，不能把「Pinia 曾支援 Vue 2」寫成「最新版仍支援」。

TypeScript 的差距在哪裡？

Vuex 的 state 型別不難寫，麻煩通常出現在帶字串名稱的 getter、mutation、action，以及模組化後的型別包裝。Pinia 的 store 是一般匯入值，狀態與 action 多半能從 defineStore() 推斷，IDE 自動完成也比較直接。

「多半」不等於完全不必標註。Option Store 的 getter 若透過 this 讀取另一個 getter，仍可能需要明確回傳型別；外部 API 資料、可為空的 state 和複雜泛型也要自己定義。Pinia 改善的是推斷路徑，沒有取消 TypeScript 的型別設計工作。

模組與程式碼分割別混在一起

Vuex 以單一 store 搭配巢狀 module；Pinia 則讓每個 store 都有自己的 id，天生就是平坦命名空間。Vuex 的一個 module 通常可以對應成一個 Pinia store。

Pinia store 只在呼叫時註冊，不代表所有未使用程式碼一定會自動從 bundle 消失。能否切成獨立 chunk，仍取決於匯入關係與 bundler 的動態匯入邊界。比較準確的說法是：Pinia 的多 store 結構較容易配合路由層級的 code splitting，不該直接保證 tree-shaking 結果。

兩套工具都能接 Vue DevTools。Pinia 官方頁列出的體積約為 1.5 kB，但實際 bundle 還會受版本、格式與壓縮方式影響；拿一個固定數字宣稱 Vuex 必然大十倍，對選型沒有幫助。

哪些專案不急著搬？

以下情況可以先留在 Vuex：

  • Vue 2 系統還要維護，而且 Vuex 3 已經跑得穩定。
  • 大量依賴 Vuex 專用外掛、動態 module 或既有測試工具。
  • 沒有功能需求會碰到 store，遷移只會製造回歸風險。

以下情況適合開始搬：

  • Vue 3 新專案，尚未建立狀態管理層。
  • Vuex 型別包裝已經拖慢日常修改。
  • 正在拆除巢狀 module，或準備把大型 store 按功能分開。

官方 Vuex 遷移指南確認兩者可以在同一個應用裡共存，所以不必一次搬完。比較安全的順序是：

  1. 選一個依賴少、測試足夠的 Vuex module。
  2. 建立同 id 的 Pinia store，將 mutation 合併到 action 或直接賦值。
  3. 逐一替換元件裡的 mapState、mapActions 與字串 namespace。
  4. 確認 SSR、router guard、外掛和單元測試的初始化時機。
  5. 觀察一個發布週期，再搬下一個 module。

我的結論

新 Vue 3 專案選 Pinia，理由是官方定位、較短的 API 路徑與 TypeScript 推斷，不需要再搬出模糊的效能神話。

舊專案的答案比較現實。Vuex 若沒有造成維護問題，就讓它繼續工作；要搬時按 module 漸進處理，保留可以回退的範圍。狀態管理的價值是讓資料流容易理解，為了換工具而讓整個系統同時不穩，順序就反了。
