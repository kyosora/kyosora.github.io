TWCA 憑證換完 iPhone 跳不信任？IIS 少送一張憑證的修法

發表於2026-11-02|資訊安全系統與維運
|總字數:3.8k|閱讀時間:13分鐘

TWCA 在 10/31 發了更換憑證公告：舊中繼憑證 2026/11/06 00:00 前廢止（公告沒寫時區），受影響的站台要在那之前換上重新簽發的憑證。公告寫「收到新憑證後直接安裝即可」，也提醒要裝完整憑證鏈。

如果你的站台跑 IIS，照這句話做完，電腦和 Android 可能都正常，iPhone 卻跳不信任。公告沒提這件事，TWCA 另一頁說明才有寫。

我上個月才碰過同一個問題：客戶的 iPad 開圖台一片白。當時我找到缺的那張憑證，也寫下了結論。今天為了寫這篇回頭查證，才發現那個結論是錯的。

時間不多的話先看下一段，後面才講為什麼。文中的資料和實測都截至 2026-11-02，TWCA 的說明頁已經改過一版，動手前以官方最新內容為準。

這週 IIS 站台要做的事

這段適用於收到這次重簽通知、憑證裝在 IIS 上的站台。公告沒列受影響的中繼清單，不確定是否在範圍內就先問 TWCA。憑證如果裝在 IIS 前面的負載平衡器或反向代理上，TWCA 說可能不受影響，一樣要驗。

動手前先核對兩件事：

  • 有用 TLS 憑證做用戶端驗證的：TWCA 4/15 的公告寫新憑證鏈不再支援 clientAuth，緩衝期到 2027/02/28，期間有需求要在申請憑證前通知它。你這張重簽憑證實際帶什麼用途，要逐張確認。
  • 有做憑證釘選的：這次是原金鑰重簽，釘公鑰的不一定受影響，釘站台憑證或中繼憑證的要核對後更新。

這些動作會改到整台機器的憑證存放區，同機其他站台和對外 TLS 呼叫都可能受影響。先排維護時段，留好回復資料：現有的 PFX、netsh http show sslcert 的繫結紀錄，以及這次要刪除或搬動的憑證（匯出一份，記下指紋和原存放區）。這些只能撤回存放區和繫結的變更，舊站台憑證在舊中繼廢止後就不能當復原方案了。回復流程我沒有演練過，上線前自己走一次。

  1. 確認收到 TWCA 這次重新簽發的站台憑證，安裝到 IIS。還在用受影響舊中繼簽發的站台憑證時，只調整中繼鏈無法完成這次換證。
  2. 裝過 10/31 四層版的，先照官方那一節清掉舊中繼，尤其是簽發者為 Global Root、到期日 2030/10/30 的 G3。沒裝過的跳過。
  3. 把 uca_1、uca_2、uca_3_SSL（EV 憑證用 uca_3_EVSSL）裝進本機電腦的「中繼憑證授權單位」。
  4. 開 certlm.msc，把到期日 2047/11/22、簽發者是自己的 TWCA CYBER Root CA（SHA-1 指紋 F6B11C1A8338E97BDBB3A8C83324E02D9C7F2666），從「受信任的根憑證授權單位」搬到「沒有信任的憑證」。IIS 選到以自簽 CYBER Root 結束的路徑時不會送出 uca_1，這一步就是要避開它。
  5. 重新匯出 PFX，勾選「如果可能的話，包含憑證路徑中的所有憑證」，再匯回 IIS、重新繫結。PFX 含私鑰，密碼和檔案都要收好。
  6. 裝過 10/31 四層版、走補救流程的，依官方要求重新啟動 IIS。其他人驗到的還是舊鏈時，也先重新啟動再驗。
  7. 從外面驗證（指令在後面），再用 Chrome 和 iPhone 實機連一次，有 Java 呼叫的也實際跑一次。

完整步驟以 TWCA 說明頁為準。

上個月那台 iPad

回報很單純：iPad 開圖台一片空白，電腦和較新的 iPhone 都正常，清快取沒用。

我先想重現。Playwright 的 WebKit 加上 iPad 機型設定跑一輪，畫面正常，Chromium 也正常。回頭看也不意外：機型設定改的是 viewport、User-Agent 這些，不代表它跟那台實機有相同的信任清單。

後來改查頁面引用的每一台外部主機。主站沒事，但 ArcGIS JS API 和圖層從另一台主機載入，那台的憑證 10/14 剛換。

這比跳警告難查。那台 iPad 沒有出現憑證警告，只是內嵌資源載入失敗，地圖頁就白了。TWCA 寫的症狀是「不信任站台」警告，那是主站本身出問題的情況。出問題的如果是內嵌資源的主機，你可能只會收到一張白畫面截圖。

同一張中繼憑證，另一台主機就正常，差別在送出的張數：

主機 送出幾張 內容
圖資主機（白畫面） 2 站台憑證、TWCA SSL CA
另一台（正常） 3 多一張由 Global Root CA 簽的 CYBER Root CA（交叉憑證）

我當時在筆記寫下結論：舊 iPad 的信任清單太舊，沒有 2022 年才建立的 CYBER Root。解法兩條，請對方比照另一台裝交叉憑證，或把 iPadOS 更新。

更新系統那條是錯的，裝交叉憑證那條則漏了 IIS 的選路條件。

查了 Apple 清單，iOS 26 也沒有

今天動筆前，我想查「哪一版 iOS 開始收 CYBER Root」，好寫一句「升到 X 版就沒事」。結果翻完 Apple 官方 iOS 16、16.5、17、17.4、18、26 六份清單，一份都沒有，TWCA 只列了 Global Root CA 和 Root Certification Authority 兩張。

再查四家根憑證計畫共用的資料庫 CCADB，用的是 2026-11-02 下載的完整憑證報表，看 Certificate Name 和各家 Status 欄：

憑證 Apple Chrome Microsoft Mozilla
TWCA CYBER Root CA（自簽） Not Included Included Included Included
TWCA Global Root CA Included Included Included Included

所以更新 iPadOS 解決不了這個缺鏈問題。Apple 的清單沒有這張根，要接到 Global Root 就得靠交叉憑證。我筆記裡的「舊 iPad」三個字是錯的。

那支較新的 iPhone 為什麼正常，我解釋不了。機器不在我手上，沒辦法複驗。我當時被這條線索帶去「舊裝置」的方向，現在只能說不該拿一支手機下結論。

新憑證鏈為什麼長成五層

Apple 清單既然沒有 CYBER Root，留在 Global Root 看起來最省事，但這條路被 Chrome 擋住了。

Chrome Root Store（連結固定在我查的 2026-10-31 版本）對 TWCA Global Root CA 掛了這個限制，CYBER Root CA 則沒有：

Chrome 153.0.8010.0 以上，2026-09-14 之後才進憑證透明度紀錄的憑證，不能再靠這張根取得信任。TWCA 4/15 的公告也寫換鏈是「因應 Chrome 政策規定」，Mozilla bug 2017381 記錄 TLS 憑證從 2026/05/04 起全面改走 CYBER Root。同一張 bug 裡，TWCA 自己列了依賴條件：Apple 要收 CYBER Root。看上面的 CCADB，到 2026-11-02 還沒納入。

於是一條鏈要同時滿足兩邊：

TWCA 10/31 第一版給的是四層，G3 直接由 Global Root 簽，說明頁寫 Chrome 無法信任，之後才改成上面的五層。我對照那個 sct_not_after，推測原因就在這裡，TWCA 沒有明講。

這條路徑共五層，根憑證不必送，伺服器要送的是站台憑證加三張中繼，共四張。IIS 選到自簽 CYBER Root 那條路徑時，就會漏掉其中的 uca_1。

IIS 為什麼不送 uca_1

Microsoft 的兩份文件湊起來就是答案。一份說 IIS 用本機電腦環境建鏈，整條鏈扣掉根憑證後送給客戶端。另一份說有多條可信路徑時比分數，同分就選最短的：

If the scores for the multiple certification paths are the same, the shortest chain is selected.

文件最後一行寫著 This behavior is by design。

Windows 信任自簽的 CYBER Root，鏈建到那裡就結束，比 uca_1 那條短一層。我在開發機上跑了一次，把三張中繼都餵給 Windows 的鏈建構，用的是本機電腦環境：

輸出整理過，拿掉了 O、C 這些欄位：

最後一行就是自簽的根。uca_1 明明給了，Windows 沒選它。根憑證不送，客戶端只拿到前三張。我再把這三張拿去只信任 Global Root 驗證，verification failed，補上 uca_1 才 OK。

所以筆記裡「比照另一台裝交叉憑證」在 IIS 上光裝沒用。當時我沒測，看到另一台有就照抄。

範圍要講清楚：這個實驗只驗到 Windows 選路，我沒有實際綁一個 IIS 站台去連。結果跟微軟文件和 TWCA 說明頁描述的行為一致。

修法裡容易漏的幾件事

前面的步驟來自 TWCA。微軟文件建議刪除或停用多餘路徑上的憑證，TWCA 改成搬到「沒有信任的憑證」，方向相同。動手時注意這幾點：

  • 要搬的只有自簽那張，動手前對一下指紋。中繼憑證區同名、由 Global Root 簽的 uca_1 要留著。
  • 舊的 TWCA SSL CA 跟新的金鑰不同（我比對過 Subject Key Identifier），新站台憑證不會選到它，不必為了選路去動它。
  • 2022 年那張舊交叉憑證跟 uca_1 是同一把金鑰，都留在中繼憑證區時 Windows 選哪張我沒測。驗證時看輸出編號 3 那組的到期日：Nov 1 2030 是 uca_1，Dec 9 2030 是舊的。公告沒說舊的在不在廢止範圍，看到它就先問 TWCA，別自己猜。
  • 每次 Windows Update 重開機後重驗一次。TWCA 寫「不排除」設定自動失效，微軟也提到自動根憑證更新可能讓不想要的憑證再度生效。
  • 這個設定要留到 TWCA 通知為止，它說會在 uca_1 到期（2030/11/01）前另行通知。要復原，到「沒有信任的憑證」把那張刪掉即可。

我這台開發機沒有動本機憑證區，搬根憑證和重綁 IIS 這段我沒親手跑過，先在測試機走一遍再上正式機。這台伺服器自己當客戶端去連別的 TWCA 站台時行為會不會變，我也沒測，同機其他站台和對外呼叫要一起驗。

Java 也會中

iPhone 只是比較容易被回報。後端服務如果信任清單裡沒有 CYBER Root，也會遇到一樣的問題。我 2026-11-02 在開發機上測：

客戶端 清單裡有 CYBER Root？ 少了 uca_1 四張都有
Oracle JDK 17.0.12 沒有 PKIX path building failed OK
Oracle JRE 8u431 沒有 PKIX path building failed OK
Python certifi 2025.01.31（用 OpenSSL 載入這份清單驗） 有 OK 沒測
Node.js 22.22 有 沒測 沒測

OpenJDK 主線的 cacerts 同一天查也只有 twcaglobalrootca。別的系統用 Java 呼叫你的 API 時，你少送 uca_1，對方就可能看到 unable to find valid certification path。

Mozilla 是 2024 年的 NSS 3.104 才收這張根，比那更舊的 Node、certifi 清單裡可能沒有，舊 Android 的系統清單我也沒測。對信任 Global Root、失敗原因又是缺 uca_1 的客戶端，伺服器把鏈送完整就解決了。上個月 eMudhra 那篇碰到的也是這件事：每個執行環境各看各的清單。

這週為什麼突然要換

公告只寫「因應國際規範要求調整中繼憑證規格」，沒有寫原因，也沒列哪些中繼在廢止範圍，你手上的憑證請以 TWCA 通知為準。

公開紀錄裡對得上的是 Mozilla bug 2087236：外部研究者回報 TWCA 的 CA 憑證序號最多只有 24 bits 看起來是隨機的，規範從 2016 年起就要求 64 bits。TWCA 已回應正在調查，承諾 2026/11/12 19:00 UTC（台灣時間 11/13 03:00）前更新完整報告。另一張 bug 回報站台憑證的序號只有 63 bits，TWCA 說會併在同一份報告處理。我推測兩者跟這次更換有關，gslin 的文章也提出類似的推測，公告沒有證實。

我那份筆記

這次最尷尬的是那份筆記，寫得很有把握。如果上個月就把它發成文章，就會有人照著去叫客戶升級 iPad。

又一次被靜默的白畫面耍了。那份筆記我已經改了。
