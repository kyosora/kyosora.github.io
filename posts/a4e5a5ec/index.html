PHP2Shell 是什麼？緩解設定寫錯地方，一個 .htaccess 就蓋回去

發表於2026-10-22|資訊安全系統與維運
|總字數:8.2k|閱讀時間:31分鐘

10 月 21 日晚上，PHP 官方發布緊急安全更新，修掉兩個不用登入就能遠端執行程式碼的漏洞。官方事先預告的發布時間是台灣晚上 10 點、日本晚上 11 點；日本那邊從當天傍晚起，pixiv、《賽馬娘》、《碧藍幻想》陸續進入緊急維護。連阿部寬那個以輕量出名的官網，都因為 Nifty 緊急維護打不開。

政府機關也停了。日本財務省暫停官網上用 PHP 跑的內容，大阪府從日本時間 23:40 起停了 12 項檢索類功能，主機商エックスサーバー則把整個集團的服務網站和管理介面都關了。日本資安部落客 piyokango 的整理，到日本時間 22 日凌晨 1 點多，已經數到 211 個組織，每一筆都附官方公告。歐洲當時是白天，荷蘭政府在修補發布前，就把政府登入系統 DigiD、MijnOverheid.nl 等網站預防性下線。

隔天早上，我看到旅行遊戲「ワールドクエスト」宣布結束服務的新聞。營運方在官方 X 上寫得很直白：伺服器使用的 PHP 本身被公布有嚴重漏洞，系統太舊沒辦法做足對策，為了保護大家的資料，即日結束服務。到了上午，營運超過十年的《僕の魔界を救って！》也宣布收掉。

我不寫 PHP。看到新聞的第一個反應是：跟我無關。

可是我管的是 IIS，做的是要過弱掃的政府案。我很確定自己的案子沒用 PHP，但「很確定」只是印象。所以我先把自己這台開發機查了一遍，順手把查的方法整理成腳本。過程中踩到的坑，比查到的結果有意思。

PHP2Shell 是什麼

PHP2Shell 是 CVE-2026-109618 和 CVE-2026-109619 兩個漏洞的合稱，PHP 官方給的 CVSS v4 分數都是 9.2。兩個都出在 PHP 直譯器本身，也就是用 C 寫的那個核心，跟你用什麼框架、程式寫得好不好都沒關係：

  • CVE-2026-109618：解析 POST 時記憶體用完，PHP 中途放棄，留下一個建到一半的資料結構，後面的清理程式卻把它當正常資料處理。
  • CVE-2026-109619：PHP-FPM、mod_php 的 worker 會重複接 request，某些路徑會撿到上一個 request 沒清乾淨的狀態。主要路徑是上傳進度追蹤（session.upload_progress），這個功能預設開著，程式沒呼叫 session_start() 也會跑。

讓我最在意的是觸發的時間點。Datadog 的研究團隊重現 109618 時，錯誤 log 長這樣：

在這次重現裡，錯誤發生在請求初始化階段，應用程式還沒開始執行。放在 PHP 應用程式裡的登入驗證和輸入檢查，來不及攔住這條路徑。 預設啟用的功能就包含受影響的程式碼，不必先寫出有漏洞的應用程式；問題程式碼又是從 2012 年的 PHP 5.4 就在了。難怪日本那邊整晚在停機。

受影響的跑法，官方列了 PHP-FPM、Apache mod_php、php-cgi、FrankenPHP、LiteSpeed，其中 mod_php 風險最高。官方和幾家資安公司的分析都沒有特別提到 Windows 或 IIS，不過 IIS 跑 PHP 最常見的做法是 FastCGI 加 php-cgi.exe，php-cgi 就在清單上，所以我把 IIS 也算進受影響範圍。這是我的推論，沒有官方背書。

這次還多一段插曲。修補原本協調在 10 月 22 日公布。照 PHP Foundation 事後的說明，10 月 20 日 15:00 UTC 左右，兩個 CVE 編號開始在論壇和社群上流傳，附的公布時間是錯的，分數也寫錯（寫 CVSS 10.0），技術細節倒是沒有外流。其中一則是 Hacker News 上的貼文，引述「可靠消息來源」、沒附證據，很快被撤下，截圖已經傳到 X 和 Mastodon；資安公司 watchTowr 也出面確認漏洞是真的。PHP 團隊在 19:30 UTC 提前發出預告，把發布改到 10 月 21 日。當時沒有立即釋出修補，是因為各發行版還在打包；PHP Foundation 說，提前一天發布是折衷。之後又發生兩件事：回報漏洞的資安公司 Calif 誤發了一支影片，PoC 跟著加速冒出來；Chainguard 在協調時間前六個多小時，提前推出含修補的 image。

同一篇說明裡還有一段自白。2024 年，PHP Foundation 委託的核心開發者在修外部安全稽核回報的問題時，就看到 109618 這個記憶體不足問題的初步跡象。當時推測過可能被拿來攻擊，但找不到具體的攻擊路徑。修法有好幾種，各有取捨，安全團隊採共識決，遲遲選不出來，修補工作停停走走，拖了好幾個月。PHP Foundation 自己的說法是「structural failure」，原因出在決策流程和人手不足。直到今年 8 月 11 日，Calif 回報同一個根因可以無條件遠端執行，修補才變成第一優先。

不寫 PHP，機器上還是可能有 PHP

會在 Windows 伺服器上冒出 PHP 的，通常是這幾種：

  • 官網或活動頁用的 WordPress
  • 管資料庫用的 phpMyAdmin
  • Zabbix 前端、Moodle 這類用 PHP 寫的系統
  • 廠商交付的系統，安裝包裡自帶一份 PHP
  • 某個人為了測試裝的 XAMPP，裝完就忘了

最後一種最容易被忘掉。XAMPP 預設的 Apache 設定載入的是 php8apache2_4.dll，也就是官方說風險最高的 mod_php。

這兩件事我整理成一支盤點腳本，完整內容放在文末附錄。它只讀 IIS 設定和檔案內嵌的版本資訊，不會執行找到的任何程式，正常跑完時會列出哪些範圍查完、哪些沒查成。

「不執行」是改過的。第一版會用系統管理員直接跑掃到的每一支 php.exe 來讀設定，送 Codex 審稿時被點出問題：低權限的使用者可以在自己寫得進去的目錄放一個同名程式，系統管理員直接去執行它，就跨過了原本的權限界線。所以現在拆成兩段，盤點只看不跑，要讀設定時再對你確認過的那一支 PHP 單獨探測。

掃磁碟也改了兩次。第一版用 where.exe /r，跑了 11 分鐘還沒掃完 C 槽。改成 dir /s /b 之後，掃到兩份我不認識的 php.exe，在另一個本機帳號的目錄底下。追下去，那是 Codex 沙箱的工作目錄，一個指回我家目錄的 junction。dir /s 會跟著 junction 走，同一份檔案算兩次，整個家目錄也掃了兩遍。

最後換成 robocopy 的清單模式，/L 只列不複製，/XJ 不跟 junction 走。同樣掃 C:\Users，dir /s 要 377 秒、多報兩筆假的，robocopy 150 秒、結果正確。C、D、E 三顆全掃，robocopy 版跑了兩次，333 秒和 524 秒，差多少看機器當時忙不忙；dir /s 版是 602 秒。

Linux 上先看有沒有 PHP 相關的程序在跑，再看 Apache 有沒有載入 mod_php：

apache2ctl 是 Debian 系的名字，RHEL 系用 httpd -M；2>/dev/null 會把「指令不存在」也藏起來，空輸出不代表沒有 mod_php。

版本號要小心兩件事。第一，Debian、RHEL 這類發行版常把修補 backport 回舊版號，8.2.x 沒到 8.2.35 不代表沒修，要看發行版自己的公告。第二，php -v 是命令列那份 PHP，不一定是網頁在跑的那份，下一節會看到差多少。

暫時不能升級：緩解設定的三個坑

能升級就升級。官方公告講得很清楚：只有升級是完整解法，暫時緩解只能降低特定攻擊路徑的暴露，不會讓沒修補的機器變安全。下面摘出跟本文相關的幾項，完整內容看官方安全公告：

  • memory_limit = -1：拿掉「PHP 記憶體上限」這個能被攻擊者控制的失敗條件，但底層的記憶體配置失敗還是可能走到漏洞路徑。官方要你用應用程式蓋不掉的方式設，並且確認沒有任何 pool、目錄或應用程式設定把上限加回去。記憶體改用 container 或 cgroup 當邊界，最好只砍出事的那個 worker；不要用 RLIMIT_AS、RLIMIT_DATA 代替，那反而會觸發漏洞要的配置失敗。
  • session.upload_progress.enabled = 0：擋 109619 已確認的上傳路徑。官方要求用「解析請求之前就生效」的設定，php.ini、FPM pool 或伺服器設定都行，明講不要靠 ini_set() 或 FPM 的 .user.ini。
  • post_max_size 壓到 8M（不需要上傳）或 32M（需要上傳），upload_max_filesize 要比它小。改之前先確認業務上的上傳需求，IIS 這層的 maxAllowedContentLength 也要另外從 IIS 查。
  • PHP 8.5 另外加 fatal_error_backtraces = 0。

改完要重啟所有 worker。

Windows 上沒有現成的 cgroup 可以搭。我的判斷是，IIS 上的 PHP 與其開 -1，不如先把對外連線擋掉，再排時間升級。

問題是「設在哪裡」。我讓 Claude Code 在本機 Docker 開了 PHP 8.4.26（修補前的最後一版）官方 image 來測，踩了三個坑。測試環境：2026-10-22，php:8.4.26-apache（sha256:60111400ff77…）和 php:8.4.26-fpm（sha256:f5431b57bda7…）。

坑一：官方 Docker image 根本沒有 php.ini

image 裡附的 php.ini-development 和 php.ini-production 只是範本，不會自動生效。這個 image 沒載入主要的 php.ini，量到的 session.upload_progress.enabled 是預設值 1；額外載入的 ini 要另外看掃描清單。要改設定，得放進 image 已經設定好要掃描的 $PHP_INI_DIR/conf.d/，或自己把範本複製成 php.ini。如果你的 Dockerfile 只改了範本，回去確認一下。

反過來的情況也有。Debian、Ubuntu 的套件，CLI 和 FPM 本來就是兩份 php.ini（/etc/php/8.x/cli/ 和 /etc/php/8.x/fpm/），改到 CLI 那份，php -i 會告訴你設好了，網頁那邊其實沒動。

開頭那行檢查，只在 PHP 直接看得到用戶端來源時有效。前面有同一台機器上的反向代理，外部請求轉進來時 REMOTE_ADDR 也會是 127.0.0.1，等於對全世界公開。這種環境要先在對外入口擋掉這個路徑、確認外面連不到，再從本機驗證；不要改成去信任 X-Forwarded-For。

在這次的 Docker 網路配置下，從容器內連看得到設定，從宿主機經 port mapping 連進去回 404。scanned 那行會列出 conf.d 載入了哪幾份 ini，緩解檔有沒有被讀到，一眼就看得出來。同一個站台底下不同子目錄、多台節點都可能不一樣，驗證要做到應用程式和每一台機器。

這證明的是「這次請求看到的設定」，不等於證明漏洞已經打不進來。

坑三：寫在 php.ini，會被 .htaccess 和 .user.ini 蓋回去

這是我覺得最該寫出來的一條。很多人改緩解的直覺是動 php.ini，但網站目錄裡還有兩個地方能改設定：mod_php 在 Apache 允許 PHP 設定指令時（AllowOverride 含 Options 或 All，這次測的官方 image 是 All）會讀 .htaccess；CGI、FastCGI、FPM 會讀 .user.ini。我們在網站目錄放了這兩個檔：

實測結果，用 ini_get() 讀網頁執行時的值：

跑法 緩解寫在哪 放了覆寫檔之後
mod_php php.ini（conf.d/） 被蓋回 1、512M

每次改設定我們都重啟了 FPM，所以不受 .user.ini 預設 300 秒快取影響。

官方公告那句「確認沒有任何目錄設定把上限加回去」，這張表就是在示範它怎麼被加回去。要講清楚的是，表裡量的是腳本執行時讀到的值。漏洞發生在請求初始化，這些目錄覆寫在初始化的哪個時間點生效、會不會重新打開攻擊路徑，要看各 SAPI 的處理順序，我沒有實測攻擊。所以結論是：只檢查 php.ini 不能算驗收，緩解要寫在目錄蓋不掉的地方。

（中間有一段白忙。Claude Code 第一次測 .user.ini 時，用 cgi-fcgi 直接打 FPM，沒帶 DOCUMENT_ROOT，PHP 就不會去找 .user.ini，結果看起來 php_value 也擋得住。補上 DOCUMENT_ROOT 重跑才現出原形，差一點就照錯的結論寫了。）

各種跑法的設定方式與覆寫限制

FPM 就是前面那份 pool 設定，用 php_admin_value，不要用 php_value。

user_ini.filename = 我是在 FPM 上測的，官方 Docker image 裡沒有 php-cgi；PHP 文件寫明這個機制由 CGI/FastCGI 處理，IIS 的 php-cgi 走的是同一套。關掉之前先看目前 user_ini.filename 設成什麼（不一定叫 .user.ini），把各站台靠它設定的項目搬回 php.ini，不然上傳大小、時區這類設定會跟著失效。它只關掉這一個機制，啟動參數和伺服器層級的設定照樣能改值，強度比不上 php_admin_value。IIS 改完 php.ini 要回收應用程式集區，php-cgi 才會重讀。

升級不了、也鎖不住的時候

8.1 以下的分支官方不會再發新版。有些系統就是升不上去：廠商倒了、程式依賴舊的 extension、沒有人看得懂。如果連廠商修補、LTS 都找不到，也沒辦法做出驗證得了的暫時防護，就先撤掉對外入口；撤不掉的，就停用。撤掉外網之後，內網哪些來源還連得到，也要再看一次。

《僕の魔界を救って！》的公告，把「升不上去」寫得很具體：

「僕の魔界を救って！」は、サービス開始から10年以上が経過しており、サーバーはPHPを含め、かなり古い環境の上で動き続けています。

これまでも可能な範囲で修正やメンテナンスを続け、遊んでくださる方が少なくなってからも、できる限りこの場所を残したいと思い、サーバーを維持してきました。

しかし今回の問題については、現在のシステムやハードウェアのまま安全に対応することが難しく、OSやPHPを新しい環境へ移行することも現実的ではない状況です。

大意是：服務已經超過十年，伺服器連同 PHP 都跑在相當老的環境上。他們一直在能力範圍內修補、維護，玩家變少之後也想盡量把這個地方留著。但這次的問題，難以在現有的系統和硬體上安全處理，把 OS 和 PHP 搬到新環境也不切實際。公告最後說，作品本身不打算就此結束，哪天有機會換個形式回來，「そのときは、また魔界を救いに来てください」，到時候請大家再來救一次魔界。

兩款遊戲都選了停用。ワールドクエスト在修補版公布當晚 23:21（日本時間）就對外宣布；《僕の魔界を救って！》隔天宣布，公告表示不能在玩家資料面臨風險的情況下繼續營運。站在玩家的角度很可惜，站在維運的角度，我認為這是負責任的決定：修不了的東西繼續開在外網，就只是在賭運氣。

改完之後，留下這幾樣紀錄

做政府案的都知道，修完不留紀錄等於沒修。這次我會留四樣：

  1. 盤點的範圍和時間，包括哪些地方沒查成（權限不足、讀取失敗、沒查的主機）。
  2. 每支 PHP 的版本，以及對應的官方、發行版或廠商修補公告。
  3. 每個站台經探測頁驗證的設定值（做到應用程式和每台節點），和舊 worker 已經重啟的確認。
  4. 改完之後登入、表單、上傳、排程這些基本功能的回歸測試。

弱掃沒掃到、本機沒找到檔案，都不能單獨拿來證明不受影響。

我這台的結果

IIS 伺服器層級的 FastCGI 註冊 0 筆；C、D、E 三顆磁碟都標「完成」，只找到我為了測試下載的那份 PHP 8.4.26（php.exe、php-cgi.exe），腳本也正確標成「低於官方修補版 8.4.27」。在這次掃描涵蓋的範圍和檔名條件內，沒有找到其他 PHP 候選檔案。

至少這台的「確定」是查過的。案子那幾台伺服器還要各自盤點，再對照實際的站台、跑法和修補紀錄。

下次再遇到這種執行環境本身出事的漏洞，我會先盤點服務，再沿著實際服務的路徑驗證設定，不再先信命令列。

附錄：盤點腳本

下面這支是 Claude Code 照我的需求寫的，在我這台機器上實際跑過，前後改了幾版才定稿。兩種用法：

  • 盤點（預設）：用系統管理員、64 位元的 PowerShell 跑 .\php-inventory.ps1。只讀 IIS 伺服器層級的 FastCGI 註冊和檔案內嵌的版本資訊，不執行找到的程式。正常跑完會列出盤點範圍，每一段標明「完成」「部分完成」或「沒查到」；只要有一段沒查完，就不會說「沒找到」。
  • 探測（-Probe）：用一般權限跑 .\php-inventory.ps1 -Probe -Path <php-cgi.exe> -PhpRc <目錄>，只執行你指定的那一支 PHP，讀出它載入的 php.ini 和設定值。會在 %TEMP% 建一個暫存檔，結束時刪掉，刪不掉會提示。

幾個設計上的細節：

  • 版本是讀執行檔內嵌的版本資訊。PHP 官方的 Windows 版有這個欄位（ProductName 是 PHP），不用執行就讀得到；讀不到或寫的不是 PHP，只標「無法確認」，不替你下結論。狀態只比版本號，發行版或廠商 backport 的修補要對照他們的公告。
  • 探測時用 -d 清空 auto_prepend_file 和 auto_append_file。我故意做了一份 php.ini 指定一支會印出 PREPEND-RAN 的 prepend 檔：直接跑 php-cgi 會印出來，用 -Probe 跑不會。extension 照樣會載入，所以探測對象還是要先確認來源。
  • 探測結果包成 JSON 傳回來，路徑裡有逗號、@、| 都不會把欄位切錯。
  • robocopy 要是根本沒跑起來，$LASTEXITCODE 會留著上一支程式的值。前一版就因為這樣，會把沒掃到的磁碟標成「完成」，是第三輪送 Codex 審稿時抓到的。現在呼叫前先清掉，沒啟動一律標「沒查到」。
  • 存檔要用 UTF-8 with BOM。PowerShell 5.1 會把沒 BOM 的檔案當系統代碼頁讀，台灣預設的 950 會把中文讀成亂碼。我這台剛好開了系統層級的 UTF-8（代碼頁 65001），沒 BOM 也正常，差點就以為這條是多慮。

-PhpRc 的效果，拿官方 PHP 8.4.26 Windows 版實測（路徑縮短過）：

同一個 php-cgi.exe，帶不帶 PHPRC，載入的設定來源和結果都可能不同。探測只能幫你辨識它載入哪份 php.ini，不能取代站台端的驗證：IIS 實際的請求還有 FastCGI 參數、其他環境變數、應用程式集區身分、站台目錄的 .user.ini，探測都沒有重現。

（改版時還踩到 PowerShell 變數不分大小寫：暫存檔變數 $probe 跟參數 $Probe 是同一個變數，出錯後腳本照樣往下跑，輸出看起來一切正常。是測試腳本把那行錯誤印出來才發現的。）

範圍限制：只掃這台機器 NTFS、ReFS 的固定磁碟，不跟 junction 走；只認 php.exe、php-cgi.exe 和常見的 mod_php DLL 命名，改過名的找不到；其他主機、容器、WSL、VM 要另外查。
