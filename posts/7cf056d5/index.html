NIKKE 啟動器被下毒後，我回頭查部落格：13 個 CDN 資源，0 個有 SRI

發表於2026-11-05|資訊安全前後端開發
|總字數:4.2k|閱讀時間:15分鐘

2026 年 11 月 4 日，《勝利女神：NIKKE》的發行商 Level Infinite 在 X 上發了一則很短的聲明：PC 啟動器的腳本檔案可能遭第三方竄改，已經推出修正，影響範圍還在調查。

讓我停下來的是研究者報告裡的一個細節。被改的檔案裡有一支叫 images.7fec4c32.js，檔名看起來帶著打包工具產生的 hash。但那串字只是網址的一部分，瀏覽器不會拿它驗證檔案內容。有人直接覆寫 CDN 上同一個路徑，檔名不變，啟動器照樣載入。

我沒裝 PC 版，不用擔心中招。我問 Claude Code 這件事值不值得寫，它沒先回答，直接去搜我部落格 build 出來的 HTML 裡有沒有 integrity。

零筆。

先講事件：一支被換掉的 JS 怎麼變成後門

以下截至 11/5。官方表示腳本可能遭第三方竄改、已推出修正；下面的攻擊鏈細節來自研究者 MotherSphere 的靜態分析報告，他附了檔案 hash 和時間線，但還不是官方說法。

  1. 9 月 27 日，Level Infinite CDN 上有四支 JS 被改。啟動器內嵌了瀏覽器，介面有一部分是從 CDN 載入的網頁。
  2. 注入的程式碼在頁面插一個 <script>，去載 insightjs.com/l.js，載完把標籤刪掉。
  3. l.js 呼叫啟動器開放給網頁的 JS 橋接 Srv_DownloadFile，下載一支 LuaJIT 後門在啟動器裡執行，再用 COM 劫持留在電腦上。
  4. 後門能偷 NIKKE 帳密、瀏覽器存的密碼和 Cookie、28 種加密貨幣錢包擴充功能的資料，也能截圖。

報告裡最早的感染紀錄在 10 月 23 日。官方修正之後，研究者還觀察到部分 CDN 邊緣節點繼續送舊檔，啟動器的快取又設了 90 天。攻擊者怎麼取得修改這些檔案的能力，公開資料還沒有交代。

依研究者描述的攻擊鏈，這是透過官方發行管道投毒的供應鏈攻擊。玩家不必另外下載來路不明的程式，正常打開官方啟動器、連上官方 CDN，就可能收到被植入後門的檔案。

如果你有裝 PC 版：研究者建議先查安裝目錄下的 Launcher/intl_service/debug.log 有沒有 k2f_chan registered。沒查到也不能就此判定沒中，完整的自查步驟和工具在他的報告裡。

做桌面程式的人應該看得出第三步有多致命：從網路載入的網頁內容摸得到原生功能，啟動器又要求系統管理員權限。CDN 一被改，就等於能在玩家電腦上遠端執行程式。Electron 和 WebView 社群講了很多年的教訓，這次又上演一次。

回到網頁這端。這條攻擊鏈提醒我，從信任的 CDN 載入，不代表檔案內容沒被換過。而我自己的部落格，也沒有用 SRI 驗證任何一個外部資源。

我的部落格：13 個 CDN 資源，0 個 integrity

部落格是 Hexo 7.3.0 加 Butterfly 5.5.4 主題，部署在 GitHub Pages，build 用 Node 22。build 完直接搜產出：

第二行是純文字盤點，再對照標籤和主題裡的動態載入呼叫，確認實際用到 13 個 jsdelivr 網址。10 個寫在 <script> 和 <link> 標籤裡：Butterfly 自己的 4 支 JS、fancybox 的 JS 和 CSS、Font Awesome、分享按鈕的 JS 和 CSS、instant.page。另外 3 個是 mermaid、chart.js、infinitegrid，頁面需要時才由 JS 臨時插進來。

13 個，沒有一個帶 integrity。jsdelivr 上任何一支被換掉，每個讀者的瀏覽器都會照單全收。

Subresource Integrity（SRI）做的事很單純：你先把檔案的 hash 寫進標籤，瀏覽器下載完自己算一次，對不上就不執行。

跨來源的 script 和 stylesheet 要加 crossorigin="anonymous"，瀏覽器才會走 CORS 請求、拿得到內容驗 hash。CDN 那端也要回傳允許跨來源存取的標頭，jsdelivr 有；換成自架的 CDN，只加屬性、伺服器不配合，檔案一樣載不進來。

先說清楚 SRI 的邊界。hash 寫在 HTML 裡，所以它防的是「HTML 沒事、外部檔案被換」。如果攻擊者連 HTML 都改得到，把 hash 一起換掉就好。NIKKE 那邊載入四支 JS 的頁面放在哪、攻擊者的權限有多大，報告裡沒有答案，所以我不確定 SRI 救不救得了他們。

我的情況單純很多：HTML 在 GitHub Pages，JS 在 jsdelivr，兩邊分開。jsdelivr 出事，HTML 裡的 hash 還在，正好是 SRI 擋得住的情況。對我來說 jsdelivr 是供應商，SRI 防的就是這一段供應鏈。

坑一：hash 要跟誰要

實作我交給 Claude Code，它寫了兩支腳本：一支手動跑，算 hash 寫成 lock 檔；一支掛在 Hexo build 流程裡，把 hash 補進 HTML。方案是它提的，我拍板兩件事：Butterfly 內部腳本改由自己的站送（原因下面講）；lock 檔沒登錄的網址只在 build 時警告、不擋 build。

（pipefail 加上分開賦值是必要的。拿一個不存在的網址試過一行版的 echo "sha384-$(curl ... | openssl ...)"：curl 失敗了，它照樣印出 sha384-OLBgp1GsljhM2TJ+sbHjaiH9txEUvgdDTAzHv2P24donTt6/529l+9Ua0vFImLlb，exit code 還是 0。那串是空字串的 SHA-384，看起來跟正常的 hash 一模一樣。）

問題在於它跟 CDN 要內容。如果 CDN 這時候已經被動過，你就把惡意版本的 hash 鎖進自己的 HTML，之後瀏覽器反而會確保每個讀者拿到的都是惡意版。

需要一個跟 jsdelivr 無關的比對基準。套件裡實際存在的檔案，jsdelivr 的 /npm/ 路徑會原樣送出，所以拿 npm registry 上同版本的 tarball 來比。npm pack 下載時會用 registry 記錄的 integrity 驗過整包 tarball，解壓後再對單一檔案算 SRI 用的 hash。Claude Code 寫的 sri-pin.js 核心長這樣（節錄，完整版多了錯誤處理和報告輸出）：

要注意這個比對能證明的範圍：它只能確認 CDN 沒有送出跟 npm 不同的內容。如果發佈到 npm 的那個版本本身就被下毒，兩邊會一模一樣，這個檢查抓不到。

腳本還沒寫完，Butterfly 那 4 支就先出問題。網址指的是 main.min.js，可是打開 node_modules/hexo-theme-butterfly/source/js/，只有 main.js，套件裡根本沒有 .min 檔。jsdelivr 遇到不存在的 .min 檔會自動壓一份並保存起來，所以這 4 支在 npm 上找不到對應的檔案，hash 只能跟 jsdelivr 本人要。

另外兩個是 fancybox.min.css 和 instantpage.min.js，原因一樣。算下來，13 個網址裡有 7 個是 jsdelivr 自動壓縮產生的檔案，npm 套件裡沒有對應的成品。

最好笑的是 fancybox：jsdelivr 自動壓的 fancybox.umd.min.js 是 104,864 bytes，套件裡的原檔 fancybox.umd.js 是 104,403 bytes。原檔本來就壓過，jsdelivr 再壓一次，反而多了 461 bytes。

解法分兩路。Butterfly 內部腳本改由自己的站送，這 4 支就不再依賴第三方 CDN。我把自己的站和 build 流程當作信任範圍，所以沒替它們加 SRI。第三方套件則在主題設定裡改指原檔：

instant.page 的原檔沒壓過，gzip 後從 1,699 bytes 變成 4,051 bytes，多 2.3KB，可以接受。代價是這三個版本號寫死了，之後 Butterfly 升級，這裡要自己手動跟著改。

坑二：mermaid 是 JS 臨時插進來的

扣掉改成自己送的 4 支，標籤裡剩下 6 個 CDN 資源。Butterfly 5.5.4 原始碼裡完全沒有 integrity 支援，所以寫一個 Hexo 的 after_generate filter，build 時掃每頁 HTML，命中 lock 檔的網址就補上 integrity 和 crossorigin。

（lock 檔原本想放在 filter 旁邊，結果發現 Hexo 會把 scripts/ 底下每個檔案都當 plugin 載入，不看副檔名，JSON 放進去會被當 JS 執行。最後 lock 放 repo 根目錄，算 hash 的腳本放 tools/。）

剩下的 3 個麻煩多了。mermaid、chart.js、infinitegrid 在 HTML 裡只有一段 inline script，頁面有圖表時才呼叫 btf.getScript('https://cdn.jsdelivr.net/npm/mermaid@11.12.2/dist/mermaid.min.js') 臨時插入 <script>。filter 改的是 HTML 標籤，改不到這種。

翻主題原始碼，btf.getScript(url, attr) 會把第二個參數的每個屬性 setAttribute 到 script 元素上，再插進頁面。所以不用改主題，包一層就好：

實際注入的是 filter 依每頁內容產生、壓成一行的版本，map 裡只放那頁用得到的網址。

這段的執行時機有講究：要在 btf 定義之後、第一次動態載入之前跑。順序錯了，btf 還不存在，函式就直接 return，保護悄悄消失，不會有任何錯誤。Butterfly 把 btf 定義在 <head> 的 inline script 裡，所以插在 </head> 前面剛好。另外 utils.js 後面會用 window.btf = { ...window.btf, ...btfFn } 重組 btf，如果 btfFn 也有 getScript，包裝就被蓋掉了。查過沒有。我沒開 PJAX；有開的話，記得測從首頁站內切換到圖表頁的情況，不能只測直接開啟。

故意改壞一個 hash

全部接好之後，build 結果是 940 頁、4242 個標籤補上 integrity，9 個 jsdelivr 網址全部鎖進 lock 檔。

先用 Playwright 開首頁和一篇有 mermaid 圖的文章：標籤上的 4 個 CDN 資源都帶了 integrity，動態插入的 mermaid script 也有，圖正常畫出來，console 零錯誤。站上目前沒有用到 chart.js 和 infinitegrid 的頁面，這兩個只確認了 lock 和注入的包裝有寫進去，沒在瀏覽器實際跑過。

接著做真正想看的測試：複製一份首頁，把 fancybox 那筆 hash 改掉一個字元，用 Playwright 打開。

瀏覽器擋下來了，window.Fancybox 是 undefined。mermaid 那頁照做，動態插入的 script 一樣被擋，圖沒畫出來。

但 console 裡還有第二個錯誤：

hash 對不上，SRI 就拒絕載入；我的主題又沒處理依賴缺失，部分初始化跟著中斷。 前者是 SRI 該做的事，後者是 Butterfly 的 main.js 沒檢查 Fancybox 在不在就直接呼叫。jsdelivr 哪天真的被換檔，我的站會壞掉一部分。頁面少了圖片燈箱，總比在讀者瀏覽器裡跑別人的程式好，這個交換我接受。

真的遇到這種錯誤，先查是誰變了。不要為了讓頁面恢復，就自動重算 hash 或把 integrity 拿掉，那等於親手把門打開。

SRI 的保護範圍，和剩下的缺口

  • Google Analytics 的 gtag.js：同一個網址的內容會更新。
  • Google Fonts 的 CSS：依瀏覽器回傳不同內容。SRI 允許寫多組 hash，但版本和變體很難列全、持續維護，我目前沒有可靠的做法，所以這兩類沒加。
  • Font Awesome CSS 再去載的字型檔：SRI 只驗 CSS 本身，管不到它再載入的東西。
  • GitHub Pages 本身：HTML 被改，hash 一起被改，SRI 無能為力。

2024 年的 polyfill.io 事件剛好是對照組。polyfill.io 依瀏覽器回傳不同的 polyfill，要預先列出並維護每一種回應的 hash 很困難，很難套用這篇這種「固定版本、固定內容」的流程。網域換了主人開始下毒時，網站能做的是立刻停止載入，再改用可信的替代來源（Cloudflare 當時就提供了鏡像），或自己 build、自己託管。NIKKE 被改的是四支靜態檔，比較適合預先鎖住 hash；但能不能擋下這次攻擊，還是要看載入頁面和 hash 本身是不是也在攻擊者手裡。

還有一個一般性的限制：SRI 只驗你標了 integrity 的那支檔案。它如果再去載別的程式碼，那些請求不會自動繼承入口檔的保護。

CSP 可以再擋一層，但要看政策怎麼寫。如果啟動器有實際生效、只允許指定來源的 CSP，額外去載 insightjs.com 的請求可能會被擋下。問題是只檢查來源的 CSP，看不出白名單 CDN 上的檔案被塞了東西，攻擊者大可把 l.js 整段塞進被改的檔案，不必再去外面載。GitHub Pages 沒有提供自訂回應標頭的設定，不加反向代理，我只能用 <meta> 設 CSP，部分指令（例如 frame-ancestors）用 <meta> 設不了，這部分我還沒動。CSP 的設定方式我之前寫過一篇 Content Security Policy 實戰。

升級主題時，還有一次檢查要做

現在的流程是：升級主題或第三方套件 → build → 跑 sri-pin 更新 lock → 再 build。

我選了「lock 沒登錄只警告、不擋 build」。這代表哪天我升級完忘了跑 sri-pin，新的 CDN 網址會在沒有 SRI 的情況下上線，只在 build log 裡留一行警告。對個人部落格來說，我接受這個風險；如果是公司專案，要求完整覆蓋，就該讓未登錄的網址直接擋住發佈。

SRI 聽起來只是每個 script 多加一個屬性。做完才發現，網址上一堆寫著 .min.js 的檔案，npm 套件裡根本沒有，是 CDN 幫我壓出來的。

NIKKE 事件的細節截至 2026 年 11 月 5 日，官方調查結果出來後我會補在文末。

附記：過程中還踩到一個 Windows 小坑。Claude Code 用 Git Bash 的 sed -i 改設定檔，整份 CRLF 被轉成 LF，內容只改一個字、檔案卻少了 1.1K 才發現。從備份還原後改用編輯工具處理。
